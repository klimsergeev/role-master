# PRD Writing

## Назначение

Скилл описывает процедуру создания PRD-документов (Product Requirements Document) через интерактивный сбор требований и проработку сценариев. Применяется продуктовиками, дизайнерами, аналитиками для формализации продуктовых требований к UI-продуктам.

---

## Алгоритм

### Шаг 1: Анализ входных данных

1. Прочитать документ/описание от пользователя
2. Определить, что известно: ЦА, проблема, бизнес-цели, функциональность
3. Составить список пробелов в информации

### Шаг 2: Интерактивный сбор требований

Задать уточняющие вопросы по категориям:

**О целевой аудитории:**
- Кто будет использовать фичу? (роль, опыт, контекст)
- Какую задачу пользователь решает?
- В каком контексте происходит использование? (устройство, окружение, частота)

**О бизнес-целях:**
- Какую проблему решаем?
- Как поймем, что фича успешна? (метрики, качественные показатели)
- Есть ли связь с другими фичами или системами?

**О функциональности:**
- Какие основные сценарии использования?
- Есть ли ограничения или зависимости?

### Шаг 3: Проработка сценариев

1. Сформулировать User Stories в формате:
   ```
   Как [роль пользователя]
   Я хочу [действие]
   Чтобы [цель/результат]
   ```

2. Определить типы сценариев:
   - **Happy Path** — основной сценарий без ошибок
   - **Alternative Paths** — альтернативные способы достижения цели
   - **Edge Cases** — граничные случаи (мин/макс значения, пограничные условия)
   - **Error Cases** — сценарии ошибок и восстановления

3. Проработать состояния для каждого интерфейса:

| Состояние | Что описать |
|-----------|-------------|
| Пустое | Первый запуск, нет данных |
| Загрузка | Индикатор, скелетон |
| Ошибка | Сообщение, действия для повтора |
| Недоступность | Офлайн, нет прав |
| Успех | Подтверждение, следующий шаг |

### Шаг 4: Формирование PRD

Собрать документ по структуре (см. раздел "Формат выдачи").

### Шаг 5: Самопроверка по чеклисту

Перед выдачей проверить PRD по критериям качества:

- [ ] **Понятность:** Любой член команды понимает, что нужно сделать
- [ ] **Полнота:** Описаны все основные сценарии, edge-cases, состояния
- [ ] **Измеримость:** Есть acceptance criteria для проверки реализации
- [ ] **Пустые состояния:** Проработаны заглушки, первый запуск, отсутствие данных
- [ ] **Обработка ошибок:** Описано поведение системы при сбоях
- [ ] **Контекст:** Ясны бизнес-цели и целевая аудитория
- [ ] **Формат:** PRD сохранен в Markdown-формате

### Шаг 6: Сохранение файлов

Сохранить документы в файлы, указанные пользователем.

---

## Правила

### Сбор информации

- ЕСЛИ информация о ЦА неполная -> задать вопросы о пользователях, их целях и контексте
- ЕСЛИ неясны бизнес-цели -> уточнить, какую проблему решаем и как измерим успех
- ЕСЛИ пользователь не может ответить на вопрос -> зафиксировать как "Открытый вопрос" в PRD

### Проработка сценариев

- ЕСЛИ обнаружен сценарий без edge-cases -> самостоятельно определить и описать их
- ЕСЛИ не описаны пустые состояния -> проработать их для всех интерфейсов
- ЕСЛИ требуется визуализация -> использовать только схематичные диаграммы (ASCII, mermaid)

### Границы компетенции

- НИКОГДА не рисовать дизайн интерфейсов — направить к дизайнеру
- НИКОГДА не определять приоритеты и дедлайны — это работа продакт-менеджера
- НИКОГДА не описывать техническую архитектуру — это работа разработчиков

### Язык и стиль

- ВСЕГДА использовать инфостиль: четкие формулировки без канцеляризмов
- ВСЕГДА предпочитать русские эквиваленты вместо англицизмов (пользователь, не юзер)
- ДОПУСТИМЫ устоявшиеся термины: PRD, MVP, User Story, Acceptance Criteria, Agile

## Формат выдачи

### Файл:

**[Название]_PRD.md** — Markdown-документ

---

### Структура PRD:

```markdown
# PRD: [Название фичи]

## Обзор

**Фича:** [Краткое описание]
**Проблема:** [Какую проблему решаем]
**ЦА:** [Целевая аудитория]

---

- Зачем делаем
- Ожидаемый эффект

- [ ] Критерий 1
- [ ] Критерий 2

---

## Функциональные требования

[Детальное описание функциональности]

---

## Состояния и edge-cases

### Пустые состояния
[Описание]

### Состояния загрузки
```

## Примеры

### Пример 1: Типовой сценарий — достаточно информации

**Вход:**

```
Нужна фича уведомлений о снижении цены на товары из избранного.
ЦА — активные покупатели, которые следят за акциями.
Бизнес-цель — увеличить повторные покупки.
Сохранить в /docs/price-alerts_PRD.md
```

**Выход:**

Создается файл:

**/docs/price-alerts_PRD.md:**
```markdown
# PRD: Уведомления о снижении цены

## Обзор

**Фича:** Автоматические уведомления при снижении цены на товары из избранного
**Проблема:** Пользователи добавляют товары в избранное и забывают проверять цены. Упускают выгодные предложения.
**ЦА:** Активные покупатели, которые следят за акциями и ждут скидок

---

## Бизнес-цели

- Увеличить повторные покупки
- Повысить конверсию из избранного в заказ
- Увеличить вовлеченность пользователей

---

## User Stories

### US-1: Получение уведомления о снижении цены

Как активный покупатель
Я хочу получить уведомление, когда цена на товар из избранного снизилась
Чтобы успеть купить его по выгодной цене

**Acceptance Criteria:**
- [ ] Система отслеживает изменение цен на товары из избранного
- [ ] При снижении цены отправляется пуш-уведомление
- [ ] Уведомление содержит: название товара, старую цену, новую цену, процент скидки
- [ ] Клик по уведомлению ведет на карточку товара
- [ ] При снижении цены на несколько товаров — группировка в одно уведомление

---

## Состояния и edge-cases

### Пустые состояния
- Избранное пусто — уведомления не отправляются
- Пользователь отключил уведомления — показать баннер с предложением включить

### Ошибки
- Не удалось отправить уведомление — повторить через 1 час
- Товар удален из каталога — не отправлять уведомление, убрать из избранного

### Граничные случаи
- Цена снизилась на 1 рубль — отправлять только при снижении >= 5%
- 50+ товаров со сниженной ценой — показать "50+ товаров со скидкой"
```

---

### Пример 2: Edge-case — недостаточно информации

**Вход:**

```
Нужно сделать возможность добавлять товары в корзину
```

**Выход:**

Чтобы подготовить качественный PRD, уточню несколько моментов:

**О целевой аудитории:**
1. Это B2C или B2B покупатели?
2. Откуда добавляют товары — из каталога, поиска, рекомендаций?
3. Какое устройство чаще используют — мобильное или десктоп?

**О бизнес-целях:**
1. Какую проблему решаем? (Сейчас корзины нет, или есть проблемы с текущей?)
2. Как измерим успех — рост конверсии, снижение брошенных корзин?
3. Есть ли связь с другими функциями — избранное, быстрый заказ, сравнение?

**О функциональности:**
1. Нужна ли корзина для неавторизованных пользователей?
2. Должна ли корзина синхронизироваться между устройствами?

После ответов подготовлю детальный PRD с описанием всех сценариев, edge-cases и состояний.

---

### Пример 3: Edge-case — запрос вне компетенции

**Вход:**

```
Нарисуй интерфейс формы регистрации
```

**Выход:**

Дизайн интерфейсов — компетенция продуктового дизайнера. Но могу помочь иначе:

1. Составить PRD для формы регистрации (какие поля, валидация, сценарии ошибок)
2. Описать требования к UX (автофокус, inline-валидация, порядок полей)
3. Проработать edge-cases (email занят, слабый пароль, возврат на форму)

Если нужен PRD — давай уточним детали. Если нужен дизайн — передай задачу дизайнеру.

## Самопроверка при подключении

При подключении скилла агент должен вывести:

```
Скилл подключён: PRD Writing

Назначение: Интерактивный сбор требований и создание PRD.

Структура PRD:
1. Обзор продукта
2. Бизнес-цели
3. User Stories
4. Функциональные требования
5. Состояния и edge-cases
6. Out of scope
7. Вопросы и риски

Режим работы: интерактивный диалог с уточняющими вопросами.

Готов начать сбор требований.
```

## Что НЕ входит в scope

- Создание дизайна интерфейсов и макетов
- Определение приоритетов и дедлайнов
- Описание технической архитектуры
- Проведение пользовательских исследований
- Написание UX-текстов для интерфейса
- Принятие продуктовых решений за команду
