# Окно и запись: `resize_window`, `gif_creator`

Два инструмента, у которых схема не называет ни одного ограничения, а ограничений много — и оба важнейших измерены, а не выведены.

> Пометки происхождения: **наблюдение** — измерено живым прогоном инструмента; **по схеме** — взято из схемы инструмента и вживую не проверялось. Срез данных — в SKILL.md.

---

## `resize_window`

**Назначение.** Изменить размер окна браузера. «Useful for testing responsive designs or setting up specific screen sizes.»

**Параметры** — все три обязательные:

| Параметр | Тип | Что это |
|---|---|---|
| `width` | number | Пиксели |
| `height` | number | Пиксели |
| `tabId` | number | Нужен, чтобы определить окно |

**Подводных камней схема не называет.** Ограничений по минимальному и максимальному размеру в ней нет. Всё, что ниже, — измерено.

### Границы

Размер окна после каждого вызова снимался **независимо от браузера** — через геометрию окна на уровне операционной системы, а не через `window.innerWidth` страницы. Это принципиально: измерение со страницы даёт неверный ответ (см. ниже). Экран машины — 1512×982 логических точек, рабочая область 1512×948.

**Верхняя граница — жёсткая, задана в самом инструменте.** Запрос 5000×5000:

```
Failed to resize window: Dimensions exceed 8K resolution limit. Maximum dimensions are 7680x4320
```

Проверка идёт **по каждой стороне отдельно**: 5000 по ширине укладывается в 7680, но 5000 по высоте превышает 4320 — и вызов отклонён. Значение 7681×4320 отклоняется тоже: 7680 — включительный предел, и проверка на 8K выполняется раньше всех прочих.

**Вторая, более близкая граница — видимость окна на экране.** Запрос 3000×2000, укладывающийся в 8K, отклонён другой ошибкой:

```
Failed to resize window: Invalid value for bounds. Bounds must be at least 50% within visible screen space.
```

Граница зависит не только от размера, но и от положения окна, поэтому единого числа у неё нет. Практический ориентир: при окне, прижатом к левому краю экрана шириной 1512, размер **2400×900 принят** и применён — окно вполне может быть **шире экрана**, лишь бы на экране оставалась достаточная его часть.

**Нижняя граница — молчаливое подтягивание вверх, без ошибки.** Инструмент рапортует об успехе запрошенными числами, а окно получает другие:

| Запрошено | Фактический размер окна | Что произошло |
|---|---|---|
| 500×300 | 500×375 | ширина принята, высота поднята до 375 |
| 300×300 | 500×375 | обе стороны подняты |
| 400×700 | 500×700 | ширина поднята до 500, высота принята |
| 600×100 | 600×375 | ширина принята, высота поднята до 375 |
| 900×600 | 900×600 | принято как есть |

Минимум — **500 в ширину и 375 в высоту**. Ниже окно не уменьшается, но **ошибки не будет**: ответ «Successfully resized window … to 300x300 pixels» приходит и тогда, когда окно осталось 500×375. Фактический размер надо проверять самостоятельно.

**Особые значения**

| Вход | Поведение |
|---|---|
| `width: 0, height: 0` | `Failed to resize window: Both width and height parameters are required` — ноль трактуется как отсутствующий параметр, а не как значение |
| Отрицательные | `Failed to resize window: Width and height must be positive numbers` |
| Дробные (800.7 × 600.4) | Принимаются, дробная часть отбрасывается: ответ «to 800x600 pixels», окно ровно 800×600 |

Ноль стоит отметить отдельно: сообщение говорит о «required parameters», хотя параметры переданы. Тот, кто вычислит нулевую ширину и получит этот ответ, будет искать ошибку не там.

### Главная ловушка: окно меняется, а страница об этом не знает

Это важнее самих границ, потому что бьёт по заявленному назначению инструмента — проверке адаптивной вёрстки.

После успешного изменения окна до 2400×900 страница продолжала сообщать `innerWidth: 1512, innerHeight: 744`, а `read_page` — прежнюю строку `Viewport: 1512x744`. При этом окно на уровне операционной системы действительно имело ширину 2400. **Область просмотра страницы не обновилась вслед за окном.**

Причина установлена: вкладка сессии MCP не была активной вкладкой в своём окне — `document.visibilityState` возвращал `hidden`. У невидимой вкладки Chrome не пересчитывает размеры, и значения замирают. Дополнительный признак того же состояния: `window.outerWidth` и `outerHeight` возвращали то `0`, то устаревшие `784×386` — числа, не совпадавшие ни с одним запрошенным размером.

Что из этого следует:

1. **Проверять раскладку по `window.innerWidth` после `resize_window` нельзя** — можно получить прежнее значение и решить, что вёрстка не отзывчива.
2. Группа вкладок MCP создаётся в отдельном окне, и вкладка агента **не обязана быть активной** — рядом может лежать пустая вкладка, которая и остаётся активной. Перед проверкой адаптива надо убедиться, что рабочая вкладка активна.
3. **Высоту области просмотра надо читать из ответа, а не вычитать из высоты окна.** При одном и том же запросе 1512×921 в разные моменты получались `Viewport: 1512x800` и `Viewport: 1512x688`; разница в 79 точек — панель закладок, которая показывается на новой вкладке и прячется на обычной странице.

Признаки для распознавания обоих отказов — в [silent-failures.md](silent-failures.md).

## `gif_creator`

**Назначение.** Записать последовательность браузерных действий и выгрузить анимированный GIF с наложениями: метки кликов, подписи действий, полоса прогресса, водяной знак.

**Параметры**

| Параметр | Тип | Обязательный | По умолчанию | Что делает |
|---|---|---|---|---|
| `action` | string | да | — | `start_recording`, `stop_recording`, `export`, `clear` |
| `tabId` | number | да | — | Определяет группу вкладок; все операции привязаны к группе |
| `download` | boolean | нет | — | «Always set this to true for the `export` action only»; вызывает скачивание GIF браузером |
| `filename` | string | нет | `recording-[timestamp].gif` | Имя файла |
| `options` | объект | нет | см. ниже | Наложения и качество |

Поля `options`: `showClickIndicators` (оранжевые круги в местах кликов), `showDragPaths` (красные стрелки перетаскиваний), `showActionLabels` (чёрные подписи действий), `showProgressBar` (оранжевая полоса внизу), `showWatermark` (водяной знак Claude) — все булевы, по умолчанию `true`; `quality` — от 1 до 30, меньше значит лучше и медленнее, по умолчанию **10**.

**Порядок работы из схемы.** Сразу после `start_recording` сделать снимок, чтобы захватить исходное состояние первым кадром; непосредственно перед `stop_recording` сделать снимок, чтобы захватить финальное состояние последним кадром. Для выгрузки — либо `coordinate` для перетаскивания в элемент страницы, либо `download: true`.

**Предупреждение доки Claude Code, которого нет в схеме:** «The recording captures everything visible in the browser, including account details on logged-in pages, so review it before sharing it outside your team». Разбор риска — в [security.md](security.md).

**Прогон:** `start_recording`, `stop_recording`, `clear` — наблюдение; **`export` вживую не запускался** (чтобы не скачивать файл) и описан по схеме.

**Наблюдения**

Ответ на запуск записи содержит **предел в 50 кадров, которого нет в схеме**:

```
Started recording browser actions for this tab group. All computer and navigate tool actions will now be captured (max 50 frames). Previous frames cleared.
```

Три вещи отсюда:

1. **50 кадров — потолок.** Длинный сценарий в одну запись не поместится, и агент узнаёт о пределе только из ответа на запуск.
2. **Запуск записи стирает предыдущие кадры** («Previous frames cleared») — повторный `start_recording` не продолжает запись, а обнуляет накопленное.
3. Захватываются именно действия инструментов `computer` и `navigate`, а не всё подряд.

Остальные ответы:

```
Stopped recording for this tab group. Captured 4 frames. Use 'export' to generate GIF or 'clear' to discard.
Cleared 4 frames for this tab group. Recording stopped.
```

Число кадров названо — по нему видно, не упёрлись ли в предел.

**Кадр приходится не на каждый вызов.** За пять действий (`hover`, `scroll_to`, `scroll`, `zoom` и служебные) записалось 4 кадра. Оценивать длину сценария по числу вызовов нельзя — смотреть надо на счётчик в ответе `stop_recording`.
