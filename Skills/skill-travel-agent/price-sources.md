# Источники цены (travel-API и страница поставщика, read-only)

## Назначение

Каталог источников цены для советника: ценовой travel-API (read-only) и страница поставщика, прочитанная в браузере, — два равноправных источника. Здесь же тест «поставщик или агрегатор», оговорки браузерной цены и микро-раздел ценово-временны́х эвристик «когда дешевле». Грузится при вопросах про цену/бюджет/«куда дёшево»/«когда дешевле» и перед тем, как перенести в план число, увиденное на странице; при обычном планировании не нужен. Как честно подать цену — в [verification.md](verification.md).

## Главное правило

Цена берётся только у того, кто её назначил, — у первоисточника. Первоисточников два, и они равноправны:

| Класс источника | Что это | Провенанс |
|---|---|---|
| Ценовой travel-API (read-only) | Travelpayouts Data API, Duffel, LiteAPI — каталог ниже | вендор + дата запроса |
| Страница поставщика в браузере | официальный сайт перевозчика, отеля, музея; собственный движок бронирования оператора | адрес страницы + дата и время просмотра |

Запрещены: память модели, сниппет веб-поиска и любой агрегатор — в том числе открытый в том же браузере. Браузер не превращает пересказ в первоисточник: разрешает не инструмент, а **поставщик как автор числа**. Разбор запрещённых каналов — в разделе «Явно ИСКЛЮЧЕНО как источник цены».

Каждая цена показывается с провенансом своей формы; кэш-цена — с пометкой «ориентировочно, проверить актуальную», браузерная — как персональная и предварительная. Правила подачи — в [verification.md](verification.md).

## Три ценовых travel-API (все в 1.0.0, read-only)

### Travelpayouts / Aviasales Data API — бесплатный базовый источник (ориентир, СНГ-центричен)

- **Доступ:** бесплатен, открыт — нужен только токен из партнёрского кабинета. Порог 50 000 MAU относится к real-time Search API, а НЕ к Data API.
- **Что отдаёт:** самые дешёвые цены по маршруту, календарь цен по дням/месяцам, матрицы недели/месяца, «куда дёшево из города».
- **Природа данных:** кэш — наполняется поисками пользователей Aviasales/Jetradar за 48 ч; хранится, по справке вендора, «от 2 до 7 дней в зависимости от типа запроса» (подтверждено дословно: support.travelpayouts.com, статья `Aviasales Data API`). Фильтр свежести v1 — поле `expires_at` (UTC). Живой прогон уточнил: `/v1/prices/cheap` поле `actual` НЕ возвращает (прежнее допущение про `actual=0/1` для этого эндпоинта неверно — `actual` относится к v2). Свежесть по v1 определяется только через `expires_at`.
- **Гео-перекос:** Aviasales-центрично — СНГ плотно, не-СНГ слабее и менее предсказуемо. Для не-СНГ маршрутов честно помечать сниженную надёжность кэша.
- **Позиционирование вендора:** Data API «to inform users / generate content» — ниша ориентира советника.
- **Нюанс TTL (честно):** диапазон 2–7 дней подтверждён, но поэндпоинтный TTL (какой путь живёт сколько) публично НЕ документирован — вендор задаёт число только на уровне всего Data API «по типу запроса». Практический ориентир: запись может быть возрастом до ~7 дней; фильтр по `expires_at` отсекает устаревшее.
- **Rate-limit (честно, обе стороны):** у Data API нет отдельного ЧАСОВОГО капа (support-статья `API rate limits`, дословно: «does not have restrictions on queries per hour»), но действует минутный кап. Живые заголовки ответа показали `X-Rate-Limit: 300`, `X-Rate-Limit-Remaining`, `X-Rate-Limit-Reset` (секунды) — по факту наблюдалось 300 запросов/мин (а НЕ документированные ранее 60/мин); при превышении — 429. Подавать честно: наблюдался кап 300/мин, не занижать и не завышать. НЕ подавать как «безлимитный»: без часового ограничения ≠ без лимита вообще.
- ⚠️ Не сверено дословно: полный текст ToS про AI-ассистентов (юр. документ целиком не открыт — support.travelpayouts.com за Cloudflare, 403; данные из зеркал спецификации и целевых поисков).

### Duffel (рейсы) — живые read-only цены

- Read-only поиск/оферы (search/offers) дают живые цены на рейсы — точность выше кэша Travelpayouts, глобальный охват. Open signup «за минуту», zero up-front, 300+ авиакомпаний. Официального MCP нет — community (`ravinahp/flights-mcp`, 210★).
- **Только чтение цен (search/offers). Заказы (order) не создаём, бронирование не проектируется.**
- Операционный нюанс read-only: excess-search fee $0.005 действует при ratio search-to-book 1500:1; советник только читает цены и не бронирует вовсе — держать в уме как потенциальную стоимость интенсивного поиска (pricing сверен дословным fetch duffel.com/pricing 20.07.2026).

### LiteAPI (отели) — живые read-only rates

- Read-only rates дают живые цены на отели, 2.6M+ отелей, open self-serve без договоров, официальный MCP (`liteapi-travel/mcp-server`).
- **Только чтение rates. Prebook/Book не вызываем, бронирование не проектируется.**
- ⚠️ Часть тарифов LiteAPI сверена дословно, часть — из выдачи; Duffel Stays-детали не подтверждены.

**Как это остаётся советническим:** показать цену с провенансом и датой — это совет, а не бронь. Верно для обоих источников: чтение цены (search/offers/rates у API, текст страницы у поставщика) ≠ создание заказа. Order/prebook/book не вызываются, кнопка оформления не нажимается.

## Как вызвать (рантайм): Python-скрипт к Travelpayouts Data API

Это раздел про **КАК** физически достать цену из Travelpayouts Data API. Проверено вживую (все три эндпоинта ниже вернули HTTP 200 с реальными ценами) — вносится как проверенные факты.

**Метод: агент пишет и запускает Python-скрипт к REST-API. Никакого MCP.** Обычный HTTP-запрос через stdlib `urllib` (+ `certifi` для TLS). Требуется рантайм с исполнением кода (Bash/Python) и заданный токен. Готовый референс-скрипт — [scripts/travelpayouts_probe.py](scripts/travelpayouts_probe.py); агент запускает его или адаптирует как шаблон.

**Условие применимости.** Метод работает только там, где есть исполнение кода И задан токен. Где кода или токена нет — остаётся второй источник, страница поставщика в браузере, и лишь при его недоступности честный отказ «цену дать не могу без источника» (лестница — в разделе «Нет подключённого API → сначала страница поставщика, потом честный отказ»). Роль решает КОГДА тянуться за ценой и каким источником; скилл держит КАК.

**Хост и авторизация.**

- Хост: `https://api.travelpayouts.com`.
- Токен — в заголовке `X-Access-Token: <token>` (либо параметром `token=<token>` в query).
- Токен берётся ТОЛЬКО из переменной окружения `TRAVELPAYOUTS_TOKEN`. Скрипт файл на диске не ищет и путь к нему не хранит; `.env` пользователь передаёт в чат по мере необходимости, а перед запуском токен экспортируется в окружение. **НИКОГДА не хардкодить токен и не выводить его в чат / в логи / в сообщения.**

**Проверенные эндпоинты (все три вернули HTTP 200 с реальными данными).**

| Эндпоинт | Назначение | Ключевые query-параметры |
|---|---|---|
| `GET /v1/prices/cheap` | Самая дешёвая цена по маршруту | `origin=IATA`, `destination=IATA`, `currency=rub` |
| `GET /v1/prices/calendar` | Цена по дням (питает эвристику «когда дешевле») | `origin=IATA`, `destination=IATA`, `currency=rub` |
| `GET /aviasales/v3/prices_for_dates` | Цена на КОНКРЕТНУЮ пару дат (туда/обратно) | `origin`, `destination`, `departure_at` (YYYY-MM или YYYY-MM-DD), `return_at`, `one_way=true/false`, `direct=true/false`, `sorting=price`, `limit`, `market=ru`, `currency` |

**Реальная схема ответа (дословно с живого запроса).**

`/v1/prices/cheap`:

```json
{"data":{"AER":{"0":{"airline":"FV","departure_at":"2026-11-25T06:30:00+03:00","return_at":"...","expires_at":"2026-07-22T12:33:57Z","price":15840,"flight_number":6559,"duration":535}}},"currency":"rub","success":true}
```

`/v1/prices/calendar`:

```json
{"data":{"2026-07-23":{"origin":"LED","destination":"AER","airline":"U6","departure_at":"...","expires_at":"...","price":26986,"flight_number":547,"transfers":0}},"success":true}
```

Структура: `data` → ключ по коду направления (у `cheap`) или по дате (у `calendar`) → оффер с полями `price`, `airline`, `flight_number`, `departure_at`, `expires_at`, `transfers`/`duration`. Свежесть — по `expires_at` (UTC). Проверять `success` в корне.

**v3 `/aviasales/v3/prices_for_dates` (проверено вживую, ~60 HTTP 200).** Закрывает дыру v1: берёт конкретную пару дат «туда/обратно», чего `cheap`/`calendar` не умеют. Поля ответа: `flight_number`, `link`, `origin_airport`, `destination_airport`, `departure_at`, `airline`, `return_at`, `price`, `gate`, `transfers`, `return_transfers`, `duration`, `duration_to`, `duration_back`.

- **`expires_at` НЕТ вовсе.** Маркер снимка — `search_date=DDMMYYYY` внутри строки `link`. Выше точность по датам, слабее верифицируемость свежести, чем у v1 — подавать с оговоркой «дата снимка …, актуальную проверить» (правила — в [verification.md](verification.md)).
- **Прямые рейсы не всплывают сами.** Месячный запрос с `sorting=price` может не вернуть ни одного беспересадочного, хотя они есть в кэше — для прямых нужен отдельный запрос с `direct=true`. Без него легко ошибочно заключить «прямых нет».

**Честные нюансы, уточнённые живым прогоном (сохранять точно):**

1. **`actual` у `/v1/prices/cheap` НЕ возвращается.** Свежесть только по `expires_at` (UTC). Поле `actual` относится к v2, а не к v1 `cheap` — прежнее допущение про `actual=0/1` для этого эндпоинта неверно.
2. **`expires_at` близко к моменту снимка** (сегодня). Цену подавать с пометкой «ориентировочно, по кэшу, `expires_at`=…», не как гарантированную.
3. **Rate-limit (живые заголовки):** `X-Rate-Limit: 300`, `X-Rate-Limit-Remaining`, `X-Rate-Limit-Reset` (секунды) — по факту наблюдалось **300 запросов/мин**, а НЕ документированные ранее 60/мин. Подавать честно: наблюдался 300/мин; при превышении — 429.
4. **TLS-нюанс (обязательно при написании скрипта):** правильный CA-бандл зависит от окружения. Порядок: сначала смотри env `SSL_CERT_FILE`/`REQUESTS_CA_BUNDLE` (в проксированных окружениях там системный бандл с CA egress-прокси, которого нет в certifi → `CERTIFICATE_VERIFY_FAILED: self-signed certificate in chain`); если их нет — падай на `certifi.where()` (нужен, напр., на python.org-сборке macOS, где системный бандл не настроен). Два зеркальных случая — проверяй env перед certifi. Это нюанс окружения, а НЕ проблема API.
5. **Гео:** СНГ покрыт плотно; не-СНГ тоже отдаёт цену (напр. MOW→TYO вернул данные) — перекос про плотность/надёжность кэша, а не про «пусто».

**Мини-алгоритм.**

1. Проверь: есть исполнение кода и токен в окружении? Если нет — переходи ко второму источнику, странице поставщика (раздел ниже), и только при его недоступности — к честному отказу.
2. Запусти [scripts/travelpayouts_probe.py](scripts/travelpayouts_probe.py) (или адаптированный шаблон) с `origin`/`destination`/`currency`; токен — из `TRAVELPAYOUTS_TOKEN`, в аргументы командной строки токен НЕ передавать.
3. Разбери JSON: `success`, оффер(ы) в `data`, поле `price`, свежесть по `expires_at`.
4. Подай цену с провенансом и пометкой свежести (правила — в [verification.md](verification.md)). Кэш-цена — всегда «ориентировочно».

**Расшифровка кодов авиакомпаний.** Справочник `https://api.travelpayouts.com/data/ru/airlines.json` (без токена) — массив с `code` и `name`. Коды из ответов (`airline`: FV, U6, VF…) расшифровывать по нему, а НЕ по памяти модели (иначе — галлюцинация названия). Общий приём: если у API есть справочная часть, коды берутся из неё.

## Страница поставщика в браузере — второй источник

Число, прочитанное на странице поставщика, идёт в план и в бюджет наравне с ценой из API.

Основание: прежний запрет держался на том, что цена приходит пересказом — сниппетом выдачи или витриной агрегатора, оторванными от маршрута и даты. Страница поставщика этому описанию не отвечает: это живой инвентарь на конкретный маршрут и конкретные даты, по свежести не хуже кэша Travelpayouts, а обычно лучше.

Что при этом НЕ меняется — граница финансового обязательства. Прочитать число со страницы значит прочитать; бронь, оплата, ввод платёжных данных и подтверждение платежа остаются запрещёнными (см. [browser-use.md](browser-use.md)). Разрешение касается статуса цены как данных, а не набора допустимых действий.

### Тест: поставщик или агрегатор

Решающий вопрос один:

> **Кто окажет услугу за это число — владелец сайта или кто-то другой?**

- Владелец сайта (его рейс, его номер, его вход, его тур) → **поставщик**, цену брать можно.
- Услугу окажет кто-то другой, сайт лишь показывает чужое предложение → **агрегатор**, цену не брать.

Четыре признака, различимых на странице до всякого нажатия:

| Признак | Поставщик | Агрегатор |
|---|---|---|
| Что на экране | собственные тарифы одной услуги: Эконом/Комфорт/Бизнес на одном рейсе, типы номеров одного отеля | витрина сравнения: список разных исполнителей с ценами рядом и сортировкой «по цене» |
| Чьи бренды в строках выдачи | один — владельца сайта | чужие логотипы перевозчиков, отелей, продавцов |
| Куда ведёт оформление | остаётся на том же сайте | «перейти на сайт партнёра», «цена у партнёра», ссылка на чужой домен — видно по адресу ссылки, нажимать не нужно |
| Что написано в подвале и в правилах | собственные реквизиты перевозчика, отеля, оператора, номер лицензии | оговорка «сервис не является продавцом», «не оказываем услуги перевозки», «цены предоставлены партнёрами» |

**Разбор краёв:**

- **Чужой домен ≠ агрегатор.** Собственный движок бронирования отеля или оператора часто живёт на отдельном домене или поддомене (белая метка вида `book.*`, встроенный виджет системы бронирования). Инвентарь при этом принадлежит поставщику — цена разрешена. Смотреть надо, чья услуга продаётся, а не какой адрес в строке.
- **Свой домен ≠ поставщик.** Сайт перевозчика или отеля рядом со своим продаёт и чужое: партнёрские рейсы, соседние отели, экскурсии подрядчика, страховку. Судить нужно конкретное предложение, а не сайт целиком — чужое предложение на сайте поставщика остаётся пересказом.
- **Признаки разошлись или ответа нет** → считать агрегатором и цену не брать. Неясность решается в пользу запрета — так же, как в тесте перед действием в [browser-use.md](browser-use.md).
- **Именованные примеры не заменяют теста.** Kayak, Aviasales, Skyscanner, Booking, Trivago — агрегаторы, но перечень конечен, а сайтов бесконечно много. Незнакомый сайт разбирается признаками, а не тем, попал ли он в список.

### Две оговорки, которых нет у API

1. **Браузерная цена персонализирована.** Она зависит от авторизованной сессии, региона, валюты профиля и куки. API отдаёт цену вне персонализации, страница — нет. Это не повод запрещать, но подавать браузерную цену как «цену для всех» нельзя: это то, что показывают **этому** пользователю **сейчас**. Оговорка проговаривается в тексте выдачи, а не подразумевается.
2. **Показанное число может вырасти на оформлении.** Сборы, налоги, плата за багаж и место, курортный сбор, комиссия способа оплаты часто добавляются на последнем шаге, которого советник не проходит. Брать то, что видно, и помечать: «до сборов и налогов, если страница не сказала иначе». ЕСЛИ страница показывает итог с разбивкой → брать итог и помечать его как итоговый.

### Что записать в момент просмотра

Провенанс браузерной цены собирается на месте, а не восстанавливается потом:

- **адрес страницы** — полный, с параметрами маршрута и дат, если они в адресе;
- **дата и время просмотра** с часовым поясом: у браузерной цены время значимо, страница живая и число меняется в течение дня;
- **что входит в число** — тариф, класс, число гостей и ночей, возвратность, багаж;
- **срок годности**, если страница его показывает («цена действует N минут», «осталось N мест по этой цене»).

Без этого набора число в документ не попадает — ровно как цена из API без вендора и даты. Формы провенанса и чек-лист — в [verification.md](verification.md); колонки бюджета — в [trip-document.md](trip-document.md).

## Явно ИСКЛЮЧЕНО как источник цены

- **Память модели — ЗАПРЕЩЕНА (галлюцинация).** Цена «по памяти» / «со слов LLM» — правдоподобная галлюцинация. У Gemini API (в т. ч. через OpenRouter) нет доступа к инвентарю Google Flights/Hotels; grounding = веб-поиск (сниппеты + цитаты), а не bookable-фиды; через OpenRouter родной grounding ненадёжен/спорен. Цена всегда только от первоисточника — из travel-API или со страницы поставщика — и всегда с провенансом.
- **Веб-поиск как источник ЦЕНЫ — ЗАПРЕЩЁН (решение пользователя).** Сниппет выдачи пересказывает чужую страницу и отстаёт от неё, а привязку к маршруту и датам теряет. Веб-поиск остаётся для прочих времязависимых фактов (часы, расписания, визы, сезонные закрытия, существование локаций), но цену из него НЕ берём. Нашёлся сниппет с ценой → это повод открыть страницу поставщика и прочитать число там, а не переписать сниппет.
- **Агрегатор — ЗАПРЕЩЁН, в том числе открытый в браузере.** Kayak, Aviasales, Skyscanner, Booking, Trivago и любой другой сайт, показывающий чужие предложения витриной, остаётся пересказом: браузер этого не меняет. Разрешает не инструмент, а поставщик как автор числа. Как отличить одно от другого — в разделе «Тест: поставщик или агрегатор».
- **Amadeus Self-Service — МЁРТВ.** Портал декоммиссирован 17.07.2026: регистрация новых остановлена весной 2026, ключи деактивированы и перестали отдавать данные. Enterprise не затронут (закрывается только self-service). Как источник НЕ рассматриваем. Статус перекрёстно подтверждён 3 независимыми источниками (PhocusWire, tripgic, ignav; дата и механика совпадают); прямой fetch developers.amadeus.com нашим окружением не прошёл (пустой JS-рендер), но по данным tripgic уведомление сообщается и на самом Amadeus for Developers.

## Нет подключённого API → сначала страница поставщика, потом честный отказ

Отсутствие токена больше не означает автоматического «цену дать не могу»: у советника два источника, и второй не требует ни ключа, ни рантайма с исполнением кода. Порядок:

1. **Ценовой travel-API подключён** (есть исполнение кода и токен) → цена из API с вендором и датой.
2. **API нет, но есть браузер и известен поставщик** → открыть его страницу, прочитать число, оформить провенансом страницы и подать с двумя оговорками (персональная, до сборов). Это полноценная цена, а не заменитель.
3. **Ни API, ни доступного поставщика** → честно «цену дать не могу / нужен подключённый источник или сайт поставщика». НЕ выдумывать число, НЕ брать из веб-поиска, НЕ брать с агрегатора.

Базовый бесплатный Travelpayouts Data API снимает первый шаг простой токен-настройкой; ступень 2 полезна и при подключённом API — как проверка кэш-цены живым числом от самого поставщика.

## Ценово-временны́е эвристики «когда дешевле»

Провенанс: `issledovanie-deshevye-dni-aviabilety.md` (июль 2026; Google Flights, CheapAir, Aviasales, Hopper, Expedia + академика Hotle et al. 2015). Это знание-подсказка для перебора дат, а НЕ источник цены.

**Жёсткое правило подачи: КАЧЕСТВЕННО, без жёстких процентов.** Точные % (−14 %, −17 %, 42 дня и т. п.) в скилл намеренно НЕ вносятся — в источниках они местами на вторичных пересказах и привязаны к конкретному рынку/маршруту, гарантировать их для произвольного рейса нельзя. Всегда с меткой рынок/год и оговоркой «средние по рынку».

Три фактора (качественно):

1. **День покупки (день недели заказа) — миф, не влияет.** НЕ советовать «покупай во вторник/воскресенье» как способ сэкономить. При вопросе — честно развенчать: день недели заказа на практике не влияет (Google / CheapAir / Aviasales — влияние ≈ ноль, тонет в ежедневных колебаниях).
2. **День вылета — влияет реально.** Воскресенье обычно самый дорогой день вылета; середина недели (вт/ср) обычно дешевле. Подавать как подсказку по ГИБКИМ ДАТАМ, не догму: «если даты гибкие, проверю вт/ср и соседние дни».
3. **Горизонт бронирования — влияет сильнее всего.** «Не в последний момент и не слишком рано»: ориентир ≈ 3 недели – 3 месяца до вылета для внутренних; для праздников/пиков и лета — раньше. Предупреждать: последние ~2–3 недели цены круто растут.

**Эвристика ≠ факт по маршруту.** Роль использует «дни недели / окно» как фильтр-подсказку для перебора: «проверю вт/ср и соседние гибкие даты и сравню», а НЕ выдаёт среднерыночную закономерность за цену конкретного рейса. Цена — только из первоисточника на конкретные даты: travel-API или страница поставщика (правила — в [verification.md](verification.md)). Формула честной подачи: «Обычно по рынку X (средние, источник/год); давай проверю фактическую цену на твои даты и пару соседних midweek-дней в API».

**Сетка дат «вылет × возврат» для сопоставимости.** Когда запрос — «туда примерно тогда-то, обратно около такого-то», один месячный запрос даёт разрозненные пары без осей. Чтобы увидеть, где в окне дешевле, перебери сетку: N дат вылета × M дат возврата (напр. 5×5 = 25 точечных запросов к `/aviasales/v3/prices_for_dates` на каждую пару) → матрица цен, из неё виден минимум и цена сдвига дня. Дёшево: 25 запросов — секунды, кап 300/мин с запасом.

**US-цифры ≠ РФ.** Для российского пользователя опираться на РФ-данные (Aviasales) и проверку в API, не переносить US-проценты. Всегда маркировать рынок и год.

## Примеры

### Пример 1: «Куда дёшево из Москвы в марте»

**Вход:** запрос ориентировочных дешёвых направлений.

**Результат:** через Travelpayouts Data API (кэш, СНГ-центричен) — «куда дёшево из города» с пометкой «ориентировочно, по кэшу на дату X, актуальную проверить». Для точной цены на конкретные даты — Duffel (рейсы).

### Пример 2: «В какой день покупать билет»

**Вход:** вопрос про день покупки.

**Результат:** развенчать миф — день недели заказа не влияет на цену; предложить вместо этого проверить гибкие даты вылета (середина недели дешевле) в travel-API. Никаких «покупай во вторник» как совета сэкономить, никаких конкретных процентов.

### Пример 3: Два числа на одном экране (edge-case)

**Вход:** ценовой API не подключён, пользователь просит цену перелёта. Агент открыл в браузере два сайта: витрину, где по этому маршруту сравниваются семь перевозчиков и самое дешёвое предложение — 18 400 ₽, и сайт самого перевозчика, где тот же рейс на те же даты стоит 19 100 ₽.

**Результат:** в план идёт **19 100 ₽** — с адресом страницы перевозчика, датой и временем просмотра, тарифом и пометкой «цена этой сессии, до сборов и багажа». 18 400 ₽ не берутся, хотя число дешевле и видно в том же браузере: витрина сравнивает чужие предложения, кнопка ведёт на сайт партнёра, в подвале стоит оговорка о том, что сервис не продавец — по тесту это агрегатор. Разница не замалчивается: агент говорит, что на витрине видел предложение дешевле, и передаёт ссылку пользователю — проверить и оформить самому. Что нельзя — переписать 18 400 ₽ в бюджет как проверенную цену.
