# Источники цены (travel-API, read-only)

## Назначение

Каталог ценовых travel-API для советника: цена берётся ТОЛЬКО из travel-API (read-only). Плюс микро-раздел ценово-временны́х эвристик «когда дешевле». Грузится только при вопросах про цену/бюджет/«куда дёшево»/«когда дешевле»; при обычном планировании не нужен. Как честно подать цену — в [verification.md](verification.md).

## Главное правило

Цена — ТОЛЬКО из travel-API (read-only). НИКОГДА из памяти модели и НИКОГДА из веб-поиска. Все три API ниже — в версии 1.0.0. Каждая цена показывается с провенансом (источник + дата / `actual` / `expires_at`); кэш-цена — с пометкой «ориентировочно, проверить актуальную». Правила подачи — в [verification.md](verification.md).

## Три ценовых travel-API (все в 1.0.0, read-only)

### Travelpayouts / Aviasales Data API — бесплатный базовый источник (ориентир, СНГ-центричен)

- **Доступ:** бесплатен, открыт — нужен только токен из партнёрского кабинета. Порог 50 000 MAU относится к real-time Search API, а НЕ к Data API.
- **Что отдаёт:** самые дешёвые цены по маршруту, календарь цен по дням/месяцам, матрицы недели/месяца, «куда дёшево из города».
- **Природа данных:** кэш — наполняется поисками пользователей Aviasales/Jetradar за 48 ч; хранится, по справке вендора, «от 2 до 7 дней в зависимости от типа запроса» (подтверждено дословно: support.travelpayouts.com, статья `Aviasales Data API`). У каждой цены поля `actual` (0/1) и `expires_at` — честный фильтр свежести.
- **Гео-перекос:** Aviasales-центрично — СНГ плотно, не-СНГ слабее и менее предсказуемо. Для не-СНГ маршрутов честно помечать сниженную надёжность кэша.
- **Позиционирование вендора:** Data API «to inform users / generate content» — ниша ориентира советника.
- **Нюанс TTL (честно):** диапазон 2–7 дней подтверждён, но поэндпоинтный TTL (какой путь живёт сколько) публично НЕ документирован — вендор задаёт число только на уровне всего Data API «по типу запроса». Практический ориентир: запись может быть возрастом до ~7 дней; фильтр по `actual`/`expires_at` отсекает устаревшее.
- **Rate-limit (честно, обе стороны):** у Data API нет отдельного ЧАСОВОГО капа (support-статья `API rate limits`, дословно: «does not have restrictions on queries per hour»), но действует общий платформенный дефолт 60 запросов/мин на метод; при превышении — 429, заголовки `X-Rate-Limit*`. НЕ подавать как «безлимитный»: без часового ограничения ≠ без лимита вообще.
- ⚠️ Не сверено дословно: полный текст ToS про AI-ассистентов (юр. документ целиком не открыт — support.travelpayouts.com за Cloudflare, 403; данные из зеркал спецификации и целевых поисков).

### Duffel (рейсы) — живые read-only цены

- Read-only поиск/оферы (search/offers) дают живые цены на рейсы — точность выше кэша Travelpayouts, глобальный охват. Open signup «за минуту», zero up-front, 300+ авиакомпаний. Официального MCP нет — community (`ravinahp/flights-mcp`, 210★).
- **Только чтение цен (search/offers). Заказы (order) не создаём, бронирование не проектируется.**
- Операционный нюанс read-only: excess-search fee $0.005 действует при ratio search-to-book 1500:1; советник только читает цены и не бронирует вовсе — держать в уме как потенциальную стоимость интенсивного поиска (pricing сверен дословным fetch duffel.com/pricing 20.07.2026).

### LiteAPI (отели) — живые read-only rates

- Read-only rates дают живые цены на отели, 2.6M+ отелей, open self-serve без договоров, официальный MCP (`liteapi-travel/mcp-server`).
- **Только чтение rates. Prebook/Book не вызываем, бронирование не проектируется.**
- ⚠️ Часть тарифов LiteAPI сверена дословно, часть — из выдачи; Duffel Stays-детали не подтверждены.

**Как это остаётся советническим:** показать цену из travel-API с провенансом/датой — это совет, а не бронь. Чтение цены (search/offers/rates) ≠ создание заказа: order/prebook/book не вызываются.

## Явно ИСКЛЮЧЕНО как источник цены

- **Память модели — ЗАПРЕЩЕНА (галлюцинация).** Цена «по памяти» / «со слов LLM» — правдоподобная галлюцинация. У Gemini API (в т. ч. через OpenRouter) нет доступа к инвентарю Google Flights/Hotels; grounding = веб-поиск (сниппеты + цитаты), а не bookable-фиды; через OpenRouter родной grounding ненадёжен/спорен. Цена всегда только из travel-API с датой.
- **Веб-поиск как источник ЦЕНЫ — ЗАПРЕЩЁН (решение пользователя).** Веб-поиск остаётся для прочих времязависимых фактов (часы, расписания, визы, сезонные закрытия, существование локаций), но цену из веб-поиска НЕ берём.
- **Amadeus Self-Service — МЁРТВ.** Портал декоммиссирован 17.07.2026: регистрация новых остановлена весной 2026, ключи деактивированы и перестали отдавать данные. Enterprise не затронут (закрывается только self-service). Как источник НЕ рассматриваем. Статус перекрёстно подтверждён 3 независимыми источниками (PhocusWire, tripgic, ignav; дата и механика совпадают); прямой fetch developers.amadeus.com нашим окружением не прошёл (пустой JS-рендер), но по данным tripgic уведомление сообщается и на самом Amadeus for Developers.

## Нет подключённого API → не выдумывать цену

Если ценовой travel-API не подключён — роль НЕ выдумывает цену и НЕ берёт из веб-поиска, а честно говорит «цену дать не могу / нужен подключённый источник». Базовый бесплатный Travelpayouts Data API снимает это простой токен-настройкой.

## Ценово-временны́е эвристики «когда дешевле»

Провенанс: `issledovanie-deshevye-dni-aviabilety.md` (июль 2026; Google Flights, CheapAir, Aviasales, Hopper, Expedia + академика Hotle et al. 2015). Это знание-подсказка для перебора дат, а НЕ источник цены.

**Жёсткое правило подачи: КАЧЕСТВЕННО, без жёстких процентов.** Точные % (−14 %, −17 %, 42 дня и т. п.) в скилл намеренно НЕ вносятся — в источниках они местами на вторичных пересказах и привязаны к конкретному рынку/маршруту, гарантировать их для произвольного рейса нельзя. Всегда с меткой рынок/год и оговоркой «средние по рынку».

Три фактора (качественно):

1. **День покупки (день недели заказа) — миф, не влияет.** НЕ советовать «покупай во вторник/воскресенье» как способ сэкономить. При вопросе — честно развенчать: день недели заказа на практике не влияет (Google / CheapAir / Aviasales — влияние ≈ ноль, тонет в ежедневных колебаниях).
2. **День вылета — влияет реально.** Воскресенье обычно самый дорогой день вылета; середина недели (вт/ср) обычно дешевле. Подавать как подсказку по ГИБКИМ ДАТАМ, не догму: «если даты гибкие, проверю вт/ср и соседние дни».
3. **Горизонт бронирования — влияет сильнее всего.** «Не в последний момент и не слишком рано»: ориентир ≈ 3 недели – 3 месяца до вылета для внутренних; для праздников/пиков и лета — раньше. Предупреждать: последние ~2–3 недели цены круто растут.

**Эвристика ≠ факт по маршруту.** Роль использует «дни недели / окно» как фильтр-подсказку для перебора: «проверю вт/ср и соседние гибкие даты в travel-API и сравню», а НЕ выдаёт среднерыночную закономерность за цену конкретного рейса. Цена — только из travel-API на конкретные даты (правила — в [verification.md](verification.md)). Формула честной подачи: «Обычно по рынку X (средние, источник/год); давай проверю фактическую цену на твои даты и пару соседних midweek-дней в API».

**US-цифры ≠ РФ.** Для российского пользователя опираться на РФ-данные (Aviasales) и проверку в API, не переносить US-проценты. Всегда маркировать рынок и год.

## Примеры

### Пример 1: «Куда дёшево из Москвы в марте»

**Вход:** запрос ориентировочных дешёвых направлений.

**Результат:** через Travelpayouts Data API (кэш, СНГ-центричен) — «куда дёшево из города» с пометкой «ориентировочно, по кэшу на дату X, актуальную проверить». Для точной цены на конкретные даты — Duffel (рейсы).

### Пример 2: «В какой день покупать билет»

**Вход:** вопрос про день покупки.

**Результат:** развенчать миф — день недели заказа не влияет на цену; предложить вместо этого проверить гибкие даты вылета (середина недели дешевле) в travel-API. Никаких «покупай во вторник» как совета сэкономить, никаких конкретных процентов.
