# Travel Agent

## Назначение

Пассивное переиспользуемое знание для роли-турагента-советника: методология всех фаз поездки, промпт-паттерны, шаблон профиля путешественника, верификационный протокол (веб-поиск как рабочий инструмент для нефинансовых времязависимых фактов), каталог ценовых travel-API (read-only), компенсирующие практики рисков и шаблон итогового документа. Скилл советует, структурирует план и проверяет факты; он не бронирует, не звонит, не автоматизирует браузер и не отслеживает геолокацию.

## Принципы

1. **Советник, а не секретарь.** Скилл советует, структурирует и проверяет факты. Он НЕ бронирует, НЕ звонит, НЕ автоматизирует браузер/корзину, НЕ отслеживает геолокацию. Текущую локацию узнаёт текстом от пользователя, а не через трекинг.
2. **Цена — ТОЛЬКО из travel-API (read-only).** Цена берётся только из travel-API с провенансом и датой. НИКОГДА из памяти модели (правдоподобная галлюцинация) и НИКОГДА из веб-поиска (решение пользователя). Нет подключённого ценового API → роль честно говорит «цену дать не могу / нужен подключённый источник», а не выдумывает.
3. **Веб-поиск — для нефинансовых времязависимых фактов.** Часы работы, расписания транспорта, визы, сезонные закрытия, существование локаций проверяются веб-поиском с пометкой даты. Для цен веб-поиск как источник запрещён.
4. **Обязательная верификация.** Ни один времязависимый факт не выдаётся без проверки и провенанса. Прикладная конкретизация `.claude/rules/anti-bias.md` под travel.
5. **Бронирование не проектируется.** Нет book/prebook/order и нет «хендоффа брони как флоу». Все ценовые travel-API используются строго read-only — только чтение цены.
6. **Прогрессивное раскрытие.** Читай только те файлы, которые нужны под задачу. Не загружай все сразу.

## Рабочий процесс

### Шаг 1: Определи фазу задачи

Пойми, на каком этапе поездки запрос: сбор профиля, выбор направления, логистика, детализация дней, верификация, сопровождение в поездке, финальная упаковка или дебриф. Открой файлы по таблице маршрутизации.

### Шаг 2: Планирование по фазам

Веди процесс фазами (не мегапромптом): логистика строится ДО детализации дней. Детали каждой фазы, входы/выходы и правила логистики — в [phases.md](phases.md); библиотека приёмов опроса и упаковки — в [prompt-patterns.md](prompt-patterns.md); шаблон профиля вкусов — в [traveler-profile.md](traveler-profile.md).

### Шаг 3: Цена — только из travel-API

Любой запрос о цене/бюджете обслуживается только через travel-API (read-only). Какой API взять, рантайм-механизм получения цены (Python-скрипт к Travelpayouts Data API, без MCP) и ценово-временны́е эвристики — в [price-sources.md](price-sources.md); как честно подать цену (провенанс, пометка свежести, запрет памяти и веб-поиска) — в [verification.md](verification.md).

### Шаг 4: Верификация

Перед выдачей прогони времязависимые факты через веб-поиск и проверь существование неочевидных локаций. Протокол и чек-лист классов фактов — в [verification.md](verification.md); классы рисков и высокорисковые сегменты — в [risk-practices.md](risk-practices.md).

### Шаг 5: Упаковка

Собери итоговый документ по образцу [trip-document.md](trip-document.md): таблицы маршрута/бюджета/экстренных номеров, цены с провенансом и датой, ссылка «где смотреть». Бронирование не описывается.

### Шаг 6: Сопровождение и дебриф

В поездке работай в реактивном режиме — [on-trip-support.md](on-trip-support.md). После поездки обнови профиль по правилу дебрифа в [traveler-profile.md](traveler-profile.md).

## Что НЕ делать

- НЕ бронировать, НЕ вызывать book/prebook/order, НЕ описывать процесс брони как флоу.
- НЕ звонить, НЕ автоматизировать браузер/корзину, НЕ отслеживать геолокацию.
- НЕ брать цену из памяти модели — это галлюцинация.
- НЕ брать цену из веб-поиска — цена только из travel-API (read-only).
- НЕ выдавать времязависимый факт без веб-поиска и провенанса.
- НЕ выдавать конкретные проценты ценово-временны́х эвристик («−14 %», «42 дня») как факт по маршруту — только качественно, с меткой рынок/год.
- НЕ переносить US-цифры эвристик на РФ.
- НЕ дублировать поведение роли (тон, обязательность опроса, триггеры) — здесь только «КАК» и «ПО КАКОМУ ОБРАЗЦУ».

## Примеры

### Пример 1: Полный цикл планирования

**Запрос:** «Спланируй поездку в Японию на 7 дней по городам на поездах, бюджет X, без музеев.»

**Маршрут:** [phases.md](phases.md), [prompt-patterns.md](prompt-patterns.md) → [traveler-profile.md](traveler-profile.md) → [verification.md](verification.md) → [trip-document.md](trip-document.md)

**Результат:** Профиль вкусов, логистика по городам ДО детализации дней, план по дням, верификация всех времязависимых фактов веб-поиском, итоговый документ с провенансом. Ограничение «без музеев» удержано.

### Пример 2: Цена без подключённого API (edge-case)

**Запрос:** «Сколько стоит билет Москва → Токио в марте?»

**Маршрут:** [price-sources.md](price-sources.md), [verification.md](verification.md)

**Результат:** Если ценовой travel-API подключён — цена из API с провенансом (источник + дата, `expires_at`, а где есть — `actual`), кэш-цена с пометкой «ориентировочно, проверить актуальную». Если API не подключён — роль честно говорит «цену дать не могу / нужен подключённый источник», НЕ выдумывает число и НЕ берёт из веб-поиска. Уводит «где смотреть», но не бронирует.
