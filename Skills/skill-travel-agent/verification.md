# Верификационный протокол

## Назначение

Обязательный протокол проверки времязависимых фактов поездки: веб-поиск как рабочий инструмент для нефинансовых фактов, чек-лист классов, проверка существования локаций и правила честной подачи цены. Прикладная конкретизация `.claude/rules/anti-bias.md` под travel. Грузится в фазе верификации и при запросе «проверь план».

## Веб-поиск как обязательный рабочий инструмент (нефинансовые факты)

Времязависимые НЕфинансовые факты НЕ выдаются «по памяти» — они проверяются веб-поиском с пометкой даты источника. Это рабочий инструмент советника, а не опция.

- ВСЕГДА искать в вебе перед выдачей времязависимого факта, а не предполагать.
- ВСЕГДА указывать дату/источник у проверенного факта.
- Для цен веб-поиск как источник — ЗАПРЕЩЁН (см. «Правила честной подачи цены»).

## Чек-лист классов времязависимых фактов

Проверять веб-поиском:

- **Часы работы** — музеи, рестораны, магазины, достопримечательности; дни закрытия (часто вт/ср).
- **Расписания транспорта** — поезда, автобусы, паромы, метро; частота и последний рейс.
- **Визы и въезд** — визовые требования, сроки, документы, ограничения на въезд.
- **Сезонные закрытия** — перевалы, маршруты, объекты, закрытые вне сезона.
- **Прочие быстро устаревающие факты** — ремонты, временные закрытия, изменения маршрутов.

## Проверка существования локаций (защита от «каньона Умантай»)

Неочевидные/малоизвестные локации проверять на само существование, а не только на часы. ИИ может уверенно назвать несуществующее место — проверять существование локации отдельным веб-поиском перед включением в план.

## Вопрос самоаудита

Перед выдачей задавать: **«Что я, скорее всего, получу неправильно?»** — вывести на поверхность факты, которые устаревают быстрее всего или сомнительны. Связано с приёмом самоаудита в [prompt-patterns.md](prompt-patterns.md) и классами рисков в [risk-practices.md](risk-practices.md).

## Правила честной подачи цены

Три обязательных правила, применимые к ЛЮБОЙ цене независимо от конкретного travel-API. Какой API взять — в [price-sources.md](price-sources.md).

1. **Цена — ТОЛЬКО из travel-API (read-only). Память и веб-поиск как источник цены — запрещены.**
   - Цена «со слов модели» (в т. ч. Gemini через OpenRouter) — правдоподобная галлюцинация. У модели нет доступа к инвентарю Google Flights/Hotels; grounding = веб-поиск, а не bookable-фиды. Не бери цену из памяти.
   - Цена из веб-поиска — запрещена (решение пользователя). Веб-поиск — только для нефинансовых фактов.
2. **Кэш-цена подаётся только с пометкой свежести.** Кэш-цена (Travelpayouts Data API) показывается в форме «ориентировочно, по кэшу на дату X (`expires_at` / время выборки), актуальную проверить». Фильтровать по не-`expired` (`expires_at` в будущем); у v1 `/v1/prices/cheap` поля `actual` нет — свежесть только по `expires_at`. У v3 `/aviasales/v3/prices_for_dates` поля `expires_at` нет вовсе — свежесть определяется по `search_date=DDMMYYYY` из строки `link` (дата снимка кэша); верифицируемость свежести слабее, чем у v1, поэтому цену подавать с явной оговоркой «снимок от …, актуальную проверить». Живые цены Duffel/LiteAPI подаются как актуальные на момент снимка, тоже с датой.
3. **Провенанс каждой цены обязателен.** Любая цена в выдаче/документе — со ссылкой на источник (travel-API) и датой снимка. Без провенанса цена не показывается. Стыкуется с обязательным провенансом цен в [trip-document.md](trip-document.md).

**Fallback:** нет подключённого ценового API → роль не выдумывает цену и не берёт из веб-поиска, а честно говорит «цену дать не могу / нужен подключённый источник».

## Стык: ценово-временна́я эвристика ≠ цена

«Дни недели / окно бронирования» — это фильтр-подсказка для перебора дат, а НЕ источник цены. Конкретная цена по-прежнему берётся только из travel-API на конкретные даты. Детали эвристики — в [price-sources.md](price-sources.md).

## Фильтр применимости — ДО сравнения цен

Есть класс ценовых предложений, дешёвых не потому что выгоднее, а потому что пассажир по ним физически/юридически не пролетит. Отсеивать их по применимости ДО сравнения цен, а не после.

Пример (времязависимый — проверять веб-поиском с датой): безвизовый airside-транзит через Шенген для гражданина РФ держится на трёх условиях сразу — единый билет, один и тот же аэропорт, маршрут не-Шенген→Шенген→не-Шенген. У лоукостеров билеты раздельные → условие единого билета не выполняется, такие стыковки отпадают. Маршрут стыковки API не раскрывает — принадлежность варианта проверять косвенно, по перевозчику.

## Примеры

### Пример 1: Часы музея

**Вход:** музей стоит в плане на вторник.

**Результат:** веб-поиск дня закрытия и часов; если вторник — выходной, переставить; факт в документе — со ссылкой и датой.

### Пример 2: Запрос цены без API

**Вход:** «Сколько стоит перелёт?» — ценовой API не подключён.

**Результат:** «Цену дать не могу — нужен подключённый ценовой источник (travel-API)». НЕ называть число из памяти, НЕ искать цену в вебе.
