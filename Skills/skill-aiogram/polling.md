# Запуск и остановка long polling

## Назначение

Как запустить приём обновлений через long polling, какие параметры у запуска, как выбираются типы обновлений, как обрабатываются и пропускаются накопившиеся обновления, как polling останавливается и что делает при сбоях. Устройство роутеров — в [dispatching.md](dispatching.md).

## Методы запуска

- `await dp.start_polling(*bots, ...)` — корутина.
- `dp.run_polling(*bots, ...)` — синхронная обёртка над ней: запускает через `asyncio.run`, а если импортируется `uvloop` — через `asyncio.Runner` с фабрикой цикла событий uvloop; `KeyboardInterrupt` подавляется.
- Оба метода возвращают `None`, принимают одинаковые параметры, боты передаются позиционно.

| Параметр | Значение по умолчанию | Что задаёт |
|---|---|---|
| `polling_timeout` | `10` | время ожидания ответа `getUpdates`, секунды |
| `handle_as_tasks` | `True` | каждое обновление обрабатывается в своей задаче asyncio |
| `backoff_config` | `BackoffConfig(min_delay=1.0, max_delay=5.0, factor=1.3, jitter=0.1)` | паузы между повторами после сбоя `getUpdates` |
| `allowed_updates` | `UNSET` (служебное значение) | какие типы обновлений запрашивать |
| `handle_signals` | `True` | установка обработчиков SIGINT и SIGTERM |
| `close_bot_session` | `True` | закрывать сессии ботов при остановке |
| `tasks_concurrency_limit` | `None` | предел одновременно обрабатываемых обновлений (с 3.20.0) |
| `tasks_shutdown_timeout` | `None` | сколько секунд ждать выполняющиеся обработчики при остановке (с 3.32.0) |
| `**kwargs` | — | данные для обработчиков (см. [handler-data.md](handler-data.md)) |

Условия и ограничения:

- нужен хотя бы один бот, иначе `ValueError`
- аргумент `bot=` в виде именованного — `ValueError`; боты передаются позиционно
- на один токен допускается один процесс polling, иначе Telegram возвращает ошибку
- второй одновременный `start_polling` на том же диспетчере ждёт освобождения блокировки

## Выбор типов обновлений

- Если `allowed_updates` не передан, aiogram запрашивает только те типы обновлений, для которых во всём дереве роутеров есть хотя бы один обработчик. Список считает `router.resolve_used_update_types(skip_events=None)`.
- `resolve_used_update_types` возвращает отсортированный список имён событий с хотя бы одним обработчиком в роутере и во всех вложенных; `skip_events` — множество имён, которые нужно пропустить; `update` и `error` пропускаются всегда.
- Явно переданный список используется как есть. `allowed_updates=None` не передают: параметр либо не задают, либо передают список.
- Обработчики, зарегистрированные после запуска polling, уже запрошенный список не меняют.

## Накопившиеся обновления

- В методах polling нет аргумента пропуска накопившихся обновлений.
- Чтобы пропустить их, до запуска вызывается метод бота `delete_webhook` с аргументом `drop_pending_updates=True`: он сбрасывает все ожидающие обновления и заодно снимает webhook.

## Параллельная обработка

- `handle_as_tasks=True`: обновления обрабатываются одновременно, каждое в своей задаче, без ожидания результата. Telegram получает подтверждение обновления со следующим `getUpdates`, обычно до окончания обработчика.
- `handle_as_tasks=False`: обновление обрабатывается внутри цикла polling по одному. При остановке выполняющийся обработчик отменяется, его обновление не подтверждено, и после следующего запуска Telegram пришлёт его снова.
- `tasks_concurrency_limit` работает только с `handle_as_tasks=True`: при достижении предела чтение новых обновлений приостанавливается. Предел действует на каждого бота отдельно, а не общий.
- При `handle_as_tasks=True` два обновления одного пользователя могут обрабатываться одновременно и читать одно и то же состояние FSM. Чтобы обновления с одним ключом состояния шли по очереди, включают изоляцию событий: раздел «Изоляция событий» в [fsm.md](fsm.md).

## Остановка

- С `handle_signals=True` SIGINT и SIGTERM останавливают polling корректно. В Windows цикл событий не поддерживает обработчики сигналов, их там нет — используется `await dp.stop_polling()`. Без поддерживаемого цикла SIGINT вызывает `KeyboardInterrupt` или отмену задачи, и остановка идёт без ожидания. Второй сигнал во время ожидания только пишется в журнал.
- `await dp.stop_polling()` можно вызвать из другой корутины, пока polling работает; если polling не запущен, будет `RuntimeError`. После него диспетчер выполняет наблюдатели `shutdown` и закрывает сессии ботов, если не задано `close_bot_session=False`.
- Порядок остановки: перестать получать обновления; ждать выполняющиеся задачи обновлений до `tasks_shutdown_timeout` секунд (`None` — не ждать); отменить оставшиеся, дождаться отмены и записать предупреждение с их числом; выполнить наблюдатели `shutdown`; закрыть сессии всех ботов.
- По умолчанию выполняющиеся обработчики не ждут, а остаток отменяется, когда `run_polling` закрывает цикл событий. Ожидаются только задачи, запущенные самим polling, но не задачи, запущенные внутри обработчиков.
- Таймаут держат короче промежутка между SIGTERM и SIGKILL у менеджера процессов. Он не гарантирует однократную обработку: обработчикам с побочными эффектами нужно записывать прогресс.
- При `handle_as_tasks=False` `tasks_shutdown_timeout` ничего не меняет.
- Обработчик, который ждёт `stop_polling()`, обычно не ждут при остановке. Его ждут и затем отменяют, если polling уже останавливается или вызов завёрнут в `asyncio.shield()`, `asyncio.gather()` либо (в Python 3.11) `asyncio.wait_for()`. Поэтому `stop_polling()` запускают отдельной задачей, хранят ссылку на неё и возвращаются из обработчика, не ожидая её.

## Несколько ботов в одном Dispatcher

- Боты передаются позиционно: `await dp.start_polling(bot1, bot2)` (или `run_polling`).
- Для каждого бота работает своя задача polling, все параллельно. Как только любая из них завершилась (или пришёл сигнал остановки), polling заканчивается для всех.
- Наблюдатели `startup` и `shutdown` выполняются один раз и получают `bot` — последний бот — и `bots` — полный список.
- Предел `tasks_concurrency_limit` действует на каждого бота отдельно.
- Обработчик получает `bot` того бота, чьё обновление обрабатывается.

## Повторы при сбоях

- Любое исключение при `getUpdates` обрабатывается одним общим обработчиком, особых веток для `TelegramConflictError` и `TelegramNetworkError` нет, и для `TelegramRetryAfter` тоже: значение `retry_after` цикл не использует.
- При сбое цикл пишет в журнал ошибку с типом и сообщением исключения, затем предупреждение со следующей задержкой, номером повтора и идентификатором бота, ждёт и повторяет запрос. Первый удачный запрос после сбоя пишет в журнал, что соединение восстановлено, и сбрасывает задержку.
- Конфликт 409 (другой экземпляр бота с тем же токеном) повторяется так же, как сетевая ошибка.
- `BackoffConfig` (`from aiogram.utils.backoff import BackoffConfig`) — неизменяемый класс данных с полями `min_delay`, `max_delay`, `factor`, `jitter` (все числа с плавающей точкой), своих значений по умолчанию у него нет. Требуются `max_delay > min_delay` и `factor > 1`, иначе `ValueError`. Polling по умолчанию использует `BackoffConfig(min_delay=1.0, max_delay=5.0, factor=1.3, jitter=0.1)`.
- Задержка начинается с `min_delay`, на каждой неудачной попытке умножается на `factor` до `max_delay`; `jitter` — стандартное отклонение нормального случайного разброса вокруг каждого значения.
- Свои значения: `start_polling(bot, backoff_config=BackoffConfig(...))`.
- Ошибка flood control при отправке сообщения из обработчика — это ошибка вызова метода, а не polling: см. [errors.md](errors.md).

## Примеры

### Пример 1: Запуск с пропуском накопившихся обновлений

**Вход:** после простоя бот не должен отвечать на старые сообщения.

**Результат:**

```python
async def main() -> None:
    dp = Dispatcher()
    dp.include_router(router)
    bot = Bot(token=os.environ["BOT_TOKEN"])
    await bot.delete_webhook(drop_pending_updates=True)
    await dp.start_polling(bot)
```

### Пример 2: Остановка polling командой из чата

**Вход:** команда `/stop` останавливает бота.

**Результат:**

```python
background_tasks: set[asyncio.Task] = set()


@router.message(Command("stop"))
async def cmd_stop(message: Message, dispatcher: Dispatcher) -> None:
    await message.answer(text="Stopping.")
    task = asyncio.create_task(dispatcher.stop_polling())
    background_tasks.add(task)
    task.add_done_callback(background_tasks.discard)
```

Остановка запущена отдельной задачей, ссылка на неё хранится, обработчик возвращается, не дожидаясь её.
