# FSM: состояния и данные диалога

## Назначение

Конечный автомат aiogram для диалога из нескольких шагов: объявление состояний, методы `FSMContext`, фильтрация обработчиков по состоянию, хранилище в памяти, стратегии ключа состояния, изоляция событий с одним ключом и работа с состоянием другого пользователя или чата. Сцены — в [scenes.md](scenes.md).

## Объявление состояний

- Группа состояний — класс-наследник `StatesGroup`, каждый шаг — атрибут класса со значением `State()`: группа `Form` с атрибутами `name`, `like_bots`, `language`, у каждого `= State()`.
- Строка состояния — `группа:атрибут`, то есть `Form.name` имеет строку `"Form:name"`. Если у `State()` нет явного имени, именем становится имя атрибута.
- У вложенной группы часть «группа» — полное имя через точку: `"Parent.Child"`.
- `State(state=None, group_name=None)`: оба параметра необязательны; `group_name` перекрывает префикс группы. У `State` вне группы префикс `"@"`.
- Два особых состояния: `default_state = State()` со строковым значением `None` (состояние не задано) и `any_state = State(state="*")` со значением `"*"`.
- Группа поддерживает проверку `in` по строкам состояний и объектам `State` и перебор всех состояний, включая вложенные группы.
- `State.group` бросает `RuntimeError`, если состояние не входит в группу.

## FSMContext

`FSMContext(storage, key)` привязан к одному ключу хранилища и хранит атрибуты `storage` и `key`. Обработчик получает его в аргументе `state`. Все методы — корутины, нужен `await`.

| Метод | Параметры | Возвращает | Что делает |
|---|---|---|---|
| `set_state` | `state: str \| State \| None = None` | `None` | задаёт состояние; `None` снимает его |
| `get_state` | нет | `str \| None` | текущая строка состояния или `None` |
| `set_data` | `data: Mapping[str, Any]` | `None` | заменяет все сохранённые данные |
| `get_data` | нет | `dict[str, Any]` | все сохранённые данные |
| `get_value` | `key: str`, `default: Any = None` | `Any` | одно значение или `default`, если ключа нет |
| `update_data` | `data: Mapping[str, Any] \| None = None`, `**kwargs` | `dict[str, Any]` | сливает словарь и именованные аргументы в данные и возвращает обновлённые данные |
| `clear` | нет | `None` | снимает состояние и заменяет данные пустым словарём |

- Если один ключ есть и в `data`, и в `kwargs` метода `update_data`, побеждает значение из `data`.
- `get_value` появился в 3.14.0.

## Фильтрация по состоянию

- Состояние как фильтр: `@router.message(Form.name)`. `State` сам по себе фильтр: он подходит, когда текущая строка состояния равна его строке. Сочетается с другими фильтрами, например `F.text.casefold() == "yes"`.
- Группу целиком можно передать как фильтр (класс или экземпляр): она подходит, когда текущее состояние — любое из группы, включая вложенные.
- `StateFilter(*states)` принимает одно и более значений: `State`, класс или экземпляр `StatesGroup`, строка, `None`. Без аргументов — `ValueError`. Подходит, когда подошло любое из перечисленных.
- Любое состояние: `"*"` или `any_state`; подходит всегда, когда обработчик достигнут, включая случай без состояния.
- Нет состояния: `None` или `default_state`; `StateFilter(None)` подходит только когда состояние не задано.
- Обработчик без фильтра состояния подходит в любом состоянии, включая отсутствие состояния. Чтобы обработчик срабатывал только без состояния, пишется `StateFilter(None)`.
- Порядок проверки обработчиков — как в [dispatching.md](dispatching.md): обработчик общей команды отмены, который должен работать в любом состоянии, регистрируется раньше обработчиков шагов.

## Хранилище

- Если `storage` не передан (по умолчанию `None`), `Dispatcher` использует `MemoryStorage` — встроенное хранилище в памяти.
- `MemoryStorage()` не принимает параметров. Состояние и данные лежат в словаре Python, по одной записи на ключ хранилища; запись — строка состояния и словарь данных.
- Чтение и запись данных копируют сохранённый словарь на один уровень (поверхностная копия): вложенные изменяемые объекты общие с хранилищем. `set_data` с не-словарём бросает ошибку.
- Данные не сохраняются между запусками: при перезапуске бота всё теряется. Для выкладки хранилище не рекомендуется.
- Передача хранилища: именованный параметр `storage` конструктора, `Dispatcher(storage=MemoryStorage())`. Рядом в конструкторе `fsm_strategy`, `events_isolation` (раздел «Изоляция событий»), `disable_fsm` (по умолчанию `False`; при `True` middleware FSM не регистрируется) и `fsm_key_on_sender_chat`.
- При `disable_fsm=True` хранилище и изоляцию событий задавать нельзя.

## Стратегии

Стратегия задаётся параметром `fsm_strategy` диспетчера: `Dispatcher(fsm_strategy=FSMStrategy.CHAT)`; по умолчанию `FSMStrategy.USER_IN_CHAT`.

| Значение | Ключ состояния |
|---|---|
| `USER_IN_CHAT` | чат и пользователь: у каждого пользователя своё состояние в каждом чате (по умолчанию) |
| `CHAT` | только чат: у всех пользователей чата общее состояние |
| `GLOBAL_USER` | только пользователь: одно состояние на пользователя во всех чатах |
| `USER_IN_TOPIC` | чат, пользователь и тема |
| `CHAT_TOPIC` | чат и тема: у всех пользователей темы общее состояние |

- `CHAT` и `CHAT_TOPIC` подставляют вместо идентификатора пользователя идентификатор чата; `GLOBAL_USER` подставляет идентификатор пользователя в оба поля; `CHAT` и `GLOBAL_USER` идентификатор темы не учитывают.
- Сообщения анонимных администраторов групп и пользователей, пишущих от имени канала, несут заменяющего пользователя, поэтому по умолчанию у них общее состояние. `Dispatcher(fsm_key_on_sender_chat=True)` использует для них идентификатор чата-отправителя как идентификатор пользователя в чатах, не являющихся каналами.
- Версии появления: `USER_IN_TOPIC` — 3.0.0b8 (предварительный выпуск 3.0.0), `CHAT_TOPIC` — 3.2.0, `fsm_key_on_sender_chat` — 3.32.0.

## Изоляция событий

Изоляция событий — блокировка по ключу хранилища FSM на время обработки обновления: два обновления с одним ключом не обрабатываются одновременно. Здесь описана изоляция внутри одного процесса; изоляция между процессами через внешнее хранилище вне охвата скилла.

| Класс | Импорт | Параметры конструктора | Что делает |
|---|---|---|---|
| `DisabledEventIsolation` | `from aiogram.fsm.storage.memory import DisabledEventIsolation` | нет | блокировку не берёт, изоляции нет; используется, когда `events_isolation` не задан |
| `SimpleEventIsolation` | `from aiogram.fsm.storage.memory import SimpleEventIsolation` | нет | держит по одному `asyncio.Lock` на каждый ключ хранилища, пока обрабатывается обновление с этим ключом |

- Подключение: `Dispatcher(events_isolation=SimpleEventIsolation())`. Тип параметра — `BaseEventIsolation | None`; значение по умолчанию `None` означает `DisabledEventIsolation`.
- Своя изоляция — подкласс `BaseEventIsolation` (модуль `aiogram.fsm.storage.base`) с асинхронным контекстным менеджером `lock(key: StorageKey)` и асинхронным методом `close()`.

### Ключ блокировки

- Блокируется `StorageKey` контекста FSM обновления: бот, чат, пользователь, тема, деловое подключение, `destiny` и признак гостя (поля — в разделе «Состояние другого пользователя или чата»).
- Какие идентификаторы чата и пользователя попадают в ключ, решают стратегия FSM и `fsm_key_on_sender_chat` (раздел «Стратегии»). Обновления ждут друг друга, только когда их ключи совпадают целиком.

### Когда блокировка берётся и снимается

1. Блокировку берёт `FSMContextMiddleware` — внешний middleware наблюдателя `update`, зарегистрированный третьим, после `ErrorsMiddleware` и `UserContextMiddleware`. При `disable_fsm=True` его нет, а с ним нет и изоляции.
2. Middleware определяет контекст FSM по чату и пользователю события и кладёт в данные `fsm_storage`.
3. Если контекст определился, берётся блокировка его ключа. Под блокировкой в данные кладутся `state` и `raw_state` — состояние читается уже после взятия блокировки — и вызывается дальнейшая обработка.
4. Блокировка снимается, когда обработка вернулась или бросила исключение.
5. Если контекст не определился (в событии нет нужных идентификаторов), обработка идёт без блокировки и без чтения состояния.

- `ErrorsMiddleware` и `UserContextMiddleware` выполняются вне блокировки.
- Middleware наблюдателей, фильтры и обработчик выполняются под блокировкой.

### Второе обновление с тем же ключом

- С `SimpleEventIsolation` второе обновление ждёт, пока первое не снимет блокировку. Оно не теряется и не отклоняется, а состояние читает после ожидания, поэтому видит то, что записало первое. Обновления с разными ключами обрабатываются параллельно.
- С `DisabledEventIsolation` (по умолчанию) второе обновление не ждёт: оба обрабатываются параллельно и могут прочитать одно и то же состояние.

### Связь с polling

- Одновременная обработка обновлений возникает при `handle_as_tasks=True` (по умолчанию): каждое обновление обрабатывается в своей задаче ([polling.md](polling.md)). При `handle_as_tasks=False` обновления обрабатываются по одному, и изоляции нечего упорядочивать.
- Задача, которая ждёт блокировку, занимает место в пределе `tasks_concurrency_limit`.

### Пределы

- Блокировки живут в памяти одного процесса и не изолируют обновления между процессами.
- Словарь блокировок `SimpleEventIsolation` пополняется записью на каждый новый ключ и очищается только в `close()`, поэтому на долгой работе бота растёт с числом пользователей и чатов.
- Долгий обработчик под `SimpleEventIsolation` задерживает все следующие обновления с тем же ключом на всё время своей работы.
- Метод `close()` middleware FSM закрывает и хранилище, и изоляцию.

## Состояние другого пользователя или чата

- Основной способ: `dispatcher.fsm.get_context(bot=bot, chat_id=..., user_id=...)` возвращает `FSMContext` для этой цели; на нём вызывают `set_state`, `update_data`, `clear` и остальные методы. В личном чате идентификатор пользователя передаётся и как `chat_id`, и как `user_id`.
- Сигнатура: `get_context(bot, chat_id, user_id, thread_id=None, business_connection_id=None, destiny="default", is_guest=False)`. Метод возвращает новый `FSMContext` над хранилищем диспетчера и `StorageKey`, собранный из этих значений и `bot.id`.
- `get_context` стратегию FSM не применяет: переданные идентификаторы используются как есть. При стратегии не по умолчанию вызывающий сам передаёт идентификаторы, которые дала бы стратегия (для `GLOBAL_USER` — идентификатор пользователя в обоих полях).
- Ручная сборка: `FSMContext(storage=dispatcher.storage, key=StorageKey(bot_id=..., chat_id=..., user_id=...))`. `StorageKey` — неизменяемый класс данных с полями `bot_id`, `chat_id`, `user_id` (обязательные), `thread_id=None`, `business_connection_id=None`, `destiny="default"`, `is_guest=False`.
- Хранилище должно быть тем, что использует диспетчер: контекст над другим объектом хранилища тех же данных не увидит.

## Примеры

### Пример 1: Анкета из двух шагов с отменой

**Вход:** `/form` спрашивает имя, затем возраст; `/cancel` прерывает анкету в любом шаге.

**Результат:**

```python
class Form(StatesGroup):
    name = State()
    age = State()


@router.message(Command("cancel"), StateFilter("*"))
async def cmd_cancel(message: Message, state: FSMContext) -> None:
    await state.clear()
    await message.answer(text="Cancelled.")


@router.message(Command("form"))
async def cmd_form(message: Message, state: FSMContext) -> None:
    await state.set_state(Form.name)
    await message.answer(text="What is your name?")


@router.message(Form.name, F.text)
async def got_name(message: Message, state: FSMContext) -> None:
    await state.update_data(name=message.text)
    await state.set_state(Form.age)
    await message.answer(text="How old are you?")


@router.message(Form.age, F.text)
async def got_age(message: Message, state: FSMContext) -> None:
    data = await state.get_data()
    await state.clear()
    await message.answer(text=f"{data['name']}, {message.text}")
```

Обработчик отмены зарегистрирован первым: обработчики проверяются в порядке регистрации, и иначе `/cancel` попал бы в `got_name` как ответ на вопрос.

### Пример 2: Сменить состояние другого пользователя

**Вход:** по команде администратора сбросить анкету пользователя с известным идентификатором (личный чат).

**Результат:**

```python
@router.message(Command("reset"))
async def cmd_reset(message: Message, dispatcher: Dispatcher, bot: Bot) -> None:
    target = dispatcher.fsm.get_context(bot=bot, chat_id=123456, user_id=123456)
    await target.clear()
```

### Пример 3: Обновления одного пользователя по очереди

**Вход:** пользователь быстро шлёт несколько сообщений подряд, и обработчики шага анкеты не должны читать и писать его состояние одновременно.

**Результат:**

```python
from aiogram.fsm.storage.memory import SimpleEventIsolation

dp = Dispatcher(events_isolation=SimpleEventIsolation())
```

При стратегии по умолчанию `USER_IN_CHAT` обновления одного пользователя в одном чате обрабатываются по очереди, и каждое следующее читает состояние, записанное предыдущим; обновления других пользователей идут параллельно. Блокировка действует только внутри одного процесса бота.
