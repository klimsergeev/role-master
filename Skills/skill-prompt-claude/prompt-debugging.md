# Отладка промпта на тестах

## Назначение

Процедура проверки и сравнения вариантов промпта на наборе тестов по официальной методике Anthropic: критерии успеха, набор задач, оценщики, прогоны, чтение транскриптов, решение.

This cycle is central to prompt engineering» (успешное приложение на LLM начинается с чётких критериев успеха и оценок, которые их измеряют; этот цикл — основа промпт-инжиниринга).

## Шаг 1. Записать критерии успеха

Develop tests: хорошие критерии — конкретные, измеримые, достижимые и релевантные.

| Свойство | Что значит | Пример из источника |
|---|---|---|
| Конкретный | Ясно, чего добиться | «accurate sentiment classification» вместо «good performance» |
| Измеримый | Количественная метрика или чётко определённая качественная шкала | «Less than 0.1% of outputs out of 10,000 trials flagged for toxicity by the content filter» вместо «Safe outputs» |
| Достижимый | Опирается на бенчмарки, прошлые эксперименты, исследования, экспертное знание | — |
| Релевантный | Связан с назначением приложения и нуждами пользователей | Точность цитирования критична для медицины, меньше — для лёгкого чат-бота |

Типовые измерения (develop tests, перечень неполный): точность выполнения задачи, согласованность ответов на похожие входы, релевантность и связность, тон и стиль, сохранение приватности, использование контекста, задержка, цена. Большинству задач нужно несколько измерений сразу.

## Шаг 2. Собрать набор задач

- Объём старта. Demystifying evals: «In reality, 20-50 simple tasks drawn from real failures is a great start» (20–50 простых задач из реальных сбоев — хорошее начало). Develop tests: «Prioritize volume over quality» (больше вопросов с автоматической оценкой лучше нескольких с ручной).
- Откуда брать. Demystifying evals: начать с ручных проверок, которые уже делаются; трекер ошибок и очередь поддержки; сбои, о которых сообщили пользователи.
- Граничные случаи. Develop tests: нерелевантные или отсутствующие входные данные; слишком длинный вход; для чатов — плохой, вредный или нерелевантный ввод; неоднозначные случаи, где и люди не сошлись бы.
- Баланс. Demystifying evals: проверять и случаи, где поведение должно произойти, и где не должно; однобокий набор даёт однобокую оптимизацию (пример источника: проверяли только, ищет ли модель, когда должна, — получили модель, которая ищет почти всё).
- Однозначность. Demystifying evals: «A good task is one where two domain experts would independently reach the same pass/fail verdict» (хорошая задача — та, где два эксперта независимо дадут один вердикт). Всё, что проверяет оценщик, должно быть ясно из условия задачи.
- Эталон. Demystifying evals: для каждой задачи — эталонное решение, проходящее все оценщики; оно доказывает, что задача решаема, а оценщики настроены верно.

## Шаг 3. Выбрать оценщиков

| Тип | Методы | Сильные стороны | Слабые стороны |
|---|---|---|---|
| Код | Точное и шаблонное совпадение, бинарные тесты, статический анализ, проверка итогового состояния, проверка вызовов инструментов, анализ транскрипта | Быстро, дёшево, объективно, воспроизводимо | Ломается на допустимых вариациях, мало нюансов |
| Модель | Оценка по рубрике, утверждения на естественном языке, попарное сравнение, сравнение с эталоном, согласие нескольких судей | Гибко, масштабируется, ловит нюансы, годится для открытых задач | Недетерминированно, дороже кода, требует калибровки по людям |
| Человек | Экспертная оценка, выборочная проверка, A/B, согласие разметчиков | Эталонное качество, служит калибровкой для модели-оценщика | Дорого, медленно |

Таблица — по Demystifying evals. Там же: оценивать то, что агент сделал, а не путь; для задач из нескольких частей — частичный зачёт; оценщики защищены от обходов.

Расхождение официальных источников о порядке выбора:

- Develop tests, раздел Grade your evaluations: «choose the fastest, most reliable, most scalable method» — код; затем «Human grading: Most flexible and high quality, but slow and expensive. Avoid if possible» (ручная оценка — самая гибкая и качественная, но медленная и дорогая; по возможности избегать); затем оценка моделью — «Test to ensure reliability first, then scale» (сначала проверить надёжность, потом масштабировать).
- Demystifying evals: «We recommend choosing deterministic graders where possible, LLM graders where necessary or for additional flexibility, and using human graders judiciously for additional validation» (детерминированные оценщики — где можно, модельные — где нужно, человеческие — взвешенно, для дополнительной проверки); модельных судей «should be closely calibrated with human experts» (тщательно калибровать по экспертам).

## Шаг 4. Настроить оценщика-модель

- Develop tests: подробные ясные рубрики («The answer should always mention 'Acme Inc.' in the first sentence. If it does not, the answer is automatically graded as 'incorrect.'»); одному критерию может понадобиться несколько рубрик.
- Develop tests: дискретный выход — только «correct» или «incorrect», или шкала 1–5.
- Develop tests: оценщик с включённым мышлением, чтобы он рассуждал до оценки.
- Develop tests, комментарий в примерах кода: «Generally best practice to evaluate with a different model from the one used to generate the evaluated output» (обычно лучше оценивать другой моделью, чем та, что сгенерировала ответ).
- Demystifying evals: дать судье выход — например, отвечать «Unknown», если сведений не хватает; каждое измерение задачи — отдельным изолированным судьёй, а не одним на все.

## Шаг 5. Прогнать варианты

- Каждый прогон — с чистого окружения; общее состояние между прогонами (оставшиеся файлы, кэш, история git) искажает результат (Demystifying evals).
- Несколько прогонов на задачу: ответы модели различаются между запусками.
- Метрики (Demystifying evals): pass@k — вероятность хотя бы одного верного решения за k попыток; pass^k — вероятность, что верны все k. При трёх прогонах и успехе 75 процентов на прогон pass^3 ≈ 42 процента. pass^k важнее там, где пользователь ждёт надёжного поведения каждый раз.
- Сравнение вариантов промпта — на одном наборе задач и одних оценщиках. Гайд Sonnet 5 (https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/prompting-claude-sonnet-5): «Iterate on prompts against a subset of your evals or test cases to validate recall or F1 score gains» (итерируй промпты на подмножестве своих тестов, подтверждая прирост полноты или F1). Отдельной официальной методики попарного сравнения текстов промптов на текущих страницах не найдено.

## Шаг 6. Прочитать транскрипты

Demystifying evals: «You won't know if your graders are working well unless you read the transcripts and grades from many trials» (не узнаешь, работают ли оценщики, пока не прочитаешь транскрипты и оценки многих прогонов).

- Провал должен выглядеть честным: ясно, что агент сделал не так. ЕСЛИ оценщик отверг допустимое решение → чинить оценщика, а не промпт.
- ЕСЛИ задача проваливается во всех прогонах → сначала проверить условие и оценщика: Demystifying evals — 0 процентов на многих прогонах чаще означает сломанную задачу, а не неспособную модель.
- Оценкам не верить на слово, пока кто-то не разобрал детали и не прочитал транскрипты (Demystifying evals).

## Шаг 7. Принять решение и поддерживать набор

- Вариант принимается, если он проходит критерии шага 1 на наборе шага 2, а транскрипты подтверждают, что разница — в поведении модели, а не в шуме оценки.
- Demystifying evals: набор проверок возможностей насыщается — на 100 процентах он ловит регрессии, но не показывает улучшений; задачи с высоким прохождением переходят в регрессионный набор, а для роста нужны новые, более трудные.
- Сбои, найденные после внедрения, добавляются в набор задач.

## Скиллы и субагенты Claude Code

- Skills, раздел Evaluate and iterate on a skill: срабатывание и результат меряются отдельно. Проверка — сравнение с базой: реалистичные запросы в свежей сессии со скиллом и с выключенным скиллом; свежая сессия нужна, потому что контекст написания скилла маскирует пробелы в инструкциях.
- Там же: для скилла в плагине — `claude plugin eval` (прогоны с плагином и без, оценщики, порог для CI); для одного скилла — плагин skill-creator (тест-кейсы в `evals/evals.json`, изолированные прогоны субагентами, оценка, сравнение со скиллом и без, слепое A/B двух версий скилла, подбор описания по запросам «должен сработать» и «не должен»).
- Срабатывание по описанию, Agent Skills: «Aim for about 20 queries: 8-10 that should trigger and 8-10 that shouldn't» (около 20 запросов: 8–10, где скилл должен сработать, и 8–10, где не должен); каждый запрос — несколько прогонов (в примере источника — по 3); запрос «должен сработать» проходит, если доля срабатываний выше порога (0.5 — разумное значение по умолчанию), «не должен» — если ниже; деление на обучающую (~60%) и проверочную (~40%) выборки, проверочная используется только для проверки, обобщаются ли улучшения.
- Sub-agents: для субагента в плагине надёжность делегирования меряется `claude plugin eval` на реалистичных запросах.

## Результат

- Критерии успеха.
- Набор задач с эталонами (файл или таблица).
- Оценщики и рубрики.
- Таблица результатов по вариантам: доля прохождения по каждому критерию, число прогонов, pass@k или pass^k.
- Выводы из транскриптов: какие провалы — от промпта, какие — от оценщика или задачи.
- Решение по варианту.

## Пример

**Вход:** два варианта системного промпта бота поддержки на Haiku 5.5; критерий — бот не даёт скидку вне правил и не отказывает в скидке, положенной по правилам.

**Ход:** 30 задач из логов поддержки — 15, где скидка положена, и 15, где нет (баланс шага 2); у каждой эталонный ответ. Оценщик кодом проверяет итоговое состояние (оформлена ли скидка), оценщик-модель по рубрике — тон, с выходом «Unknown». По 3 прогона на задачу, метрика pass^3. Чтение транскриптов показывает, что две «ошибки» второго варианта — эталон с устаревшей ценой; эталон исправлен, прогон повторён.

**Результат:** таблица pass^3 по двум критериям для обоих вариантов и решение по варианту.

Пример иллюстративный: числа условные.
