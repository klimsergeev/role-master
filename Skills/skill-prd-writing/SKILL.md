# PRD Writing

## Назначение

Процедура создания PRD-документов через интерактивный сбор требований и проработку сценариев. Применяется любым агентом для формализации продуктовых требований к UI-продуктам.

## Принципы языка

1. **Инфостиль** — четкие формулировки без канцеляризмов и воды
2. **Русские эквиваленты** — пользователь (не юзер), нажать (не кликнуть), функциональность (не фича в тексте PRD)
3. **Допустимые англицизмы** — PRD, MVP, User Story, Acceptance Criteria, Agile, Sprint, API, UX, A/B-тест
4. **Без смешивания** — не "заапрувить", не "задеплоить", не два англицизма подряд (кроме устоявшихся)
5. **Структурированность** — списки, таблицы, заголовки для навигации
6. **Экономия** — без долгих вступлений, фокус на сути
7. **Полная таблица англицизмов** — в [prd-template.md](prd-template.md)

## Рабочий процесс

### Шаг 1: Анализ входных данных

Прочитать документ/описание от пользователя. Определить, что известно: ЦА, проблема, бизнес-цели, функциональность. Составить список пробелов.

### Шаг 2: Сбор требований

Задать уточняющие вопросы по категориям. Детали процедуры и правила опроса -- в [requirements-gathering.md](requirements-gathering.md).

### Шаг 3: Проработка сценариев

Сформулировать User Stories, определить типы сценариев (Happy Path, Alternative, Edge, Error), проработать состояния UI. Детали -- в [scenarios-and-states.md](scenarios-and-states.md).

### Шаг 4: Формирование PRD

Собрать документ по структуре шаблона. Структура и формат -- в [prd-template.md](prd-template.md).

### Шаг 5: Самопроверка по чеклисту

Перед выдачей проверить PRD:

- [ ] **Понятность:** Любой член команды понимает, что нужно сделать
- [ ] **Полнота:** Описаны все основные сценарии, edge-cases, состояния
- [ ] **Измеримость:** Есть acceptance criteria для проверки реализации
- [ ] **Пустые состояния:** Проработаны заглушки, первый запуск, отсутствие данных
- [ ] **Обработка ошибок:** Описано поведение системы при сбоях
- [ ] **Контекст:** Ясны бизнес-цели и целевая аудитория
- [ ] **Формат:** PRD сохранен в Markdown-формате

### Шаг 6: Сохранение

Сохранить PRD в файл, указанный пользователем. Формат: `[Название]_PRD.md`.

## Что НЕ делать

- Не рисовать дизайн интерфейсов -- направить к дизайнеру
- Не определять приоритеты и дедлайны -- это работа продакт-менеджера
- Не описывать техническую архитектуру -- это работа разработчиков
- Не принимать продуктовые решения за команду
- Не создавать DOCX без явной просьбы (по умолчанию Markdown)

## Примеры маршрутизации

### Пример 1: PRD с нуля при достаточной информации

**Запрос:** "Нужна фича уведомлений о снижении цены. ЦА -- покупатели. Цель -- повторные покупки."

**Маршрут:** [prd-template.md](prd-template.md), [scenarios-and-states.md](scenarios-and-states.md)

**Результат:** Полный PRD с User Stories, AC, состояниями, edge-cases.

### Пример 2: PRD с нуля при недостатке информации

**Запрос:** "Нужно сделать возможность добавлять товары в корзину"

**Маршрут:** [requirements-gathering.md](requirements-gathering.md) -> после ответов -> [prd-template.md](prd-template.md)

**Результат:** Сначала уточняющие вопросы, затем PRD.

### Пример 3: Запрос вне компетенции

**Запрос:** "Нарисуй интерфейс формы регистрации"

**Маршрут:** Отказ. Предложить альтернативу: PRD для формы регистрации.

**Результат:** Объяснение границ компетенции + предложение помочь с PRD.
