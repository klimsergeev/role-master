# Skill Refine

## Назначение

Скилл берёт выжимку уроков из сессии (артефакт вида session-harvest — обычно от `skill-session-harvest`) и существующий скилл, лежащий в git-репозитории, и решает по каждому уроку: улучшит ли он этот скилл — и если да, как именно. На выходе первой фазы — вердикт с обоснованием по каждому уроку и конкретные предложения правок. Сами файлы скилла меняются только во второй фазе и только после того, как пользователь явно одобрил конкретные предложения.

Это скилл-редактор чужого рабочего инструмента: ошибка здесь стоит дороже, чем при сборе знаний, потому что портит скилл, которым пользуются каждый день. Git даёт страховку (изолированное, откатываемое изменение), но не отменяет осторожность — одобрять правки придётся человеку.

## Принципы

1. **Дефолт — не менять.** Правка должна заслужить право на существование; «ничего не менять» — уважаемый, частый исход. Когда сомневаешься — не применяй. Полностью — в [refinement-bar.md](refinement-bar.md)
2. **Сомнение = не трогать скилл.** Если хоть по одной проверке планки нет уверенности — считай её не пройденной. См. планку в [refinement-bar.md](refinement-bar.md)
3. **Сверка с реальным кодом, не догадкой.** Привязку урока к скиллу и проверки «новизны» и «без вреда» делай, читая настоящий код скилла. Детали — в [workflow-gate.md](workflow-gate.md)
4. **Прочитать скилл целиком до выводов.** Без полного скилла нельзя судить ни о новизне, ни о вреде правки (см. [workflow-gate.md](workflow-gate.md))
5. **Правка минимальна и в стиле скилла.** Меняй ровно то, что нужно, как точечный diff / «было → стало» с указанием файла и места (см. [refinement-bar.md](refinement-bar.md))
6. **Жёсткий гейт до записи.** До явного одобрения в файлы не пишется ничего; скилл не коммитит и не пушит (см. [workflow-gate.md](workflow-gate.md))
7. **Честность суждения.** Отличай факт от догадки, уважай метки уверенности, не выводи отсутствие проблем из отсутствия урока в выжимке. Согласуется с проектным правилом [anti-bias.md](../../.claude/rules/anti-bias.md) (проверяй, а не оговаривайся; при сомнении — дополнительная проверка; не выдумывай данные)
8. **Активация строго по имени.** Скилл не запускается по смыслу запроса — только при явном вызове по имени или через механизм харнесса (см. frontmatter и [когда не применяется](#когда-скилл-не-применяется))

## Рабочий процесс

Две фазы. Между ними — **жёсткий гейт одобрения**: до него в файлы не пишется ничего. Полные детали каждого шага — в [workflow-gate.md](workflow-gate.md).

### Фаза 1 — анализ (ничего не пишет)

1. **Предполёт:** целевой скилл в git, рабочее дерево чистое (посторонние незакоммиченные изменения — предупреди до правок). Нет git (скилл вставлен в чат) — анализ всё равно делается, предложения выдаются как diff для ручного применения.
2. **Прочитай целевой скилл целиком** (SKILL.md + reference-файлы + бандл).
3. **Прочитай выжимку** (обычно артефакт `skill-session-harvest`; может быть текстом в чате).
4. **Прогони каждый урок через планку** ([refinement-bar.md](refinement-bar.md)) → вердикт (применить / не применять / проверить вручную) с обоснованием на реальном коде скилла.
5. **Покажи** вердикт по каждому уроку, для «применить» — правку (файл, место, было → стало), и общий итог. Ни один урок не прошёл — скажи прямо, почему. **Остановись.** Образец тона — в [example-analysis.md](example-analysis.md).

### Фаза 2 — применение (только после явного одобрения)

6. **Дождись одобрения** конкретных предложений (все, часть или ни одного). До одобрения не пиши в файлы.
7. **Внеси только одобренное** в рабочее дерево, минимально и ровно как предложено. Не примешивай неодобренное.
8. **Покажи `git diff`. Не коммить.** Можешь предложить commit-сообщение и отметить уместность bump версии / записи в changelog — но решение оставь пользователю.

## Что НЕ делать

- НЕ запускай скилл по смыслу запроса — только при явном вызове по имени или через механизм харнесса
- НЕ пиши в файлы до явного одобрения — жёсткий гейт между фазами
- НЕ применяй урок при сомнении хоть по одной проверке планки — вердикт «не применять» или «проверить вручную»
- НЕ притягивай урок за уши: дефолт — «не менять», лишняя инструкция раздувает контекст и сбивает поведение (см. [refinement-bar.md](refinement-bar.md))
- НЕ суди урок по догадке — только сверкой с реальным кодом целевого скилла
- НЕ разбивай скилл, не создавай новые скиллы, не переноси содержимое между скиллами — это архитектура, вынеси как наблюдение для человека (см. [workflow-gate.md](workflow-gate.md))
- НЕ коммить и не пуши — решение за пользователем
- НЕ грузи все reference-файлы сразу — только нужные под задачу (см. таблицу маршрутизации)

## Когда скилл не применяется

Скилл не запускается сам по смыслу запроса — только при явном вызове по имени или через механизм харнесса (см. описание во фронтматтере). По назначению он **не предназначен** для: написания нового скилла с нуля, общего код-ревью репозитория, редактирования произвольных файлов вне целевого скилла, а также сбора уроков из сессии (это делает `skill-session-harvest` до него). Его единственная работа — сверить уроки из выжимки с одним существующим скиллом и предложить, а после одобрения внести, точечные улучшения.

## Примеры

### Пример 1: Полный прогон, часть уроков отсеяна (типовой)

**Запрос:** «запусти skill-refine по этому скиллу — вот выжимка session-harvest»

**Маршрут:** [refinement-bar.md](refinement-bar.md), [workflow-gate.md](workflow-gate.md), при необходимости [example-analysis.md](example-analysis.md)

**Результат:** Предполёт (git чист) → скилл прочитан целиком → каждый урок прогнан через планку. Из четырёх уроков к применению — один (например, «обновить» инструкцию о тоне: релевантно, переносимо, ново, без вреда, уверенность высокая) с правкой «было → стало» и указанием файла/места; остальные — «не применять (новизна)», «не применять (переносимость)», «проверить вручную (низкая уверенность)», каждый с конкретной причиной. Анализ останавливается: в файлы ничего не пишется, ждём одобрения. Развёрнутый образец — в [example-analysis.md](example-analysis.md).

### Пример 2: Ни один урок не прошёл планку + скилл вставлен в чат (edge-case)

**Запрос:** «skill-skill-refine — сверь эти уроки со скиллом» (скилл вставлен текстом, git недоступен)

**Маршрут:** [workflow-gate.md](workflow-gate.md), [refinement-bar.md](refinement-bar.md)

**Результат:** git/файловой системы нет → анализ всё равно делается, предложения — как diff для ручного применения. После прогона планки выясняется, что все уроки либо уже покрыты (новизна), либо частности задачи (переносимость), либо помечены низкой уверенностью. Вердикт прямой: **правок не предлагается**, и по каждому уроку — почему. Ничего не правится, гейт не пройден за отсутствием одобряемых предложений.
