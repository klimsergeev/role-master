# Производительность анимаций

## Назначение

Процедура диагностики отвечает на вопрос «успевает ли каждый кадр»: находит причину потери кадров и выбирает свойство и драйвер, при которых движение укладывается в бюджет кадра. Кривая, длительность и решение, анимировать ли вообще, — в [motion-values.md](motion-values.md) и [review-motion.md](review-motion.md); React Native — вне охвата скилла.

## Жёсткие правила

1. **`transform` и `opacity` по умолчанию.** Всему остальному нужна причина. ЕСЛИ более дешёвое свойство даёт тот же вид → берётся оно, даже когда дорогое «вроде нормально».
2. **Причина называется до изменения кода.** Каждое исправление называет, какую из причин ниже оно устраняет. «Добавил `will-change`, вроде плавнее» — не диагноз.
3. **Вывод «всё в порядке» по быстрой машине не делается.** У каждой находки — отметка, проверена ли она по коду или нужна запись на реальном устройстве. Планка — телефон среднего класса.
4. **Никогда `transition: all`.** Перечисляются точные свойства: `all` анимирует всё, что изменится, включая свойства раскладки, которые никто не собирался анимировать.
5. **Корректность не меняется на оптимизацию «по возможности».** Аппаратное ускорение браузер может дать, а может не дать; какие свойства анимировать — решает код. Усилие тратится на второе.

| Проблема | Решение |
| --- | --- |
| Анимация дёргается | Анимировать `transform`/`opacity`, а не `width`/`height`/`top`/`margin` |
| Анимация тени рвётся | `filter: drop-shadow()` |

| Самописная анимация теряет кадры в React | Писать в `ref.current.style`, а не в состояние |
| Перетаскивание тормозит тем сильнее, чем длиннее список | Перестать анимировать наследуемую CSS-переменную; ставить `transform` напрямую |
| Переход с размытием лагает (особенно в Safari) | Держать анимированный `blur()` меньше 20px |
| Анимируются неожиданные свойства | Заменить `transition: all` явными свойствами |
| Элемент сдвигается на 1px в начале или конце движения | `will-change: transform`, только когда это увидели |

## Бюджет кадра

1000/60 ≈ 16.7ms на кадр при 60 Гц, 1000/120 ≈ 8.3ms при 120 Гц; web.dev советует при 60 Гц уложить свою работу в 10ms из-за накладных расходов браузера. Самая распространённая частота — 60 Гц, широко используются 75, 120 и 144 Гц; проектировать под меньший бюджет.

Расхождение с первоисточником: у Эмиля — «On a 120Hz screen, now most phones and many laptops, it's **8ms**.» (skills/animation-performance/SKILL.md); по MDN, https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame — распространённая частота 60 Гц, широко используются и 75, 120, 144 Гц; данных о том, что 120 Гц у большинства телефонов, нет.

Для масштаба: перерасчёт раскладки на сложной странице может занять больше 100ms (оценка документации Motion) — это не один пропущенный кадр, а дюжина.

Попадание в бюджет решают две вещи:

1. **Что анимируется** — сколько работы стоит каждый кадр.
2. **Где это выполняется** — может ли работу заблокировать всё остальное, что делает страница.

## Что анимируется

Чтобы показать визуальное изменение, браузер выполняет до трёх этапов:

- **Layout** (раскладка) — вычислить размер и положение каждого элемента.
- **Paint** (отрисовка) — нарисовать страницу в слои.
- **Composite** (композиция) — вывести слои на экран.

Каждое свойство входит в конвейер в одной из трёх точек, и стоимость различается на порядок:

| Уровень | Свойства | Стоимость |
| --- | --- | --- |
| Только композиция | `transform`, `opacity` — во всех основных браузерах; `filter`, `backdrop-filter`, `clip-path` — в Chromium; `background-color` — в Chromium и Firefox | Самая дешёвая. Анимация этих свойств повышает элемент до своего слоя |
| Отрисовка + композиция | `box-shadow`, `border-radius`, `color` | Без перерасчёта раскладки, но перерисовка каждый кадр |
| Раскладка + отрисовка + композиция | `width`, `height`, `padding`, `margin`, `top`, `left`, `border-width` | Самая дорогая. Один растущий элемент может сдвинуть всё вокруг |

`transform` и `opacity` на компоновщике во всех основных браузерах. `filter`, `backdrop-filter`, `clip-path` — в Chromium, не в Firefox. `background-color` — в Chromium через paint worklet и в Firefox. Поведение Safari не сверялось. Анимация этих свойств повышает элемент до своего слоя.

Расхождение с первоисточником: у Эмиля — «and in current Chrome/Firefox also `filter`, `clip-path`, `background-color`» (skills/animation-performance/SKILL.md); по исходному коду Firefox, https://github.com/mozilla-firefox/firefox/blob/main/servo/components/style/properties/longhands.toml — в Firefox на компоновщике нет `filter` и `clip-path`.

`transform` и `opacity` меняют то, как элемент выглядит, а не где он стоит в потоке документа, поэтому ничего не перемеряется. Всё остальное на уровне композиции проверяется на разных браузерах и устройствах: поддержка неравномерная.

Замена на уровень ниже:

| Вместо | Анимировать |
| --- | --- |
| `width` / `height` / `padding`, чтобы вырасти или сжаться | `scale()` |
| `top` / `left` / `margin`, чтобы сдвинуть | `translate()` (проценты — от размера самого элемента) |
| Переключение `display` / `visibility` | `opacity` |
| `box-shadow` | `filter: drop-shadow(…)` |

Последнюю замену упускают чаще всего: анимированная тень выглядит безобидно, но перерисовывает элемент каждый кадр. Выигрыш от `drop-shadow` — там, где `filter` анимируется на компоновщике (уровень «только композиция» выше).

Два следствия:

- **Анимация раскладки не всегда теряет кадры.** Абсолютно позиционированный элемент или элемент с немногими детьми может анимировать `padding` без видимой цены. Но анимации `padding` и `scale()` выглядят одинаково, и только одна из них не может деградировать на более медленном устройстве. Берётся та, у которой нет минуса.
- **Свойства раскладки двигают не то.** Анимация `margin-left` боковой панели толкает соседнее содержимое каждый кадр; `translateX` — нет. Для рабочей панели рядом с открывающейся боковой панелью это перерасчёт раскладки всей страницы 60 раз в секунду.

## Где выполняется

**JavaScript всегда работает на главном потоке.** Анимация на `requestAnimationFrame` конкурирует со всем остальным, что делает браузер. Когда главный поток занят, код анимации не может выполниться, и кадр опаздывает.

| Драйвер | Поток |
| --- | --- |
| JS + `requestAnimationFrame` (GSAP, layout-анимации Motion) | Главный поток, всегда |
| Web Animations API (`element.animate()`, `animate()` из Motion и компоненты `motion/react`) | Может быть аппаратно ускорен |
| CSS-переходы и ключевые кадры | Может быть аппаратно ускорен |

Аппаратное ускорение — это выполнение анимации вне главного потока: она остаётся плавной, что бы ни делал JavaScript. «JS» и «главный поток» не синонимы: JS-библиотека, которая передаёт работу в WAAPI, может быть ускорена, цикл на rAF — нет.

Надёжно ускоряются `transform` и `opacity`. `filter`, `clip-path`, `background-color` получают поддержку.

Вне главного потока работают CSS-анимации и переходы тех свойств, которые браузер выносит на компоновщик (надёжно — `transform` и `opacity`). Анимации на `requestAnimationFrame`, включая layout-анимации Motion, при занятом главном потоке теряют кадры.

Расхождение с первоисточником: у Эмиля — «CSS animations run off the main thread.» (skills/emil-design-eng/SKILL.md); по документации Motion, https://motion.dev/docs/performance — вне главного потока работают только анимации свойств, которые браузер выносит на компоновщик.

**Шаблон, за которым следить, — движение, которое играет, пока страница делает тяжёлую работу:** переходы страниц, индикаторы вкладок во время навигации, всё, что запускается вместе с загрузкой данных или гидрацией. По опыту Эмиля Ковальски, дашборд Vercel анимировал индикатор активной вкладки shared layout-анимацией Framer Motion; браузер в этот момент грузил следующую страницу и терял кадры. Перенос на CSS-анимацию исправил это.

Motion отдаёт в WAAPI `opacity`, `transform`, `clip-path` и `filter`, поэтому они могут быть ускорены. Сокращения `x`, `y`, `scale`, `rotate` зависят от версии:

```jsx
<motion.div animate={{ x: 100 }} />                          // motion 14.2+: hardware-accelerated. Before: main thread, can jank
<motion.div animate={{ transform: "translateX(100px)" }} />  // hardware-accelerated in every version
```

С `motion` 14.2 сокращения на HTML-элементе собираются в одну ускоренную анимацию `transform`, поэтому их оставляют. В более старых версиях, когда анимация должна пережить занятый главный поток, — строковая форма. В любой версии на главном потоке остаются: layout-анимации (`layout`, `layoutId`), `onUpdate`, `transformTemplate`, инерция и значения, которые каждый кадр задаёт motion value (перетаскивание, `useTransform`).

**Ускорение — прогрессивное улучшение.** Браузеры молча отказывают в нём при условиях, которые меняются между версиями; Chrome, например, долго не ускорял процентные трансформации. Это не повод отказаться от `translateY(100%)`: проценты — верный выбор для элементов неизвестного размера (так Sonner и Vaul ставят тосты и шторки), а корректность важнее оптимизации «по возможности».

## React: не анимировать через состояние

Библиотеки анимаций работают вне цикла рендера React, поэтому с ними всё в порядке. Изменение motion value (`y.set(nextY)`) обновляет DOM без перерисовки React; `setState` на каждом кадре перерисовывает компонент каждый кадр, и тяжёлый компонент съедает этим бюджет кадра.

Расхождение с первоисточником: у Эмиля — «the component re-renders every 16.7ms and the render alone blows the budget» (skills/animation-performance/SKILL.md); по документации Motion, https://motion.dev/docs/react-motion-value — motion value обновляет DOM без перерисовки React; что перерисовка всегда выбивает бюджет, источником не подтверждено, цена зависит от компонента.

```jsx
// Drops frames: one re-render per frame
setY(nextY);

// Smooth: no re-render
ref.current.style.transform = `translateY(${nextY}px)`;
// or with a motion value: y.set(nextY)
```

Искать обновления состояния внутри `requestAnimationFrame`, `pointermove`, `scroll` и обработчиков перетаскивания.

## Две ловушки, которые выглядят правильно

Обе используют `transform` и всё равно теряют кадры.

**Наследуемые CSS-переменные.** По опыту Эмиля Ковальски, перетаскивание Vaul начинало тормозить, когда в шторке было больше ~20 элементов, без всяких перерисовок React. Расстояние перетаскивания писалось в CSS-переменную, которую читал `translateY()`:

```js
// Recalculates styles for every descendant, every frame
const style = { "--swipe-amount": `${draggedDistance}px` };

// Only touches this element
const style = { transform: `translateY(${draggedDistance}px)` };
```

Пользовательские CSS-свойства наследуются, поэтому смена переменной на родителе затрагивает стили всех потомков, которые её наследуют; объём пересчёта зависит от движка. Наследование отключает регистрация через `@property` с `inherits: false`. ЕСЛИ анимация на `transform` деградирует с ростом содержимого → подозревать эту ловушку.

Расхождение с первоисточником: у Эмиля — «Changing a CSS variable on a parent recalculates styles for all children.» (skills/emil-design-eng/SKILL.md); по CSS Properties and Values API Level 1, https://drafts.css-houdini.org/css-properties-values-api-1/#inherits-descriptor — наследование подтверждено, объём пересчёта спецификация не описывает, `inherits: false` наследование отключает.

**Размытие.** По наблюдению Эмиля Ковальски, `filter: blur()` быстро дорожает, особенно в Safari. Анимированное размытие держать меньше 20px; для смягчения кроссфейда хватает 2–5px.

## `will-change`

По наблюдению Эмиля Ковальски, браузер может передать анимацию с CPU на GPU посреди движения, и эта передача может сдвинуть элемент на пиксель в начале или конце; `will-change` повышает элемент заранее, и передачи не происходит:

```css
.drawer {
  will-change: transform;
}
```

**Добавлять только после того, как увидели сдвиг или замерили потерю кадров.** Анимируемые свойства браузер и так считает включёнными в `will-change`, поэтому во время анимации `transform` или `opacity` подсказка ничего не добавляет; польза — когда её задают заранее, до начала изменения. Каждый слой стоит памяти GPU. `will-change` ставится на анимируемый элемент, никогда на `*` и не на большие контейнеры.

Расхождение с первоисточником: у Эмиля — «so on the common path it does nothing» (skills/animation-performance/SKILL.md); по MDN, https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/will-change — во время анимации подсказка лишняя, но заданная заранее она даёт браузеру подготовиться к изменению.

Место, где `will-change` окупается, — дорогая отрисовка, например большой размытый или отфильтрованный элемент. Его повышают и держат слой маленьким: маленький слой компоновать дешевле полноэкранного.

## Нужно ли избегать JS-анимации

Нет. Анимация на главном потоке страдает, только когда страница занята во время неё; это редкость, и выше описано, как это распознать.

Motion даёт то, чего нет в CSS: пружины, которые подхватывают скорость, анимации ухода размонтированных компонентов React, жесты с инерцией. Пружину без скорости Motion умеет сгенерировать для CSS-перехода (`spring()`), переходы общих элементов между видами есть в View Transition API. Вопрос в том, нужно ли это задаче, а не в том, разрешена ли JS-анимация.

Расхождение с первоисточником: у Эмиля — «Framer Motion gives you things CSS can't: real springs, shared layout animations» (skills/animation-performance/SKILL.md); по документации Motion, https://motion.dev/docs/spring — пружину без скорости можно сгенерировать для CSS-перехода, переходы общих элементов даёт View Transition API.

**Рабочее разделение:** CSS — для простого движения и всего, что играет, пока страница занята; Motion — для сложного, прерываемого, жестового движения.

## Рабочий процесс

### Фаза 1: Найти, что анимируется

Каждая анимация в охвате — с драйвером и свойствами:

| Элемент | Драйвер | Свойства | Когда играет |
| --- | --- | --- | --- |
| Tab indicator | `motion/react` `layoutId` | layout | route change |
| Drawer | CSS transition | `transform` | user drag |
| Card hover | CSS transition | `all` | hover |

`transition: all` и сокращения Motion разворачиваются в то, что они анимируют на самом деле.

### Фаза 2: Диагностика

Список идёт по частоте причин:

1. **Какие свойства анимируются?** Всё, кроме `transform`/`opacity`, — первый подозреваемый: сначала свойства раскладки, затем `box-shadow` и `border-radius`, которые не похожи на раскладку и легко упускаются.
2. **Совпадают ли рывки с занятостью страницы?** Навигация, загрузка, гидрация, длинная задача. Анимация переносится в CSS или WAAPI.
3. **Перерисовывается ли React каждый кадр?** Обновления состояния в обработчиках rAF, указателя или скролла.
4. **Становится ли хуже с ростом содержимого?** Наследуемая CSS-переменная или слишком много одновременно анимируемых узлов.
5. **Анимируется ли CSS-переменная вообще?** Или `x`/`y`/`scale` Motion в версии до 14.2?
6. **Есть ли анимированный `blur()` больше 20px?**
7. **Всё ещё сдвигается или дёргается?** Теперь — `will-change: transform` на анимируемый элемент.

Подтверждение — записью, а не на ощупь. Панель Performance показывает потерянные кадры и длинные задачи; панель Animations замедляет, повторяет и прокручивает анимацию. Профилирование — на реальном телефоне среднего класса через удалённую отладку. Троттлинг DevTools замедляет процессор (в 4 раза); поэтому итоговая проверка — на реальном телефоне среднего класса.

Расхождение с первоисточником: у Эмиля — «CPU throttling on a desktop models a slow CPU, not a weak GPU or a small memory budget.» (skills/animation-performance/SKILL.md); по документации Chrome DevTools, https://developer.chrome.com/docs/devtools/performance — троттлинг описан только как замедление процессора в 4 раза, о GPU и памяти документация не пишет.

### Фаза 3: Отчёт

Артефакт процедуры — запись по каждой находке:

```
**[Element]**: `file.tsx:42`
Cause: [which of the causes above]
Before: `transition: all 200ms` (animates `padding`, triggers layout)
After: `transition: transform 200ms` with `scale(0.97)`
Verified: from code / needs a device recording
```

Находки упорядочены по стоимости: раскладка раньше отрисовки, занятый главный поток раньше свободного. ЕСЛИ исправление не входит в задачу → процедура заканчивается отчётом.
