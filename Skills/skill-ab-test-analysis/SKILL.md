# A/B Test Analysis

## Назначение

Процедура анализа результатов A/B-тестов от валидации эксперимента до финальной рекомендации ship/no-ship/iterate. Применяется продуктовыми аналитиками, продакт-менеджерами и data-аналитиками при интерпретации экспериментов.

## Принципы

1. **Статистическая значимость != практическая значимость** -- всегда оценивай и p-value, и размер эффекта
2. **Валидация до анализа** -- проверь SRM, длительность и мощность прежде чем смотреть на результаты
3. **Guardrails обязательны** -- положительный primary metric не оправдывает деградацию guardrail-метрик
4. **Pre-registered анализ** -- сегменты, метрики и пороги определяются ДО просмотра результатов
5. **Честная неопределённость** -- "inconclusive" это валидный результат, не повод для post-hoc манипуляций

## Рабочий процесс

### Шаг 1: Валидация эксперимента

Прежде чем анализировать результаты, проверь корректность самого эксперимента.

**Чеклист валидации:**

- [ ] **SRM (Sample Ratio Mismatch):** фактическое соотношение трафика соответствует запланированному (chi-square test, p > 0.01)
- [ ] **Длительность:** тест проработал минимально необходимое время (обычно >= 1 полный бизнес-цикл, минимум 7 дней)
- [ ] **Размер выборки:** достигнут pre-calculated sample size для заданного MDE и power
- [ ] **Нет внешних факторов:** не было промо-акций, технических сбоев, сезонных аномалий в период теста
- [ ] **Контроли на нулевом эффекте:** invariant-метрики (те, на которые вариант не может влиять) не сдвинулись; для новой метрики, новой единицы рандомизации или нового пайплайна прогнан A/A-тест

ЕСЛИ SRM обнаружен -> тест невалиден, результаты нельзя использовать. Сообщить и предложить диагностику причин.

ЕСЛИ invariant-метрика значимо сдвинулась ИЛИ A/A даёт значимость чаще alpha -> пайплайн невалиден, см. [common-errors.md](common-errors.md). Результаты не использовать.

ЕСЛИ выборка не достигнута -> перейти к шагу 5, рекомендация "extend" или "inconclusive".

### Шаг 2: Расчёт primary metric

Рассчитать основную метрику эксперимента. Детали статистических методов -- в [statistical-framework.md](statistical-framework.md).

**Обязательные показатели:**

| Показатель | Формула / описание |
|---|---|
| Observed lift | (Treatment - Control) / Control * 100% |
| Confidence interval (95%) | Диапазон правдоподобных значений истинного эффекта |
| P-value | Вероятность наблюдаемого результата при отсутствии эффекта |
| Statistical power | Вероятность обнаружения эффекта заданного размера (целевая >= 80%) |

ЕСЛИ p < 0.05 И lift положительный -> предварительно положительный результат, перейти к шагу 3.

ЕСЛИ p < 0.05 И lift отрицательный -> предварительно негативный результат, перейти к шагу 3.

ЕСЛИ p >= 0.05 -> результат не значим, перейти к шагу 3 (guardrails всё равно проверяются).

### Шаг 3: Проверка guardrail-метрик

Guardrails -- метрики, которые НЕ должны ухудшиться в результате эксперимента.

**Типичные guardrails:**
- Latency / время загрузки страницы
- Error rate / crash rate
- Revenue per user (если primary metric -- engagement)
- Retention (если primary metric -- конверсия)
- Customer support tickets

**Правило оценки:**

- ЕСЛИ guardrail значимо ухудшился (p < 0.05) -> блокирующий фактор для ship
- ЕСЛИ guardrail ухудшился незначимо, но тренд заметен -> отметить как risk, не блокировать
- ЕСЛИ все guardrails стабильны -> перейти к шагу 4

### Шаг 4: Сегментный анализ

Проверить, как эффект распределён по ключевым сегментам. Анализировать ТОЛЬКО pre-registered сегменты.

**Стандартные сегменты:**

| Сегмент | Что ищем |
|---|---|
| Новые vs. вернувшиеся пользователи | Novelty effect (эффект только у новых) |
| Mobile vs. desktop | Платформенная специфика |
| Когорта регистрации | Различия по зрелости пользователей |
| Географический регион | Региональные особенности |

**Правила:**
- ЕСЛИ эффект значим в одном сегменте, незначим в другом -> рассмотреть сегментный rollout
- ЕСЛИ эффект противоположный в разных сегментах -> возможен Simpson's Paradox, см. [common-errors.md](common-errors.md)
- НИКОГДА не добавлять сегменты post-hoc для "улучшения" результата -- это p-hacking

### Шаг 5: Ship/no-ship решение

Собрать все данные в финальную рекомендацию. Матрица решений и формат вывода -- в [decision-framework.md](decision-framework.md).

**Экспресс-матрица:**

| Primary metric | Guardrails | Решение |
|---|---|---|
| Значимо положительный | Стабильны | **Ship** |
| Значимо положительный | Один ухудшился | **Iterate** (доработать) |
| Незначимый (p >= 0.05) | Стабильны | **Inconclusive** (продлить или закрыть) |
| Значимо отрицательный | Любые | **No-ship** |
| Любой | SRM обнаружен | **Невалидный тест** |

ВСЕГДА формировать финальный отчёт по шаблону из [decision-framework.md](decision-framework.md).

## Что НЕ делать

- Не анализировать результаты без проверки валидности эксперимента (шаг 1)
- Не останавливать тест раньше запланированного срока только потому что p < 0.05 (peeking)
- Не добавлять сегменты или метрики post-hoc для "улучшения" результатов
- Не игнорировать деградацию guardrail-метрик ради положительного primary metric
- Не путать статистическую и практическую значимость
- Не принимать "inconclusive" за "нет эффекта" -- это разные утверждения
- Не проводить множественные сравнения без коррекции (Bonferroni или аналог)
- Не рекомендовать ship при обнаруженном SRM

## Примеры

### Пример 1: Типовой положительный A/B-тест

**Запрос:** "Тест нового чекаута: конверсия выросла с 3.2% до 3.5%, p = 0.02, 50k пользователей в каждой группе. Можно шипить?"

**Маршрут:** Этот файл (рабочий процесс), [decision-framework.md](decision-framework.md)

**Результат:**
1. Валидация: SRM нет (50/50), длительность достаточна
2. Primary metric: lift +9.4%, CI [+1.8%, +17.0%], p = 0.02 -- значим
3. Запросить guardrail-метрики (latency, error rate, revenue)
4. Сегментный анализ по pre-registered сегментам
5. Рекомендация: **Ship** (при условии что guardrails стабильны)

### Пример 2: Edge-case -- SRM и противоречивые сегменты

**Запрос:** "A/B-тест показал +5% конверсии (p = 0.01), но в группе B на 15% больше пользователей чем планировали. Среди mobile +12%, среди desktop -3%."

**Маршрут:** Этот файл, [common-errors.md](common-errors.md), [decision-framework.md](decision-framework.md)

**Результат:**
1. Валидация: SRM обнаружен (15% отклонение от плана) -- тест невалиден
2. Рекомендация: **Невалидный тест**. Результаты нельзя использовать для принятия решений
3. Расхождение mobile/desktop может быть артефактом SRM, а не реальным эффектом
4. Действие: найти причину SRM (бот-трафик, ошибка в распределении, разница в eligibility criteria), перезапустить тест

### Пример 3: Edge-case -- статистически значимый, но практически бесполезный результат

**Запрос:** "Тест с 2 млн пользователей: конверсия +0.02%, p = 0.04. Шипить?"

**Маршрут:** Этот файл, [statistical-framework.md](statistical-framework.md), [decision-framework.md](decision-framework.md)

**Результат:**
1. Валидация: пройдена (большой sample)
2. Primary metric: p = 0.04 -- формально значим, но lift +0.02% ничтожен
3. Практическая значимость: эффект ниже любого разумного MDE
4. Рекомендация: **No-ship** или **Inconclusive**. Статзначимость достигнута за счёт огромной выборки, реальный эффект отсутствует. Ресурсы лучше направить на другие гипотезы
