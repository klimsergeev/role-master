# Матрица версий

Отвечает на вопрос: **можно ли на этом сервере написать вот эту конструкцию — и что писать, если нельзя.**

Матрица начинается с SQL Server 2016 (13.x). Строки 2012–2014 — в свёрнутой секции в конце. Прежде чем сверяться с матрицей, выясни версию **и** уровень совместимости: [server-profile.md](server-profile.md).

---

## Как читать матрицу

Каждая строка опирается на строку «Applies to» страницы соответствующей конструкции в T-SQL Reference. Формулировка «SQL Server 2019 и новее» означает, что так написано на странице, а не что кто-то это проверил на сервере.

Две колонки условий — не украшение:

| Колонка | Что означает |
|---|---|
| Минимальная версия | какой код установлен на сервере (`SERVERPROPERTY('ProductMajorVersion')`) |
| Дополнительное условие | уровень совместимости базы или иная оговорка страницы |

**Общее правило из документации:** «New T-SQL syntax isn't gated by database compatibility level, except when they can break existing applications by creating a conflict with user T-SQL code» (страница `ALTER DATABASE … SET COMPATIBILITY_LEVEL`). То есть большинство новых конструкций уровнем не гейтится — но исключения есть, они перечислены ниже и их надо знать поимённо.

## SQL Server 2016 (13.x)

| Возможность | Дополнительное условие | Примечание |
|---|---|---|
| `STRING_SPLIT` | **уровень совместимости ≥ 130** | «If your database compatibility level is lower than 130, SQL Server won't be able to find and execute `STRING_SPLIT` function» — то есть на сервере 2022 с базой 120 функции просто нет. Порядок строк на выходе не гарантирован |

| `DATEDIFF_BIG` | — | Когда `DATEDIFF` переполняет `int` |
| `STRING_ESCAPE` | — | Пока только режим `'json'` |
| `COMPRESS` / `DECOMPRESS` | — | GZIP; результат `varbinary(max)` |
| `SESSION_CONTEXT` | — | Читает то, что положили `sp_set_session_context` |
| `sys.dm_exec_query_stats`, диагностические DMV из [dmv-diagnostics.md](dmv-diagnostics.md) | права | Существуют и раньше 2016; здесь важны права, а не версия |

## Вторая ось: уровень совместимости

Уровень совместимости — свойство базы, а не сервера. Читается из `sys.databases.compatibility_level`, допустимые значения — 80, 90, 100, 110, 120, 130, 140, 150, 160, 170. Таблица «версия движка → уровень по умолчанию → поддерживаемые уровни» — в [server-profile.md](server-profile.md).

Подтверждённые случаи, когда уровень решает исход:

| Что зависит | Порог | Что именно происходит |
|---|---|---|
| `STRING_SPLIT` | ≥ 130 | Ниже — движок функцию не находит |
| `OPENJSON` | ≥ 130 | Ниже — функции нет; остальные функции JSON доступны на любом уровне |
| `STRING_AGG … WITHIN GROUP (ORDER BY …)` | ≥ 110 | Сама `STRING_AGG` доступна на любом уровне, а её сортировка — нет |
| Стиль по умолчанию у `CAST`/`CONVERT` над `time` и `datetime2` | 110 | С уровня 110 стиль всегда 121; ниже — 121 везде, кроме вычисляемых столбцов, где 0 |
| Неявное преобразование `datetime` → `datetime2` | 130 | С уровня 130 учитываются доли миллисекунд, значения получаются другие. Вернуть прежнее поведение можно только уровнем 120 или ниже |
| `PIVOT` внутри рекурсивного CTE | 110 | С уровня 110 запрещён; ниже разрешён, но при нескольких строках на группу даёт неверный результат |
| Состав зарезервированных слов | зависит от уровня | «The words that are reserved depend on the database compatibility level» — то же имя может быть валидным идентификатором на одном уровне и требовать скобок на другом |
| `TRY_CONVERT` как зарезервированное слово | 110 | «`TRY_CONVERT` is a reserved keyword, starting with compatibility level 110». У `TRY_CAST` наоборот: «isn't a new reserved keyword and is available in all compatibility levels» |

**Обход по уровню — не наш инструмент.** Конфигурация `ALLOW_BUILTIN_TVF_IN_ALL_COMPAT_LEVELS` снимает требование по уровню для `GENERATE_SERIES`, `OPENJSON`, `REGEXP_MATCHES`, `REGEXP_SPLIT_TO_TABLE` и `STRING_SPLIT`, но **applies to там — только Azure SQL Database и SQL database в Fabric, и сама конфигурация в предварительной версии**. На «коробочном» SQL Server её нет. Знать о ней стоит ради обратного вывода: если табличная функция вдруг работает на низком уровне, объяснение может быть в этом — но только если вы в Azure.

Менять уровень совместимости агент не предлагает: это запись и администрирование.

## Если возможности нет

Порядок действий:

1. **Проверь, не в уровне ли дело.** Если конструкция из таблицы выше — препятствием может быть база, а не сервер. Тогда сказать надо именно так: «функция есть, но база на уровне 120».
2. **Возьми обход из списка ниже.** Каждый собран из конструкций, документированных для целевой версии; ссылки на страницы — в самой строке.
3. **Обхода нет — скажи прямо**, что на этой версии конструкция недоступна, и предложи переформулировать задачу. Придумывать обход «по аналогии» запрещено.

**Оговорка ко всем обходам.** Скилл собран по документации, живого прогона к базе у него нет ([SKILL.md](SKILL.md), «Срез данных»). Обход ниже — сборка из документированных конструкций, а не протестированный на сервере рецепт: перед тем как отдать результат пользователю, выполни его на его сервере и посмотри на вывод.

### Замена `IS [NOT] DISTINCT FROM` (до 2022)

Единственный обход, который документирован дословно: страница `IS [NOT] DISTINCT FROM` приводит выражения, в которые движок сам разворачивает предикат для связанных серверов, не умеющих его разбирать.

```sql
-- A IS DISTINCT FROM B
((A <> B OR A IS NULL OR B IS NULL) AND NOT (A IS NULL AND B IS NULL))

-- A IS NOT DISTINCT FROM B
(NOT (A <> B OR A IS NULL OR B IS NULL) OR (A IS NULL AND B IS NULL))
```

### Замена `GREATEST` / `LEAST` (до 2022)

Табличный конструктор значений (`VALUES` в предложении `FROM`) документирован задолго до 2016, агрегаты — тем более:

```sql
SELECT t.order_id,
       (SELECT MAX(v) FROM (VALUES (t.date_a), (t.date_b), (t.date_c)) AS x(v)) AS greatest_date,
       (SELECT MIN(v) FROM (VALUES (t.date_a), (t.date_b), (t.date_c)) AS x(v)) AS least_date
FROM   dbo.some_table AS t;
```

Отличие от `GREATEST`/`LEAST`, о котором надо помнить: агрегат `MAX`/`MIN` игнорирует `NULL`, поэтому поведение при `NULL` в списке может не совпасть — сверься с задачей.

### Замена `DATETRUNC` и `DATE_BUCKET` (до 2022)

Арифметика на `DATEADD`/`DATEDIFF` — обе функции есть во всех версиях матрицы:

```sql
-- начало месяца (аналог DATETRUNC(month, @d))
SELECT DATEADD(month, DATEDIFF(month, 0, @d), 0);

-- начало дня
SELECT DATEADD(day,   DATEDIFF(day,   0, @d), 0);

-- начало часа
SELECT DATEADD(hour,  DATEDIFF(hour,  0, @d), 0);
```

Ограничение: `DATEDIFF` возвращает `int` и на мелких единицах (секунды, миллисекунды) на больших промежутках переполняется — тогда `DATEDIFF_BIG` (2016+), но её результат в `DATEADD` уже не подставить без приведения. Для суточных и более крупных единиц проблемы нет.

### Замена `TRIM` (до 2017) и `TRIM(символы FROM …)` (до 2022)

`LTRIM(RTRIM(@s))` — обе функции есть во всех версиях. Удаление произвольных символов до 2022 одной функцией не выражается; собирается `REPLACE`/`PATINDEX`, и это уже не «обход», а отдельная задача — так и скажи.

### Замена `CONCAT_WS` (до 2017)

`CONCAT` (2012+) плюс явные разделители, либо `+` с `ISNULL`. Разница в поведении: `CONCAT` превращает `NULL` в пустую строку, `+` при `NULL` даёт `NULL` — выбирай осознанно.

### Замена `STRING_AGG` (до 2017)

`FOR XML PATH('')` со снятием через `TYPE` и `.value()`. Конструкция документирована (`FOR XML`, режим `PATH`, директива `TYPE`), но у неё есть особенность: **`FOR XML` экранирует служебные символы** — в документации это показано на примере whitespace-символов («The XML generated by the `FOR XML` white space characters in the data is entitized»), и то же касается `&`, `<`, `>`. Именно поэтому результат снимают через `.value('.', 'nvarchar(max)')`, а не берут строкой напрямую:

```sql
SELECT  t.group_id,
        STUFF((SELECT ',' + x.item_name
               FROM   dbo.items AS x
               WHERE  x.group_id = t.group_id
               ORDER BY x.item_name
               FOR XML PATH(''), TYPE).value('.', 'nvarchar(max)'), 1, 1, '') AS items
FROM    dbo.groups AS t
ORDER BY t.group_id;
```

### Замена `STRING_SPLIT` (нет функции или уровень ниже 130)

Рекурсивный CTE на `CHARINDEX` и `SUBSTRING` — все три конструкции документированы для всех версий матрицы:

```sql
WITH split AS (
    SELECT  CAST(NULL AS nvarchar(4000)) AS value,
            CAST(@s + N',' AS nvarchar(4000)) AS rest,
            0 AS ordinal
    UNION ALL
    SELECT  CAST(LEFT(rest, CHARINDEX(N',', rest) - 1) AS nvarchar(4000)),
            CAST(SUBSTRING(rest, CHARINDEX(N',', rest) + 1, 4000) AS nvarchar(4000)),
            ordinal + 1
    FROM    split
    WHERE   CHARINDEX(N',', rest) > 0
)
SELECT  ordinal, value
FROM    split
WHERE   ordinal > 0
ORDER BY ordinal
OPTION (MAXRECURSION 0);
```

Что здесь надо понимать, прежде чем отдавать это пользователю:

- Предел рекурсии по умолчанию — 100 уровней; `OPTION (MAXRECURSION 0)` снимает предел совсем, и при плохих данных это бесконечный цикл. Осмысленнее поставить конкретное число (`0`–`32767`).
- Типы в якорной и рекурсивной части обязаны совпадать — отсюда явные `CAST` в обеих частях.
- В отличие от `STRING_SPLIT`, этот обход **даёт** порядковый номер и **сохраняет** порядок; пустые подстроки между двумя подряд идущими разделителями он тоже вернёт (как и `STRING_SPLIT`).
- Живого прогона у скилла нет: выполни и посмотри на вывод, прежде чем строить на этом ответ.

### Замена предложения `WINDOW` (до 2022)

Повторить `OVER (…)` в каждой оконной функции. Никакой потери смысла — только длиннее.

### Замена `IIF` и `CHOOSE`

Обе — синтаксический сахар над `CASE` и доступны во всех версиях матрицы, поэтому обход нужен в обратную сторону: если код читает `IIF`, а вам надо переносимо — это `CASE WHEN … THEN … ELSE … END`. Ограничение вложенности `IIF` — 10 уровней, ровно как у `CASE`, потому что это и есть `CASE`.

## Что в матрице не подтверждено

| Утверждение | Состояние на 22.08.2026 |
|---|---|
| Версия введения `TRY_CAST` | **Не установлена.** Страница `TRY_CAST` версии не называет: её «Applies to» — общая строка «SQL Server» без года, а текст говорит только, что функция «isn't a new reserved keyword and is available in all compatibility levels». Практически на любом сервере от 2016 и новее она есть; год введения в скилле не называется, потому что документального подтверждения нет |
| Версия введения `TRY_CONVERT` | Прямой строки «введено в 2012» тоже нет, но страница говорит две вещи: слово зарезервировано начиная с уровня совместимости 110 и функция «is capable of being remoted to servers that have SQL Server 2012 and later versions. ## Чего в матрице нет и не будет

- **Номеров накопительных обновлений (CU) и дат их выхода.** Протухают ежемесячно. Актуальный CU читается с сервера: `SERVERPROPERTY('ProductUpdateLevel')`.
- **Соответствия «мажорная версия ↔ год выпуска».** Оно стабильно и живёт в [server-profile.md](server-profile.md), чтобы не дублироваться.
- **Возможностей вне читающих сценариев** — DDL, запись, Always On, Ledger, векторный поиск. Не предмет скилла.
- **Azure SQL Database, Managed Instance, Synapse, Fabric как целевых платформ.** Номера версий там несравнимы с «коробочными», и часть строк матрицы не действует; профиль распознаёт платформу по `EngineEdition` и предупреждает.

Нижняя граница матрицы — 2016. Если профиль показал `ProductMajorVersion` 11 или 12, работать придётся так:

| Что нужно знать | 2012 (11.x) | 2014 (12.x) | Основание |
|---|---|---|---|

| `LAG` / `LEAD` | есть | есть | «Accesses data from a previous row … starting with SQL Server 2012» |
| `STRING_SPLIT`, `OPENJSON` и функции JSON, `AT TIME ZONE`, `DATEDIFF_BIG`, `STRING_ESCAPE`, `COMPRESS`, `SESSION_CONTEXT` | нет | нет | «Applies to» этих страниц — 2016 и новее |
| `STRING_AGG`, `CONCAT_WS`, `TRIM`, `TRANSLATE` | нет | нет | «Applies to» — 2017 и новее |
| `sys.dm_os_host_info` | нет | нет | «Applies to» — 2017 и новее |
| Уровни совместимости | по умолчанию 110; поддерживаются 110, 100, 90 | по умолчанию 120; поддерживаются 120, 110, 100 | таблица уровней совместимости |
| Индексы в объявлении табличной переменной (inline) | нет | есть | «Starting with SQL Server 2014, new syntax was introduced which allows you to create certain index types inline with the table definition» |

Отдельно: `IIF`, `CHOOSE`, `CONCAT`, `FORMAT`, `PARSE`, `TRY_CONVERT`, `TRY_CAST` на своих страницах года введения не называют — там общая строка «Applies to: SQL Server» без версии. Считать их доступными или недоступными на 2012–2014 по документации нельзя; если это важно для задачи, проверь на самом сервере одним `SELECT`.

Практический вывод: на 2012–2014 читающая аналитика собирается из `CASE`, `CROSS APPLY`, оконных функций и `FOR XML PATH` вместо `STRING_AGG`. Обходы из раздела выше применимы, кроме тех, что опираются на `DATEDIFF_BIG` (2016+).

Статус поддержки этих версий — в [server-profile.md](server-profile.md); углублять архивную часть матрицы скилл не берётся, потому что страницы документации по снятым с поддержки версиям частью недоступны, а выдумывать нельзя.
