# Отладка промпта на тестах

## Назначение

Процедура проверки и сравнения вариантов промпта на наборе тестов по официальной методике Anthropic: критерии успеха, набор задач, оценщики, прогоны, чтение транскриптов, решение.

Сверено 2026-11-09.

Успешное приложение на LLM начинается с чёткого определения критериев успеха и оценок, которые измеряют работу по этим критериям; этот цикл — основа промпт-инжиниринга.

## Шаг 1. Записать критерии успеха

Хорошие критерии — конкретные, измеримые, достижимые и релевантные.

| Свойство | Что значит | Пример |
|---|---|---|
| Конкретный | Ясно, чего добиться | Точная классификация тональности вместо хорошей работы вообще |
| Измеримый | Количественная метрика или чётко определённая качественная шкала | Меньше 0,1% ответов из 10 000 прогонов помечены фильтром контента как токсичные — вместо просто безопасных ответов |
| Достижимый | Опирается на бенчмарки, прошлые эксперименты, исследования, экспертное знание | — |
| Релевантный | Связан с назначением приложения и нуждами пользователей | Точность цитирования критична для медицины, меньше — для лёгкого чат-бота |

Типовые измерения (перечень неполный): точность выполнения задачи, согласованность ответов на похожие входы, релевантность и связность, тон и стиль, сохранение приватности, использование контекста, задержка, цена. Большинству задач нужно несколько измерений сразу.

## Шаг 2. Собрать набор задач

- Объём старта. На практике 20–50 простых задач из реальных сбоев — отличное начало. Объём важнее качества — больше вопросов с автоматической оценкой лучше нескольких с ручной.
- Откуда брать. Начать с ручных проверок, которые уже делаются; трекер ошибок и очередь поддержки; сбои, о которых сообщили пользователи.
- Граничные случаи. Нерелевантные или отсутствующие входные данные; слишком длинный вход; для чатов — плохой, вредный или нерелевантный ввод; неоднозначные случаи, где и люди не сошлись бы.
- Баланс. Проверять и случаи, где поведение должно произойти, и где не должно; однобокий набор даёт однобокую оптимизацию (пример: проверяли только, ищет ли модель, когда должна, — получили модель, которая ищет почти всё).
- Однозначность. Хорошая задача — та, по которой два эксперта в предметной области независимо вынесут один и тот же вердикт «прошла» или «не прошла». Всё, что проверяет оценщик, должно быть ясно из условия задачи.
- Эталон. Для каждой задачи — эталонное решение, проходящее все оценщики; оно доказывает, что задача решаема, а оценщики настроены верно.

## Шаг 3. Выбрать оценщиков

| Тип | Методы | Сильные стороны | Слабые стороны |
|---|---|---|---|
| Код | Точное и шаблонное совпадение, бинарные тесты, статический анализ, проверка итогового состояния, проверка вызовов инструментов, анализ транскрипта | Быстро, дёшево, объективно, воспроизводимо | Ломается на допустимых вариациях, мало нюансов |
| Модель | Оценка по рубрике, утверждения на естественном языке, попарное сравнение, сравнение с эталоном, согласие нескольких судей | Гибко, масштабируется, ловит нюансы, годится для открытых задач | Недетерминированно, дороже кода, требует калибровки по людям |
| Человек | Экспертная оценка, выборочная проверка, A/B, согласие разметчиков | Эталонное качество, служит калибровкой для модели-оценщика | Дорого, медленно |

Оценивать то, что агент сделал, а не путь; для задач из нескольких частей — частичный зачёт; оценщики защищены от обходов.

Источники расходятся о порядке выбора:

- Одна позиция — выбирать самый быстрый, надёжный и масштабируемый метод — код; затем ручная оценка — самая гибкая и качественная, но медленная и дорогая, её по возможности избегать; затем оценка моделью — сначала проверить её надёжность, потом масштабировать.
- Другая — детерминированные оценщики — где возможно, модельные — где необходимо или нужна дополнительная гибкость, человеческие — взвешенно, для дополнительной проверки; модельных судей тщательно калибровать по оценкам экспертов-людей.

## Шаг 4. Настроить оценщика-модель

- Подробные ясные рубрики («The answer should always mention 'Acme Inc.' in the first sentence. If it does not, the answer is automatically graded as 'incorrect.'»); одному критерию может понадобиться несколько рубрик.
- Дискретный выход — только «correct» или «incorrect», или шкала 1–5.
- Оценщик с включённым мышлением, чтобы он рассуждал до оценки.
- Обычно лучше оценивать другой моделью, чем та, что сгенерировала оцениваемый ответ.
- Дать судье выход — например, отвечать «Unknown», если сведений не хватает; каждое измерение задачи — отдельным изолированным судьёй, а не одним на все.

## Шаг 5. Прогнать варианты

- Каждый прогон — с чистого окружения; общее состояние между прогонами (оставшиеся файлы, кэш, история git) искажает результат.
- Несколько прогонов на задачу: ответы модели различаются между запусками.
- Метрики: pass@k — вероятность хотя бы одного верного решения за k попыток; pass^k — вероятность, что верны все k. При трёх прогонах и успехе 75 процентов на прогон pass^3 ≈ 42 процента. pass^k важнее там, где пользователь ждёт надёжного поведения каждый раз.
- Сравнение вариантов промпта — на одном наборе задач и одних оценщиках. Итерировать промпты на подмножестве своих оценок или тест-кейсов и подтверждать на нём прирост полноты (recall) или F1. Отдельной официальной методики попарного сравнения текстов промптов нет.

## Шаг 6. Прочитать транскрипты

Понять, хорошо ли работают оценщики, можно только прочитав транскрипты и оценки многих прогонов.

- Провал должен выглядеть честным: ясно, что агент сделал не так. ЕСЛИ оценщик отверг допустимое решение → чинить оценщика, а не промпт.
- ЕСЛИ задача проваливается во всех прогонах → сначала проверить условие и оценщика: 0 процентов на многих прогонах чаще означает сломанную задачу, а не неспособную модель.
- Оценкам не верить на слово, пока кто-то не разобрал детали и не прочитал транскрипты.

## Шаг 7. Принять решение и поддерживать набор

- Вариант принимается, если он проходит критерии шага 1 на наборе шага 2, а транскрипты подтверждают, что разница — в поведении модели, а не в шуме оценки.
- Набор проверок возможностей насыщается — на 100 процентах он ловит регрессии, но не показывает улучшений; задачи с высоким прохождением переходят в регрессионный набор, а для роста нужны новые, более трудные.
- Сбои, найденные после внедрения, добавляются в набор задач.

## Скиллы и субагенты Claude Code

- Срабатывание и результат скилла меряются отдельно. Проверка — сравнение с базой: реалистичные запросы в свежей сессии со скиллом и с выключенным скиллом; свежая сессия нужна, потому что контекст написания скилла маскирует пробелы в инструкциях.
- Для скилла в плагине — `claude plugin eval` (прогоны с плагином и без, оценщики, порог для CI); для одного скилла — плагин skill-creator (тест-кейсы в `evals/evals.json`, изолированные прогоны субагентами, оценка, сравнение со скиллом и без, слепое A/B двух версий скилла, подбор описания по запросам «должен сработать» и «не должен»).
- Срабатывание по описанию: около 20 запросов — 8–10, где скилл должен сработать, и 8–10, где не должен; каждый запрос — несколько прогонов (например, по 3); запрос «должен сработать» проходит, если доля срабатываний выше порога (0.5 — разумное значение по умолчанию), «не должен» — если ниже; деление на обучающую (~60%) и проверочную (~40%) выборки, проверочная используется только для проверки, обобщаются ли улучшения.
- Для субагента в плагине надёжность делегирования меряется `claude plugin eval` на реалистичных запросах.

## Результат

- Критерии успеха.
- Набор задач с эталонами (файл или таблица).
- Оценщики и рубрики.
- Таблица результатов по вариантам: доля прохождения по каждому критерию, число прогонов, pass@k или pass^k.
- Выводы из транскриптов: какие провалы — от промпта, какие — от оценщика или задачи.
- Решение по варианту.

## Пример

**Вход:** два варианта системного промпта бота поддержки на Haiku 5.5; критерий — бот не даёт скидку вне правил и не отказывает в скидке, положенной по правилам.

**Ход:** 30 задач из логов поддержки — 15, где скидка положена, и 15, где нет (баланс шага 2); у каждой эталонный ответ. Оценщик кодом проверяет итоговое состояние (оформлена ли скидка), оценщик-модель по рубрике — тон, с выходом «Unknown». По 3 прогона на задачу, метрика pass^3. Чтение транскриптов показывает, что две «ошибки» второго варианта — эталон с устаревшей ценой; эталон исправлен, прогон повторён.

**Результат:** таблица pass^3 по двум критериям для обоих вариантов и решение по варианту.

Пример иллюстративный: числа условные.
