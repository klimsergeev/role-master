# Gemini: задание субагенту Gemini CLI

## Назначение

Техника текста задания, которое главный агент Gemini CLI передаёт субагенту: как задание доходит до субагента, что CLI к нему дописывает и что должно быть в самом задании. Официальных правил оформления задания в документации Gemini CLI нет; файл опирается на то, как CLI передаёт задание, и на описание поля задания, которое видит модель.

Файл не задаёт рамку вызова инструмента делегирования — какого субагента вызвать и какие поля вызова заполнить; он о содержании текста задания. Определение субагента — в [gemini-cli-artifacts.md](gemini-cli-artifacts.md).

Сверено 2026-11-11.

## Как задание доходит до субагента

- Субагент виден главному агенту как инструмент. Главный агент вызывает инструмент делегирования с двумя полями: `agent_name` — имя субагента и `prompt` — текст задания.
- Описание поля `prompt`, которое видит модель, требует полного и подробного запроса: весь контекст, предыстория, вопросы и ожидаемый формат вывода; краткие и неполные инструкции запрещены.
- У субагента из файла определения задание становится первым сообщением; если задания нет, подставляется стартовая фраза по умолчанию. Системный промпт из тела файла получает подстановки по входным полям.
- У встроенных субагентов свои поля задания: у исследователя кодовой базы — исчерпывающее описание конечной цели пользователя вместе с исходной целью, вопросами и дополнительным контекстом; у универсального субагента — сама задача или вопрос.

## Что субагент знает

- Свой системный промпт — тело файла определения.
- Содержимое файлов контекста (`GEMINI.md` всех уровней), рабочий каталог и структуру папок.
- Список навыков, если ему доступна их активация.
- Истории главного агента у него нет: у субагента отдельное окно контекста.
- Работает без пользователя: CLI дописывает ему, что он в неинтерактивном режиме и не может спрашивать пользователя, что пути к файлам — абсолютные.
- Итог возвращает одним вызовом завершения, в поле `result`, и должен следовать требованиям к формату из своих инструкций. В истории главного агента вся работа субагента сводится к этому одному итогу.

## Что должно быть в задании

| Часть задания | Что в ней |
|---|---|
| Цель | Что сделать и зачем |
| Контекст и предыстория | Что уже известно и решено, пути к файлам, тексты ошибок |
| Вопросы | На что именно субагент должен ответить |
| Формат результата | Что вернуть в итоге и в какой форме |

Задание самодостаточно: субагент не может уточнить у пользователя и не видит разговора главного агента.

## Как писать текст задания

- Задание называет, что именно должно оказаться в итоге и в какой форме: главный агент получит только этот итог.
- Пути, ошибки и принятые решения вписываются прямо в текст, а не упоминаются как «см. выше».
- Правила, которые субагент обязан соблюдать и которых нет в его системном промпте и в файлах контекста, повторяются в задании.
- Общие техники текста — [principles.md](principles.md).

## Когда главный агент делегирует

Встроенный системный промпт CLI велит главному агенту:

- передавать задачу субагенту с самой подходящей экспертизой, даже если его экспертиза шире задачи;
- делегировать пакетные задачи — больше чем на 3 файла или с повторяющимися шагами, — объёмный вывод и исследование методом проб;
- точечные задачи — простое чтение, правку одного файла, прямые вопросы на 1–2 хода — делать самому;
- не запускать за один ход несколько субагентов, если они меняют одни и те же файлы или ресурсы; параллельно — только независимые задачи (например, несколько исследований только на чтение) или по явной просьбе пользователя.

## Проверка задания перед отправкой

- [ ] Субагент выполнит задание, не зная ничего, кроме его текста, своего системного промпта и файлов контекста.
- [ ] Есть цель, контекст и предыстория, вопросы, формат результата.
- [ ] Пути, ошибки и решения вписаны в текст.
- [ ] Обязательные правила, которых нет у субагента, повторены.
- [ ] Ни одно действие не требует вопроса пользователю посреди работы.
- [ ] Параллельные задания не меняют одни и те же файлы.

## Пример

**Плохо:**

```text
Look into why the auth tests fail.
```

**Лучше:**

```text
Goal: find why the auth tests fail after the session-timeout change. Do not fix anything; the main agent will apply the fix.

Context:
- Failing tests: tests/auth/test_refresh.py::test_expired_session, tests/auth/test_refresh.py::test_refresh_rotation
- Error output in both: "AssertionError: expected 401, got 200".
- Decision already made: refresh tokens rotate on every use.
- Relevant code: /home/dev/app/src/auth/

Questions:
1. Which code path returns 200 for an expired session?
2. Which commit introduced it?

Result format: the root cause in two or three sentences, the file and line numbers involved, and the commit hash.
```

Пример иллюстративный: пути и ошибки условные.
