# GPT: параметры запроса, связанные с текстом промпта

## Назначение

Справочник параметров запроса к моделям GPT через API OpenAI, которые официальные материалы связывают с текстом промпта: текст заменяет параметр, параметр пробуется после правки текста, параметр определяет, куда попадает текст и сколько он действует, или изменение параметра меняет инструкции внутри контекста. Остальные параметры (цены, окна контекста, асинхронный вызов инструментов, правка задания по ходу через WebSocket и прочие) сюда не входят.

Значения сверены 2026-11-11.

## Поверхности

| Поверхность | Что это | Где различия |
|---|---|---|
| Responses API | Основной интерфейс; новые механизмы моделей GPT-6 (`configuration_update`, `phase`, многоагентный режим) описаны только для него | Разделы ниже |
| Chat Completions | Поддерживается всеми моделями GPT-6. Вызов инструментов у GPT-6 Astra, GPT-6.1 Sol и GPT-6.1 Terra — только через Responses API; у GPT-6 Sol и GPT-6 Luna вызов функций в Chat Completions — только при `reasoning_effort: "none"`. Встроенных инструментов OpenAI в Chat Completions нет, интеграцию инструментов пишут сами. Рассуждающие модели в Responses API работают лучше, чем в Chat Completions, при том же промпте | Разделы ниже, где названа поверхность |
| Codex | Агентная среда для программирования | [codex-artifacts.md](codex-artifacts.md) |
| ChatGPT | Пользовательские инструкции и инструкции проектов | [principles.md](principles.md), раздел «Инструкции ChatGPT» |

## Где живёт промпт

- Многоразовые объекты промптов выводятся из употребления, `v1/prompts` отключается 30.11.2026: рабочие промпты хранятся в коде приложения. Сборщики промптов — рядом с вызывающей функцией, динамические значения типизированы, до изменения рабочих промптов — фикстуры, тесты и проверки.
- Приложение закрепляют за конкретным снимком модели, чтобы поведение не менялось. У моделей GPT-6 снимок по умолчанию совпадает с идентификатором модели.

## Роли и `instructions`

- В Responses API параметр `instructions` равен developer-сообщению в начале `input` и имеет приоритет над промптом в `input`.
- `instructions` действует только в текущем запросе: при ведении беседы через `previous_response_id` инструкции прошлых ходов в контексте не окажутся — их передают заново.
- При вызове `/responses/compact` `instructions` не передают.
- Роль `system` в Responses API принимается; инструкции с ролью `developer` или `system` имеют приоритет над ролью `user`. Как модели GPT-6 обрабатывают сообщение `system`, присланное разработчиком, — не установлено.
- В Chat Completions всё — массив `messages`; для o1 и более новых моделей инструкции разработчика передаются ролью `developer`, она заменяет прежнюю `system`. Состояние беседы в Chat Completions ведётся вручную.
- Полномочия ролей и что класть в каждую — [principles.md](principles.md), раздел «Роли сообщений и полномочия».

## `reasoning.effort`

Уровень рассуждения: `reasoning.effort` в Responses API, `reasoning_effort` в Chat Completions.

| Модель | Уровни | По умолчанию |
|---|---|---|
| GPT-6 Astra | `low`, `medium`, `high`, `xhigh`, `max` | не установлено; в Codex — `low` |
| GPT-6.1 Sol | `low`, `medium`, `high`, `xhigh`, `max` | `medium` |
| GPT-6.1 Terra | `none`, `low`, `medium`, `high`, `xhigh`, `max` | `medium` |
| GPT-6 Luna | `none`, `low`, `medium`, `high`, `xhigh`, `max` | `medium` |
| GPT-6 Sol | `none`, `low`, `medium`, `high`, `xhigh`, `max` | `medium` |
| GPT-5.3-Codex | не установлено | не установлено |

- `none` у GPT-6 Astra и GPT-6.1 Sol возвращает ошибку HTTP 400 — вместо него `low`. При переходе с уровня `minimal` — начать с `low` и сравнить результаты.
- Назначение уровней: `none` — задачи, критичные к задержке, без рассуждения (голос, быстрый поиск, классификация); `low` — рутинные задачи: извлечение фактов, небольшие правки, черновики, поддержка; `medium` — настройка по умолчанию для большинства задач, работа со взвешенными решениями (планирование функции, сравнение вариантов); `high` — сложная отладка, углублённый анализ, тщательная проверка; `xhigh` и `max` — пробовать, где доступно, если `high` не хватает, и оставлять, только если оценки показывают явную пользу, оправдывающую время и стоимость. `max` — для самых трудных задач, где качество важнее всего, не повсеместно.
- Уровень — ручка тонкой настройки, а не основной способ вернуть качество: повышать после правки промпта, а не вместо неё ([principles.md](principles.md), раздел «Рассуждение»).
- Выбор уровня: на одинаковых входах менять только уровень, оставляя модель и входы неизменными, и оставлять самую лёгкую настройку, которая проходит порог качества.
- В Codex — начинать с уровня модели по умолчанию, снижать для простых задач и повышать для углублённого анализа.

## Резерв на рассуждение и вывод

Начиная эксперименты с моделями рассуждения, резервировать не меньше 25 000 токенов на рассуждение и вывод и подстраивать запас по фактическому расходу. Рассуждение невидимо, но занимает контекст и оплачивается как вывод.

## `reasoning.context` и сохранённое рассуждение

- По умолчанию `reasoning.context: all_turns` у GPT-6.1 Sol; у моделей, вышедших раньше, — `current_turn`; у GPT-6.1 Terra значение по умолчанию не установлено.
- Сохранённое рассуждение переносится только внутри одного семейства моделей.
- Сохранённое рассуждение — не всегда польза: устаревшее рассуждение добавляет токены, увеличивает задержку и привязывает модель к прежнему подходу.
- Сводки рассуждения доступны параметром `reasoning.summary`; сырые токены рассуждения не раскрываются.

## `text.verbosity`

- Значения `low`, `medium`, `high`; по умолчанию `medium`.
- Параметр задаёт общий диапазон длины на уровне системных инструкций; фактический ответ в этом диапазоне гибко следует промптам разработчика и пользователя. Это главный рычаг баланса краткости и полноты; требования конкретной задачи пишутся в промпте.
- Какие модели GPT-6 поддерживают параметр — прямо не сказано, не установлено. В Codex по умолчанию у моделей GPT-6 — `low`.

## Параметры сэмплирования

- При уровне рассуждения выше `none` убрать `temperature`, `top_p` и `top_logprobs`.
- GPT-6 Astra свои значения `temperature`, `top_p` и вероятности токенов не поддерживает.
- Принимают ли GPT-6.1 Terra и GPT-6 Luna `temperature` и `top_p` при `none` — не установлено.

## Ведение истории вручную

- Параметр `phase` ставится только у сообщений ассистента, не у сообщений пользователя: `commentary` — у промежуточных, `final_answer` — у итогового. Потерянный при восстановлении истории `phase` ведёт к тому, что предисловие принимается за итоговый ответ; у GPT-5.3-Codex — к значительному падению качества.
- Источники расходятся: одна позиция — `phase` описан для моделей GPT-5.x и GPT-6; другая — `phase` поддерживается только у GPT-5.3-Codex.
- Параллельные вызовы в истории: сначала все `function_call`, затем все `function_call_output` — так ближе к обучающему распределению.

## Префикс и смена настроек посреди беседы

- Начиная с новых передовых моделей, API отбрасывает элементы рассуждения, идущие после изменения префикса: модели приходится заново проделывать часть рассуждения, растут расход токенов, стоимость и задержка, может упасть качество.
- Изменение префикса — сокращение результата инструмента, переписывание developer-сообщения, замена старых ходов сводкой, изменение `tools`, `instructions`, `text.format`.
- Новые инструкции — новым developer-сообщением с просьбой игнорировать прежние и следовать новым ([principles.md](principles.md), раздел «Смена инструкций посреди беседы»). Для инструкций на один ход — явная точка кеша прямо перед последним developer-сообщением, чтобы повторно используемый префикс заканчивался до него.
- Смена схемы вывода и уровня рассуждения — элементом `configuration_update`, исходный `text.format` оставить без изменений; добавление инструментов — `additional_tools`; ограничение набора без изменения списка `tools` — `tool_choice` с `allowed_tools`.
- Длинные результаты инструментов, файлы и изображения сокращать до первой отправки модели.

## Кеширование и порядок

- Содержимое, повторяющееся из запроса в запрос, — в начале промпта и среди первых параметров тела запроса; динамический контекст пользователя — ближе к концу.
- Кешируется полный отрисованный контекст: инструкции OpenAI, developer-сообщения, определения инструментов, история. Параметры `tools`, `parallel_tool_calls`, `reasoning.effort`, `text.verbosity`, `text.format`, `context_management` превращаются в инструкции внутри этого контекста: их изменение меняет префикс.
- Кеширование не меняет того, как модель генерирует ответ.

## Компакция

- Серверная компакция — `context_management` с `compact_threshold`; отдельный вызов — `/responses/compact`. Сжатый элемент непрозрачен и не предназначен для чтения.
- Сжимать после крупных этапов, а не каждый ход; промпт после компакции держать функционально неизменным.

## Структурированный вывод

- Структурированный вывод вместо описания схемы в тексте промпта: проверка автоматическая, точность выше, жёсткие формулировки ради формата не нужны. Схема ответа переводит модель в программный режим ([principles.md](principles.md), раздел «Формат ответа»).
- Поля выводятся в порядке ключей схемы: поля рассуждения, которые должны идти до ответа, ставят в схеме раньше.
- Модель всегда пытается следовать схеме и при входе, совсем не подходящем к схеме, выдумывает: в промпте сказать, что возвращать в таком случае.
- Режим JSON требует явной инструкции генерировать JSON: без слова «JSON» в контексте API возвращает ошибку, а модель может выдавать бесконечный поток пробелов.
- Для функций рекомендован строгий режим: `strict: true`, все поля в `required`, `additionalProperties: false`. В Chat Completions функции по умолчанию нестрогие, в Responses API без поля `strict` делается попытка строгого режима.
- Схема задаётся `text.format` в Responses API и `response_format` в Chat Completions.
- Значения `description` и имена полей схемы — текст промпта: правила для них — [agents-and-tools.md](agents-and-tools.md), раздел «Описания функций и полей схем».
