# Grok: задание субагенту Grok Build

## Назначение

Техника текста задания, которое главный агент Grok Build передаёт субагенту: как задание доходит до субагента, что субагент знает и что должно быть в самом задании. Отдельные правила оформления задания у xAI — не установлено; файл опирается на то, как Grok Build передаёт задание, на описания инструмента и полей, которые видит модель, и на состав того, что субагент получает при запуске.

Файл не задаёт рамку вызова инструмента делегирования — какого субагента вызвать и какие поля вызова заполнить; поля описаны как то, что доходит до субагента. Определения субагентов и персон — в [grok-build-artifacts.md](grok-build-artifacts.md).

Значения сверены 2026-11-13. Текущая версия Grok Build на дату сверки — 1.0.77; сведения, известные только для версии 1.0.45, помечены этой версией.

## Как задание доходит до субагента

- Главный агент запускает субагента инструментом `spawn_subagent`; в версии 1.0.45 с ним сопоставлены и имена инструментов Claude Code `Agent` и `Task`. Субагенты включены по умолчанию и отключаются флагом `--no-subagents` или настройкой.
- В версии 1.0.45 текст задания — поле `prompt`: по описанию, которое видит модель, это полный текст задания, которое выполнит субагент. Обязательны `prompt` и `description` — короткое описание задачи в 3–5 слов.
- Остальные поля в версии 1.0.45:
  - `background` — запуск в фоне, по умолчанию `true`; результат забирается отдельным инструментом. Источники расходятся об имени поля: одна позиция — `background`, другая — `run_in_background`;
  - `isolation` — `none` (общая рабочая папка, по умолчанию) или `worktree` (отдельная рабочая копия git, правки в которой не затрагивают папку родителя до слияния);
  - `resume_from` — продолжить завершённого субагента того же сеанса;
  - `cwd` — рабочая папка субагента;
  - `model` — идентификатор модели из доступных; без него субагент берёт модель родителя. По описанию поля модель выбирают явно только по прямой просьбе пользователя; когда выбор модели отключён, поля в схеме нет;
  - `subagent_type` — появляется в схеме, только когда есть агенты из плагинов, проекта или пользователя, и перечисляет их с описаниями; встроенные типы в нём не перечислены, без поля субагент — `general-purpose`.
- В описании инструмента, которое видит главный агент (версия 1.0.45), сказано: субагенты получают сжатую версию инструкций проекта (`AGENTS.md`), поэтому подробные соглашения, нужные задаче, — правила сборки, шаблоны тестов — включаются прямо в задание; продолженный через `resume_from` субагент сохраняет стенограмму и состояние инструментов, поэтому ему описывают только то, что изменилось, не объясняя исходную задачу заново; результаты независимых субагентов главный агент обязан включить в работу, прежде чем её завершить.
- По завершении субагент возвращает родителю сводку; в версии 1.0.45 — одним сообщением.

## Что субагент знает

- Субагент — независимый дочерний сеанс со своим контекстом. Режим разрешений он наследует от родителя.
- Инструмента вопроса пользователю у субагента нет, инструмента рабочих процессов тоже; инструменты `web_search` и `x_search` родителя у него есть.
- В версии 1.0.45 системный промпт субагента — базовый шаблон с описанием среды (ОС, оболочка, рабочая папка, текущая дата) и текст своего типа (`general-purpose`, `explore`, `plan`) или тело определения своего агента.
- Инструкции проекта (`AGENTS.md` и совместимые файлы), если в определении агента не выключено `agentsMd`. В версии 1.0.45 источники расходятся дважды: о полноте — одна позиция: субагент получает сжатую версию, другая: полный блок, как основной агент; о месте — одна позиция: сообщением в обёртке `<system-reminder>` в начале разговора, другая: разделом в сборке системного промпта ([grok-build-artifacts.md](grok-build-artifacts.md), раздел «AGENTS.md и правила проекта»).
- В версии 1.0.45 инструкции персоны — сообщением `<system-reminder>`, если персона назначена через тип или роль.
- В версии 1.0.45 инструменты — по типу агента, у `general-purpose` без ограничений; уже подключённые MCP-серверы родителя и найденные родителем скиллы — по умолчанию.
- В версии 1.0.45 модель выбирается в порядке: явное указание при запуске, умолчание роли, умолчание персоны, модель родителя.
- В версии 1.0.45 разговор родителя субагенту не копируется. Продолженный через `resume_from` получает стенограмму, состояние инструментов и модель прежнего субагента, а системный промпт и инструменты строятся заново по текущему определению агента.
- В версии 1.0.45 субагент своих субагентов запустить не может: глубина вложенности — один.

## Что должно быть в задании

| Часть задания | Что в ней |
|---|---|
| Цель | Что сделать и зачем |
| Вводные | Всё из разговора, что нужно задаче: пути к файлам, тексты ошибок, найденное к этому моменту, решения пользователя — разговора родителя субагент не видит |
| Соглашения проекта | Правила из `AGENTS.md`, от которых зависит задача, — прямо в тексте: инструкции проекта могут дойти до субагента сжатыми |
| Критерии решений | По каким признакам субагент решает сам: спросить пользователя ему нечем |
| «Готово» и итог | Когда работа закончена и что вернуть: субагент отвечает родителю сводкой |

## Как писать текст задания

- Задание самодостаточно: пути, ошибки и решения вписываются прямо в текст, а не упоминаются как «см. выше».
- Задание продолженному через `resume_from` субагенту — только то, что изменилось с прошлого запуска; исходную задачу не пересказывать.
- Общие техники текста — [principles.md](principles.md).

## Проверка задания перед отправкой

- [ ] Субагент выполнит задание, не видя разговора родителя: всё нужное — в тексте.
- [ ] Соглашения проекта, от которых зависит задача, вписаны прямо в задание.
- [ ] Есть цель, вводные, критерии решений, «готово» и вид итога.
- [ ] Задание не рассчитывает на вопросы пользователю.
- [ ] Задание продолженному субагенту описывает только изменившееся.

## Пример

**Плохо:**

```text
Fix the flaky upload test.
```

**Лучше:**

```text
Goal: find out why tests/upload/test_resume.py::test_resume_after_timeout fails about one run in five, and fix the cause, not the symptom.

Context:
- The failures started after commit 3f2a9c1, which switched the upload client to chunked transfer.
- Error in the failing runs: "AssertionError: expected 3 chunks, got 2".
- The user decided: no retries or sleeps in tests.

Project rules that apply:
- Run tests with `make test-unit`, not plain pytest: the Makefile sets required environment variables.
- Keep changes inside src/upload/ and tests/upload/.

Decide yourself whether the bug is in the client or in the test fixture; if both, fix both.

Done when: the test passes 20 runs in a row with `make test-unit TEST=tests/upload/test_resume.py`.

Return in one message: the root cause in two or three sentences, the files you changed, and the result of the 20 runs.
```

Пример иллюстративный: пути, коммит и команды условные.
