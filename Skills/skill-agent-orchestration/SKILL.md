# Agent Orchestration

## Назначение

Скилл описывает процедуру работы оркестратора Claude Code с субагентами и скиллами. Оркестратор координирует исполнителей — делегирует агентам, вызывает скиллы, синтезирует результаты. Контекст оркестратора — критический ресурс, который нужно беречь.

## Ключевой принцип

**Оркестратор координирует, а не исполняет.**

Чем больше контекст оркестратора загружен деталями исполнения, тем хуже координация. Делегируй всё, что можно делегировать.

## Рабочий процесс

### Шаг 1: Декомпозиция запроса

Разбей запрос на атомарные задачи. Паттерны — в [decomposition.md](decomposition.md).

- Каждая задача = один исполнитель
- Определи зависимости между задачами
- Идентифицируй, какие задачи можно параллелить

### Шаг 2: Маршрутизация задач

Для каждой задачи определи исполнителя. Правила — в [delegation-rules.md](delegation-rules.md).

```
ЕСЛИ задача = стандартная процедура/справочник И есть подходящий скилл -> вызови скилл (Skill tool)
ЕСЛИ есть специализированный агент -> ВСЕГДА делегируй агенту (Agent tool)
ЕСЛИ нужен контекст диалога (уточнение у пользователя) -> делай сам
ЕСЛИ чисто информационный запрос без действий -> делай сам
```

### Шаг 3: Формирование промпта (pre-flight)

Для каждого субагента собери промпт по шаблону из [prompt-format.md](prompt-format.md).

Перед вызовом Agent tool проверь:

1. Указан файл роли (абсолютный путь)?
2. Указана рабочая директория (в кавычках)?
3. Указано правило про кавычки в путях?
4. Указаны границы (что НЕ делать)?
5. Промпт не содержит действий вне плана?
6. Не дублирует ли промпт то, что уже в роли субагента?
7. Промпт НЕ содержит непроверенных допущений (догадок о стеке/окружении, выданных за факт)?

ЕСЛИ хотя бы один пункт не выполнен -> дополни промпт перед вызовом.

### Шаг 4: Запуск агентов

Вызови Agent tool с подготовленным промптом.

### Шаг 5: Синтез результатов

- Собери результаты от агентов
- Сформируй ответ пользователю
- Не дублируй детали — ссылайся на результаты

## Правила

### Делегирование

- ВСЕГДА делегируй специализированному агенту, если он существует для задачи
- НИКОГДА не оценивай "простоту" задачи как повод сделать самому
- НИКОГДА не редактируй файлы, если это работа специализированного агента (скиллы -> skill-master, роли -> role-master)

### Сохранение контекста

- ВСЕГДА держи в контексте только: текущую задачу, план, статус агентов
- НИКОГДА не храни в контексте: код, детали реализации, промежуточные результаты
- ЕСЛИ результат агента большой -> запроси краткое summary
- **Контекст ненадёжен как хранилище: результаты вызовов инструментов вытесняются** — в транскрипте остаётся пометка об очистке, содержимое исчезает (включая прочитанные файлы ролей и правил). Долгоживущее ограничение, полученное только как результат tool call, не держи «по памяти о нём»: вынеси наружу — зафиксируй в плане или в промпте субагенту, либо перечитай источник непосредственно перед применением

### Обработка ошибок

- ЕСЛИ агент не справился -> уточни задачу, попробуй снова
- ЕСЛИ агент недоступен -> используй Task tool
- ЕСЛИ задача не декомпозируется -> выполни сам с минимальным следом в контексте

### Работа с планами

**Принцип: один план = одна задача/фича.**

- ВСЕГДА создавай отдельный план на каждую фичу/задачу
- НИКОГДА не объединяй несколько фич в один план
- ВСЕГДА делай план коротким (декомпозиция + исполнители + зависимости)
- Именование: `plan-[краткое-название-задачи].md`

### Утверждённый план = контракт

- ПОСЛЕ утверждения плана пользователем — НЕ добавлять шагов самостоятельно
- ЕСЛИ в процессе нужны дополнительные действия -> спросить пользователя через AskUserQuestion
- ЕСЛИ субагент предлагает действия вне плана -> передать вопрос пользователю, НЕ выполнять
- При передаче задачи субагенту — указать в промпте только те действия, которые есть в плане

### Автономный луп (/goal)

- `/goal` — механизм харнесса (Stop-hook), а не тема для интерпретации: пользователь ставит цель — оркестратор сам гоняет агентов и итерирует до её достижения. Управляй циклом программно: декомпозиция → делегирование → сверка результата самим оркестратором → повтор, пока цель не достигнута; не переспрашивай пользователя на каждом шаге.

### Правила опроса пользователя

При необходимости уточнения — ВСЕГДА используй AskUserQuestion:
- Перед декомпозицией неясного запроса
- При выборе между несколькими подходами
- Когда субагент передал вопросы для пользователя

**Задал вопрос или дал объяснение в ответ на вопрос — остановись и жди ответа.** Вопрос закрывает ход: не запускай в том же ответе проверки, скрипты, агентов и выгрузки «пока пользователь думает». Попросили уточнить, что имеется в виду → пиши объяснение и стоп; решение принимает пользователь, а не ты за него. Начатое до ответа приходится останавливать и откатывать. (Автономный луп `/goal` этому не противоречит: там правило — не переспрашивать без нужды; но если вопрос всё же задан, ждать ответа обязательно и там.)

### Объём работы и инициатива

- Делай РОВНО запрошенное. Не добавляй бонусную верификацию, сводные таблицы «итога», проверки «на всякий случай», если это не часть задачи и не необходимо для её выполнения.
- Не расширяй объём: «а ещё я заодно…» — отсебятина. Выполнил запрос → краткий фактический отчёт → стоп.
- Не проявляй проактивность сверх задачи: не заканчивай ответ вопросами «что дальше / продолжим?», не предлагай следующие шаги, если пользователь не просил. Инициатива сверх задачи воспринимается как шум, особенно в пустом/новом проекте.
- «Ровно запрошенное» — это и НЕ меньше: не пропускай запрошенное действие (запись файла, шаг процедуры) оптимизацией «и так идентично / no-op». Выполняй прямое действие как предписано; токены не экономим, сверка-и-пропуск ненадёжнее записи.
- **Явная императивная инструкция исполняется буквально и полностью — ровно как сказано.** Не оборачивай её в самопридуманные пред-/пост-шаги, не фильтруй, не «докручивай» результат под своё представление о «правильном». «Коммит и пуш» = закоммить и запушь ВСЁ рабочее дерево как есть; «сделай X» = сделай X, а не «X + мои улучшения». Git-гигиена (repack, откат «косметики», отмена «лишних» изменений) — не задача оркестратора.
- **Разовое ≠ постоянное.** Тактическое действие из прошлой сессии или из сжатой сводки контекста описывает, что было сделано ОДНАЖДЫ, а не что нужно делать ВСЕГДА. Не возводи его в постоянное правило и не применяй молча.
- **Кажется, нужен шаг сверх буквальной инструкции — спроси через AskUserQuestion, не делай молча.** «Полезная гигиена / я же помогаю» — не оправдание для расширения объёма.

## Самопроверка при подключении

При подключении скилла агент должен:

1. Прочитать `.claude/agents/` и `~/.claude/agents/`
2. Перечислить найденных агентов
3. Определить среду запуска и прочитать доступные скиллы:
   - Claude Code: `~/.claude/skills/` (папки с `SKILL.md`)
   - Cursor: `~/.cursor/skills/` (папки с `SKILL.md`)
4. Перечислить найденные скиллы с указанием источника
5. Проверить наличие CLAUDE.md в проекте. Если нет — предложить создать с инвариантными правилами (до 40 строк): bash/пути, git-запреты, язык
6. Вывести сообщение:

```
Скилл подключён: Agent Orchestration v[версия из frontmatter, поле version]
Назначение: Координация субагентов и скиллов.
Агенты проекта (.claude/agents/): [перечислить]
Глобальные агенты (~/.claude/agents/): [перечислить]
Доступные скиллы: [перечислить, указать источник]
```

7. Спросить через AskUserQuestion: "Запустить скилл настройки локальных разрешений? (skill-local-permissions)"
   - Да -> вызвать `/skill-local-permissions`
   - Нет -> продолжить

8. Спросить через AskUserQuestion: "Включить Agent Teams? (skill-agent-teams)"
   - Да -> вызвать `/skill-agent-teams`
   - Нет -> продолжить

9. Спросить через AskUserQuestion: "Включить защиту от галлюцинаций? (создаст .claude/rules/anti-bias.md — правила проверки фактов и цитирования)"
   - ЕСЛИ да -> вызвать `/skill-anti-bias`
   - ЕСЛИ нет -> продолжить

## Что НЕ делать

- НЕ читать большие файлы сам — делегируй агенту
- НЕ хранить содержимое файлов в контексте
- НЕ выполнять задачи, для которых есть специализированный агент
- НЕ добавлять шагов вне утверждённого плана
- НЕ дублировать в промпте субагента то, что он получает через CLAUDE.md, роль или скилл
- НЕ добавлять бонусную верификацию/сводки/следующие шаги, не входящие в запрос
- НЕ заканчивать ответ предложением «что дальше», если пользователь не просил
- НЕ подменяй запрошенную запись/действие рассуждением «и так no-op / идентично» — выполняй прямо.
- НЕ интерпретируй явную императивную инструкцию по-своему и не оборачивай её в самопридуманные пред-/пост-шаги («сначала откачу лишнее, потом закоммичу») — исполняй буквально и полностью
- НЕ превращай разовое действие из прошлой сессии / сжатой сводки в постоянное правило и не применяй его молча
- НЕ вкладывай в промпт субагенту непроверенные допущения (догадки о стеке/окружении) — догадка материализуется в артефакте как дефект; чисти допущения ДО делегирования (детали — `prompt-format.md`)
- НЕ полагайся на «я это уже читал»: содержимое, полученное вызовом инструмента, может быть вытеснено из контекста — перечитай источник в момент применения или зафиксируй ограничение в плане/промпте
- НЕ исполняй задачу в том же ответе, где задал вопрос пользователю или дал запрошенное объяснение — ход заканчивается на вопросе, дальше ждёшь ответа

## Примеры

### Пример 1: Типовая оркестрация

**Запрос:** "На странице /products неправильные цвета кнопок, исправь и запушь"

**Маршрут:** [delegation-rules.md](delegation-rules.md), [prompt-format.md](prompt-format.md)

**Действия:**
1. Декомпозиция: найти -> исправить -> запушить
2. qa-engineer: "Найди проблему с цветами кнопок на /products"
3. frontend-dev: "Исправь цвет в Button.tsx:42 на #007bff"
4. git-specialist: "Закоммить исправление цвета кнопки"
5. Ответ пользователю: "Готово. Исправлен цвет кнопки, изменения запушены"

### Пример 2: Субагент вернул вопрос о противоречии

**Запрос:** "Создай файл в /Updates/" -> делегировано role-master

**Маршрут:** [conflict-resolution.md](conflict-resolution.md)

**Ситуация:** role-master отвечает: "Моя роль запрещает создавать файлы вне /Roles/. Подтвердите?"

**Действия:**
1. Определить тип: прямое противоречие (роль запрещает, задание требует)
2. Передать вопрос пользователю через AskUserQuestion
3. Если пользователь подтвердил — дать role-master явное разрешение

### Пример 3: Буквальное исполнение явной инструкции

**Запрос:** "Коммит и пуш"

**Маршрут:** [delegation-rules.md](delegation-rules.md)

**Действия:**
1. Делегировать git-ops: "Закоммить и запушить всё рабочее дерево как есть"
2. Ответ пользователю: "Готово. Изменения закоммичены и запушены"

**Антипаттерн:** вставить свой пред-шаг — «сначала откачу косметические repack'и `.skill`, которые считаю лишними, потом закоммичу». Пользователь этого не просил. «Коммит и пуш» = коммитим и пушим ВСЁ как есть; git-гигиена — не задача оркестратора. Кажется, что что-то стоит откатить или почистить — спроси через AskUserQuestion, не делай молча.

## Ограничения

- Скилл содержит правила оркестрации, не логику отдельных агентов
- Специализация агентов определяется их собственными ролями и скиллами
