# Product Analytics Methods

## Назначение

Справочник методов продуктовой аналитики: воронки, сегментация, фреймворки метрик. Применяется для анализа конверсии, профилирования пользователей и построения системы KPI продукта.

## Принципы

1. **Метод под задачу** -- сначала определи бизнес-вопрос, потом выбери метод; не наоборот
2. **Данные до анализа** -- проверь доступность и качество данных прежде чем начинать анализ
3. **Actionable output** -- каждый анализ заканчивается рекомендацией, а не графиком
4. **Не дублировать** -- A/B-тесты покрыты skill-ab-test-analysis, когорты -- skill-cohort-analysis
5. **Сегменты живут** -- сегментация требует регулярного пересчёта; однократная сегментация устаревает

## Рабочий процесс

### Шаг 1: Определить бизнес-вопрос

Сформулируй вопрос в формате: "Как [действие] влияет на [метрику] для [сегмента]?"

| Тип вопроса | Метод | Файл |
|---|---|---|
| Где теряем пользователей? | Воронка | [funnel-analysis.md](funnel-analysis.md) |
| Кто наши лучшие/худшие пользователи? | Сегментация | [segmentation.md](segmentation.md) |
| Что измерять и как? | Фреймворк метрик | [kpi-framework.md](kpi-framework.md) |
| Работает ли изменение? | A/B-тест | skill-ab-test-analysis |
| Удерживаем ли пользователей? | Когортный анализ | skill-cohort-analysis |

### Шаг 2: Проверить данные

- Источник данных доступен (аналитика, БД, хранилище)
- События размечены корректно (нет пропусков в цепочке воронки)
- Правила включения и исключения записаны, а не подразумеваются: что считается целевым событием, входят ли возвраты, зачёты, повторы, тестовые и служебные записи. ЕСЛИ правило держится на здравом смысле исполнителя -> следующий пересчёт рассудит иначе, и метрика изменится молча
- Распределение любого флага или атрибута проверено ДО того, как строить на нём фильтр: флаг у 99.9% или у 0.1% записей фильтром не работает (пример: технический флаг «искусственное событие» стоял у 99.97% хитов -- фильтрация по нему оставляла 0.1% данных)
- Период данных достаточен (минимум 2-4 недели для стабильных паттернов). Прежде чем называть находку трендом, посмотри тот же показатель на горизонте в 3-6 раз длиннее: монотонный рост на 4 неделях часто оказывается колебанием внутри длинного коридора, и статистическая значимость на коротком окне этого не исключает
- Дата и время выгрузки зафиксированы вместе с числами. ЕСЛИ источник живой (события дописываются, приходят с задержкой, пересчитываются задним числом) -> опорные числа, снятые в начале работы, к концу перестают воспроизводиться, и без даты выгрузки это читается как ошибка в расчёте, а не как обновление данных
- Объём выборки достаточен для выбранного метода

### Шаг 3: Выполнить анализ

Загрузить файл процедуры из таблицы маршрутизации и следовать пошаговым инструкциям внутри файла.

### Шаг 4: Сформулировать результат

Каждый анализ завершается:
- **Находка** -- что обнаружено (факт с цифрами)
- **Причина** -- почему это происходит (гипотеза или подтверждённая причина)
- **Рекомендация** -- что делать (конкретное действие)
- **Приоритет** -- High / Medium / Low (на основе impact и effort)

**Представление долей:** доли, разбивающие целое (сегменты базы, распределение drop-off, структура выручки), после построчного округления не дают 100% -- типичный результат 101% или 99%; то же расхождение возникает у средних, которые обязаны сходиться с общей суммой. Правило: округли строки, затем отдай остаток крупнейшему слагаемому явно. Ручная правка одной цифры в тексте не решает -- расхождение вернётся при следующем пересчёте.

## Что НЕ делать

- Не дублировать A/B-тесты -- для экспериментов используй skill-ab-test-analysis
- Не дублировать когорты -- для retention используй skill-cohort-analysis
- Не строить воронку без определения цели (какой шаг считается конверсией)
- Не сегментировать на выборке < 1000 пользователей -- результат нестабилен
- Не выбирать North Star Metric "по ощущениям" -- использовать критерии из [kpi-framework.md](kpi-framework.md)
- Не игнорировать guardrail-метрики при оптимизации одной метрики
- Не представлять анализ без actionable-рекомендации

## Примеры

### Пример 1: Оптимизация воронки регистрации

**Запрос:** "Где отваливаются пользователи при регистрации в мобильном приложении?"

**Маршрут:** [funnel-analysis.md](funnel-analysis.md)

**Результат:** Воронка из 5 шагов (открытие -> ввод телефона -> подтверждение SMS -> заполнение профиля -> первая покупка). Drop-off 62% на шаге "подтверждение SMS". Рекомендация: упростить верификацию -- добавить auto-read SMS, сократить таймаут повторной отправки. Приоритет: High (impact на всех новых пользователей).

### Пример 2: Выбор KPI для нового продукта без исторических данных

**Запрос:** "Запускаем B2B SaaS для управления проектами. Какие метрики отслеживать?"

**Маршрут:** [kpi-framework.md](kpi-framework.md)

**Результат:** North Star -- Weekly Active Projects (отражает ценность для пользователя). Дерево метрик: NSM декомпозирована на sign-ups, activation rate (создание первого проекта), weekly engagement, expansion (приглашение коллег). Guardrails: churn rate, support tickets, page load time. AARRR-фреймворк адаптирован под B2B цикл с акцентом на Activation и Revenue.

### Пример 3: Сегментация для персонализации коммуникаций

**Запрос:** "Хотим персонализировать email-рассылки. Как разбить базу?"

**Маршрут:** [segmentation.md](segmentation.md), [funnel-analysis.md](funnel-analysis.md)

**Результат:** RFM-анализ выделил 5 сегментов (Champions, Loyal, At Risk, Hibernating, Lost). Для каждого сегмента -- профиль и стратегия коммуникации. Воронка email (доставка -> открытие -> клик -> конверсия) строится отдельно по сегментам для измерения эффекта персонализации.
