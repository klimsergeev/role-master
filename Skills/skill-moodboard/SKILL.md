# Moodboard

## Назначение

Процедурный скилл для двух типов задач: (1) создание визуальных мудбордов — структурированных документов с визуальным направлением проекта (палитра, типографика, лейаут, настроение); (2) создание тематических коллекций UI-паттернов — подборок примеров конкретного типа (FOMO, онбординг, empty states) с категоризацией, визуальными мокапами и do/don't. Поддерживает три режима сбора источников: из URL пользователя, поисковый (агент сам ищет по теме), fallback (по описанию настроения). Два формата выдачи: markdown-документ и Figma-фрейм с визуальными мокапами (через Figma MCP).

## Принципы

- **Мудборд — не код.** Результат скилла — markdown-документ и/или Figma-фрейм с визуальным направлением. Генерация Tailwind config, CSS-переменных, компонентов — задача других инструментов
- **Итеративность.** Мудборд создаётся через цикл «создать -> показать -> уточнить». Не пытаться угадать идеальный результат с первого раза
- **Конкретность.** Каждый элемент мудборда должен быть actionable: hex-коды вместо «тёплые тона», названия шрифтов вместо «современная типографика», описания паттернов вместо «красивые карточки»
- **Источники прежде всего.** Не выдумывать палитры и шрифты — извлекать из реальных источников (сайты, Figma, референсы пользователя). Если пользователь описал тему, но не дал URL — искать источники самостоятельно через WebSearch (поисковый режим). Fallback-режим с допущениями — только когда нет ни URL, ни темы для поиска

## Самопроверка при подключении

При активации скилла:
- ЕСЛИ в проекте уже есть файл мудборда (искать `*moodboard*` в директории, которую укажет пользователь) -> показать найденный файл, предложить обновить или создать новый
- ЕСЛИ мудборда нет -> спросить пользователя, куда сохранять результат (путь к директории)

## Рабочий процесс

### Шаг: Определить формат и путь сохранения

Спросить пользователя:
- **Формат выдачи:** markdown (по умолчанию), Figma-фрейм, или оба
- **Путь сохранения markdown:** если пользователь не указал — предложить `docs/moodboard.md` или корень проекта
- **Figma-ссылка:** если выбран Figma-формат — получить ссылку на страницу, куда создавать мудборд

ЕСЛИ пользователь явно указал формат (например, «делай борд в Figma», «создай мудборд в Figma на странице X») -> принять указанный формат, НЕ переспрашивать.
ЕСЛИ пользователь дал Figma-ссылку, но формулировка неоднозначна -> уточнить: только Figma, или markdown тоже нужен.

### Шаг: Собрать источники

Получить от пользователя источники вдохновения. Типы источников:
- URL сайтов
- Figma-ссылки (fileKey + nodeId)
- Скриншоты или описания
- Ключевые слова настроения

Определить режим по таблице из [moodboard-workflow.md](moodboard-workflow.md):
- ЕСЛИ пользователь дал конкретные URL -> основной поток
- ЕСЛИ пользователь описал тему / тип паттернов без конкретных URL (например, «собери примеры FOMO», «найди референсы онбординга») -> поисковый режим: агент самостоятельно находит источники через WebSearch, показывает пользователю для подтверждения, затем работает с ними как с обычными URL
- ЕСЛИ у пользователя только описание настроения, без темы для поиска -> fallback-режим

### Шаг: Извлечь элементы

Для каждого источника извлечь дизайн-элементы по справочнику [element-extraction.md](element-extraction.md):
- Цвета (hex-коды)
- Типографика (шрифты, веса, размеры)
- UI-паттерны (навигация, карточки, кнопки, лейауты)
- Настроение (ключевые слова, эмоции, характер бренда)

### Шаг: Создать черновик мудборда

Выбрать шаблон по таблице выбора из [moodboard-templates.md](moodboard-templates.md):
- Визуальное направление для проекта -> стандартный шаблон мудборда
- Коллекция паттернов одного типа -> шаблон тематической коллекции

Сгенерировать markdown-документ по выбранному шаблону. Сохранить в указанную директорию.

### Шаг: Ревью с пользователем

Показать мудборд и запросить обратную связь:
- Направление в целом
- Цвета — скорректировать?
- Типографика — предпочтения?
- Паттерны — добавить, убрать?
- Ключевые слова настроения — что не подходит?

### Шаг: Итерировать

По обратной связи обновить мудборд. Правила итерации:
- Фокусные изменения — не перекраивать всё сразу
- Объяснять, что изменилось и почему
- Максимум 3-4 итерации; если после четвёртой нет консенсуса — синтезировать обратную связь и предложить финальный вариант

### Шаг: Создать мудборд в Figma (если выбран Figma-формат)

ЕСЛИ пользователь выбрал Figma-выдачу — после создания и одобрения markdown-черновика (или параллельно с ним) создать мудборд-фрейм в Figma по процедуре из [figma-output.md](figma-output.md).

ЕСЛИ выбран только Figma без markdown — всё равно сначала сформировать данные мудборда (палитра, типографика, паттерны), затем создать фрейм.

ЕСЛИ задача — тематическая коллекция паттернов -> использовать структуру фрейма для тематической коллекции и создавать визуальные мокапы (бейджи, таймеры, нотификации) через `use_figma`, а не только текстовые описания. Процедура мокапов — в секции «Визуальные мокапы» в [figma-output.md](figma-output.md).

ЕСЛИ пользователь просит использовать skill-figma-mcp — загрузить его для справки по инструментам. Процедура мудборда (порядок вызовов, структура фрейма) берётся из [figma-output.md](figma-output.md).

### Шаг: Финализировать

При одобрении пользователя — оформить финальную версию мудборда по шаблону из [moodboard-templates.md](moodboard-templates.md). ЕСЛИ есть Figma-выдача — обновить фрейм в Figma по финальным данным. Проверить по чеклисту готовности.

## Что НЕ делать

- НЕ генерировать код (Tailwind config, CSS, компоненты) — мудборд это документ, не код
- НЕ выдумывать hex-коды и названия шрифтов — извлекать из реальных источников или явно указывать, что это предложение на основе описания пользователя
- НЕ пропускать ревью с пользователем — даже если «очевидно, что подходит»
- НЕ создавать мудборд без источников или описания настроения — сначала собрать хотя бы текстовое описание
- НЕ перезаписывать предыдущие версии мудборда без подтверждения — версионировать (v1, v2) или спросить
- НЕ делать более 4 итераций без синтеза — если пользователь не может определиться, предложить финальный вариант с обоснованием
- НЕ ссылаться на внешние скиллы (design-wizard, color-curator, typography-selector) — скилл автономный
- НЕ вызывать `use_figma` или `generate_figma_design` без предварительной загрузки соответствующего Figma Skill (`/figma-use`, `/figma-generate-design`) — это обязательное требование Figma MCP
- НЕ создавать мудборд в Figma через Desktop MCP — write-операции только через Remote

## Примеры

### Пример: Мудборд по URL сайтов (типовой сценарий)

**Запрос:** "Создай мудборд для лендинга. Вдохновение: stripe.com, linear.app"

**Маршрут:** [moodboard-workflow.md](moodboard-workflow.md), [element-extraction.md](element-extraction.md), [moodboard-templates.md](moodboard-templates.md)

**Результат:**
- Агент спрашивает путь сохранения
- WebFetch извлекает CSS/HTML обоих сайтов
- Агент формирует палитру, типографику, паттерны из реальных данных
- Создаёт черновик мудборда v1 по шаблону
- Показывает пользователю, получает обратную связь
- Итерирует до одобрения, оформляет финальную версию

### Пример: Мудборд без визуальных источников (edge-case)

**Запрос:** "Нужен мудборд для приложения трекера привычек. Хочу минимализм, спокойные тона, ощущение порядка."

**Маршрут:** [moodboard-workflow.md](moodboard-workflow.md) (fallback-режим), [element-extraction.md](element-extraction.md), [moodboard-templates.md](moodboard-templates.md)

**Результат:**
- Агент переходит в fallback-режим (нет URL/Figma)
- Формирует палитру на основе ключевых слов: минимализм -> нейтральные тона, ограниченная палитра; спокойные тона -> приглушённые, низкая насыщенность; порядок -> структурированная сетка, чёткая иерархия
- Все предложения явно помечены как «на основе описания, не из реального источника»
- Показывает пользователю для корректировки

### Пример: Мудборд из Figma-макета (чтение)

**Запрос:** "Вот ссылка на макет в Figma: figma.com/design/abc123/... — собери мудборд на основе этого"

**Маршрут:** [element-extraction.md](element-extraction.md), [moodboard-templates.md](moodboard-templates.md)

**Результат:**
- Агент использует Figma MCP: get_screenshot для визуального анализа, get_design_context для извлечения цветов и стилей
- Формирует мудборд из реальных данных макета
- Показывает пользователю для подтверждения

### Пример: Тематическая коллекция паттернов в Figma (поисковый режим)

**Запрос:** "Создай мудборд с примерами FOMO-плашек. Делай борд в Figma на странице figma.com/design/xyz789/...?node-id=123-456"

**Маршрут:** [moodboard-workflow.md](moodboard-workflow.md) (поисковый режим), [moodboard-templates.md](moodboard-templates.md) (тематическая коллекция), [figma-output.md](figma-output.md) (мокапы), [element-extraction.md](element-extraction.md)

**Результат:**
- Агент определяет: формат = Figma (явно указан), тип = тематическая коллекция (примеры паттернов, не визуальное направление), режим = поисковый (нет конкретных URL)
- WebSearch по запросам: "FOMO UI patterns examples", "urgency scarcity ecommerce design", "countdown timer low stock badge UI"
- Показывает 5-8 найденных источников пользователю для подтверждения
- WebFetch для каждого подтверждённого URL, извлекает конкретные паттерны
- Создаёт черновик по шаблону тематической коллекции: категории (scarcity, urgency, social proof), паттерны с визуальными характеристиками, do/don't
- Создаёт Figma-фрейм с визуальными мокапами (бейджи, таймеры, нотификации через `use_figma`) вместо текстовых описаний
- get_screenshot для проверки, показывает пользователю
- Итерирует по обратной связи

### Пример: Создание мудборда в Figma с URL-источниками (запись)

**Запрос:** "Создай мудборд в Figma на странице figma.com/design/xyz789/... Вдохновение: notion.so, linear.app"

**Маршрут:** [moodboard-workflow.md](moodboard-workflow.md), [element-extraction.md](element-extraction.md), [figma-output.md](figma-output.md)

**Результат:**
- Агент определяет: формат = Figma (явно указан), режим = основной поток (даны URL)
- Извлекает элементы из notion.so и linear.app через WebFetch
- Формирует палитру, типографику, паттерны
- Загружает `/figma-use` skill, создаёт мудборд-фрейм на указанной странице через `use_figma`
- Делает get_screenshot для проверки, показывает пользователю
- Итерирует по обратной связи

## Формат выдачи

После каждого шага агент выводит краткий статус:

```
Мудборд v[N] сохранён: [путь к файлу]
Источники: [количество]
Элементы: цвета [N], шрифты [N], паттерны [N], ключевые слова [N]
Статус: [черновик / на ревью / финализирован]
Формат: [markdown / Figma / markdown + Figma]
```

ЕСЛИ есть Figma-выдача — добавить:

```
Figma-фрейм: [ссылка на файл/страницу]
```

После финализации стандартного мудборда:

```
Мудборд финализирован: [путь к файлу]
Готовность к имплементации:
  - Цвета определены: [да/нет]
  - Шрифты выбраны: [да/нет]
  - Подход к лейауту задан: [да/нет]
  - Пользователь одобрил: [да/нет]
  - Figma-фрейм создан: [да/нет/не запрашивался]
```

После финализации тематической коллекции:

```
Коллекция паттернов финализирована: [путь к файлу]
Тема: [название]
Категории: [N] ([перечисление])
Паттернов: [N]
Визуальные мокапы: [N] (в Figma / не запрашивались)
Do/Don't: [да/нет]
Пользователь одобрил: [да/нет]
Figma-фрейм: [ссылка / не запрашивался]
```
