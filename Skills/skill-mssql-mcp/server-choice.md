# Выбор MCP-сервера к SQL Server

Файл отвечает на два вопроса: почему выбран именно этот сервер и что делать, если он не подойдёт.

**Провенанс — разделён явно, потому что смешивать нельзя:**

- **Проверено при написании скилла:** существование каждого репозитория, число звёзд, лицензия, дата последней записи в ветку, состав каталога `microsoft/mcp/servers`, содержимое пакета в NuGet, тег и дата образа в Docker Hub, а для выбранного сервера — весь исходный код версии 0.1.0.
- **Взято из предшествующего разбора инвентаря:** описания механизмов защиты у невыбранных серверов и результаты прогонов их валидаторов. Эти серверы при написании скилла не ставились и не запускались; такие утверждения помечены `[инвентарь]`.

Числа звёзд и даты протухают сами. Приведены по состоянию на дату из раздела «Срез данных» в [SKILL.md](SKILL.md); перед тем как на них опираться, проверьте заново.

---

## Почему «возьми официальный сервер Microsoft» — нерабочий совет

Первая мысль при подключении агента к SQL Server — найти вендорское решение. Его в привычном виде нет.

- **В каталоге `microsoft/mcp` сервера к SQL Server нет.** В каталоге `servers` репозитория `microsoft/mcp` лежат `Azure.Mcp.Server`, `Fabric.Mcp.Server` и `Template.Mcp.Server` — проверено обращением к содержимому репозитория. Ссылка каталога по теме SQL ведёт к Data API builder.
- **Прежний сэмпл `MssqlMcp` из `Azure-Samples/SQL-AI-samples` удалён.** Пути `MssqlMcp` в репозитории больше не существует (проверено: обращение к нему возвращает «Not Found»), последняя запись в ветку — начало июня 2026. Ссылки на него из статей и обсуждений ведут в никуда.
- **Вендорский путь, который существует, — SQL MCP Server в составе Data API builder** (`Azure/data-api-builder`, 1493★, живой репозиторий). Он устроен принципиально иначе: произвольного SQL там нет, работа идёт через заранее описанные сущности и RBAC.

Отсюда практический вывод: выбор идёт между сторонними проектами, и критерий выбора приходится формулировать самому.

## Критерий отбора

Из инвентаря в двенадцать репозиториев в кандидаты прошли четыре по одному признаку: **ограничение доступа не как обещание в README, а как механизм, который видно в коде или в составе инструментов.**

Остальные восемь отсеяны — таблица в конце файла.

## Четыре кандидата

### A — `codegiveness/mssql-mcp`

C#/.NET, поставка через npm, NuGet и Docker, транспорт stdio, лицензия MIT.

Единственный из всех, у кого есть настоящий разбор T-SQL: валидатор строится на синтаксическом дереве, а не на списке запрещённых слов. Read-only по умолчанию, произвольный `SELECT` разрешён, обобщённые табличные выражения проходят; есть встроенная предстартовая проверка подключения `--validate` [инвентарь].

Что видно без прогона: **0★, репозиторий заведён недавно, версия 1.0.0 не выпущена.** Ни одного стороннего пользователя. Качество валидатора обещано кодом, но не эксплуатировалось никем, кроме автора.

### B — `ConnorBritain/mssql-mcp-reader`

Node, поставка через npm, 5★, MIT.

Гарантия структурная, и это её сильная сторона: **инструментов записи в сервере просто нет** — нечего включать и нечего забыть выключить.

Проблема в другом: валидатор построен на списках запрещённых подстрок и **отклоняет нормальные запросы**. Прогоном воспроизведены отказы на обобщённых табличных выражениях и на `DB_NAME()` [инвентарь]. Дополнительно сервер сам подставляет ограничение в тысячу строк.

### C — `aadversteeg/mssqlclient-mcp-server` — выбран

C#/.NET 10, официальный MCP C# SDK, транспорт stdio, лицензия MIT. 41★, 12 форков, ноль открытых issues (единственная запись в счётчике GitHub — pull request), последняя запись в ветку — июнь 2026. Самый обкатанный из четырёх.

Установка двумя путями без npm: пакет `Ave.McpServer.MsSqlClient` в NuGet (актуальная версия 0.1.0, три опубликованных версии, около 1,8 тыс. загрузок) либо образ `aadversteeg/mssqlclient-mcp-server` в Docker Hub (тег `latest` совпадает с `0.1.0`, около 11,5 тыс. загрузок).

Механизм ограничения — не валидатор, а **гейт на регистрации инструментов**: выполнение SQL по умолчанию не зарегистрировано. При включении флага валидации нет никакой. Ячейки по умолчанию режутся до 40 символов.

Всё, что касается C, в этом скилле проверено по исходникам версии 0.1.0, а не пересказано.

### D — SQL MCP Server в составе Data API builder

Вендорский путь Microsoft, `Azure/data-api-builder`, 1493★, MIT, активная разработка.

Произвольного SQL нет **принципиально**: агент работает с заранее описанными сущностями, доступ регулируется RBAC, DML-инструменты отключаются конфигурацией [инвентарь]. Требует описания сущностей и запуска через собственный CLI.

## Почему выбран C

1. **A не вызывает доверия по зрелости.** Ноль звёзд, версия 1.0.0 не выпущена, ни одного стороннего пользователя. Валидатор на синтаксическом дереве — лучший механизм в матрице, но проверен только автором.
2. **Валидатор B отклоняет нормальные запросы.** Для разведочной аналитики — а это основной сценарий — ложный отказ бьёт в главный сценарий, а не в краевой.
3. **D отпадает по устройству.** Курированный набор сущностей несовместим с задачей «иди посмотри, что в базе».
4. **Главный минус C снимается настройкой.** Усечение до 40 символов — значение параметра `MaxCellOutputLength`, а не свойство сервера: `0` выключает обрезку целиком.
5. **C — единственный, у кого зрелость и произвольный `SELECT` есть одновременно.**

### Чем C заменяет валидацию

Гейтом на регистрации инструментов. Четыре флага — `EnableExecuteQuery`, `EnableExecuteStoredProcedure`, `EnableStartQuery`, `EnableStartStoredProcedure` — по умолчанию `false`; с версии 0.0.5 это заявленное изменение поведения: «Query and stored procedure execution tools are now **disabled by default** for security» [README].

Достоинство механизма — проверяемость снаружи: выключенный инструмент не попадает в `tools/list`, и это видно счётчиком в `/mcp`, а не чтением README. Раскладка — в [setup.md](setup.md).

### Честная цена решения

Три пункта, каждый из которых нужно знать до, а не после.

1. **Валидации SQL нет вовсе.** При `EnableExecuteQuery=true` через `execute_query` проходит любой T-SQL; единственная проверка — что строка запроса не пуста [код 0.1.0]. Слой сервера отвечает на вопрос «какие операции доступны», а не «безопасен ли этот запрос». Что позволено сделать через доступную операцию, определяют права учётной записи — сервер их не дублирует и не заменяет. Механизмы ограничения записи — в [read-only-layers.md](read-only-layers.md).
2. **Предстартовой проверки нет.** Ни ключа `--validate`, ни инструмента `test_connection`. К СУБД сервер подключается только при первом вызове инструмента, поэтому статус `✔ Connected` не означает, что база доступна. Проба канала собирается вручную — [failures.md](failures.md).
3. **Конфигурация по умолчанию — ловушка.** Сорок символов на ячейку: длинное значение обрезается многоточием и выглядит как данные. Обратная сторона выключенного усечения — весь объём едет в порог вывода Claude Code. Обе стороны разобраны в [limits.md](limits.md).

Четвёртое, что выяснилось уже при чтении кода и в матрицу инвентаря не входило: **README сервера местами расходится с кодом.** Инструменты сессий и таймаутов README относит к доступным всегда, а код регистрирует их только при включённых фоновых сессиях; параметр `ConnectionTimeoutSeconds` объявлен, но к соединению не применяется. Оба расхождения разобраны в [setup.md](setup.md). Прав в таких случаях код.

## Как сменить сервер

Скилл написан так, чтобы смена стоила правки двух файлов.

| Что придётся переписать | Почему |
|---|---|
| [setup.md](setup.md) — целиком | Способ установки, имена переменных, состав флагов и таблица гейта у каждого сервера свои |
| Этот файл — раздел «Почему выбран C» | Меняется решение и его цена |
| [failures.md](failures.md) — дословные тексты ошибок | Тексты порождаются конкретной реализацией |
| [limits.md](limits.md) — раздел про обрезку на стороне сервера | Пороги и их механика у каждого свои. Пороги Claude Code не меняются |

Что останется без правок:

- [connection-string.md](connection-string.md) — при условии, что новый сервер тоже на `Microsoft.Data.SqlClient`. Для Node- и Python-серверов меняются умолчания шифрования и таймаутов: справочная таблица драйверов в конце того файла для этого и написана.
- [read-only-layers.md](read-only-layers.md) — механизмы сформулированы через свойства, а не через имена инструментов конкретного сервера. Механизм A (права) не зависит от сервера вообще; механизм C (`permissions`) — только от имени сервера в конфигурации; механизм B переписывается под новый набор переключателей.
- Пороги вывода и таймауты Claude Code в [limits.md](limits.md).

Порядок действий при смене:

1. Определить, что сломалось в текущем сервере: механизм разошёлся с описанием, установка невозможна, поведение неприемлемо.
2. Выбрать по матрице замену: **A** — если нужна валидация и появилась зрелость; **B** — если нужна структурная гарантия вместо правовой и ложные отказы терпимы; **D** — если задача сменилась с разведки на курированный набор сущностей.
3. Проверить механизмы нового сервера **по его коду**, а не по README: расхождение README с кодом обнаружилось даже у самого обкатанного из четырёх.
4. Переписать [setup.md](setup.md), обновить этот файл и дословные тексты в [failures.md](failures.md).
