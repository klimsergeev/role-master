# Что ограничивает один вызов

Файл отвечает на два вопроса: почему результат пришёл усечённым и как сформулировать запрос, чтобы этого не случилось.

Главный вывод, ради которого стоит прочитать первый раздел: **режут в трёх местах, по трём разным правилам, и только одно из трёх сообщает о себе.**

---

## Три обрезки, которые легко перепутать

| Что режется | Кто режет | Чем управляется | Видно ли это |
|---|---|---|---|
| Значение внутри ячейки | сервер | `MaxCellOutputLength`, умолчание 40 | Многоточие в конце значения — неотличимо от данных |
| Весь ответ целиком | Claude Code | `MAX_MCP_OUTPUT_TOKENS`, умолчание 25 000 токенов | Ответ обрывается или заменяется ссылкой на файл |
| Число строк | **никто** | — | — |

Третья строка — не опечатка. **Лимита строк у сервера нет.** Он не подставляет `TOP n` в ваш запрос и не режет результат по числу записей: единственное вхождение `TOP` в коде — в детекторе возможностей СУБД, к пользовательским запросам отношения не имеющем [код 0.1.0]. Поэтому `SELECT *` по большой таблице выполнится целиком, целиком попадёт в память процесса сервера и целиком поедет в Claude Code — где его оборвёт порог вывода.

---

## Обрезка на стороне сервера: как она устроена на самом деле

Формулировка «40 символов на ячейку» описывает результат неточно. Механика такая [код 0.1.0: `AsyncDataReaderExtensions.ToToolResult`]:

1. Ширина каждой колонки берётся равной длине её имени.
2. Затем читаются **все** строки результата, и ширина колонки увеличивается до длины самого длинного значения в ней.
3. Если `MaxCellOutputLength` больше нуля, ширина ограничивается сверху этим значением.
4. При выводе значение обрезается, только если оно длиннее итоговой ширины колонки: остаётся `ширина − 3` символа плюс `...`.

Что из этого следует:

- **Обрезка срабатывает не всегда.** Если все значения в колонке короче лимита, ширина колонки меньше лимита, и не обрезается ничего.
- **При умолчании 40 от значения остаётся 37 символов** и три точки. Итоговая длина ровно 40.
- **Обрезка идёт по символам .NET (UTF-16), а не по байтам и не по графемам.** Для кириллицы это то же, что символы; для эмодзи и других знаков вне базовой плоскости граница может пройти по суррогатной паре.
- **Имя колонки не обрезается никогда** — оно только дополняется пробелами. Колонка с именем длиннее лимита ломает выравнивание таблицы: строка-разделитель окажется короче заголовка.
- **`NULL` печатается словом `NULL`** и на выводе неотличим от строкового значения `'NULL'` [код 0.1.0].

### Как выключить и как переопределить

| Способ | Область действия |
|---|---|
| `DatabaseConfiguration__MaxCellOutputLength=0` | Все вызовы; обрезка выключена целиком |
| Параметр вызова `maxCellOutputLength` у `execute_query` | Только этот вызов; перекрывает конфигурацию |

Второй способ — рабочий приём для широких выборок: держать умолчание для повседневных запросов и поднимать лимит точечно там, где нужны полные значения.

Узнать текущее значение, не читая конфигурацию, можно прямо из описания инструмента: в текст описания `execute_query` подставляется фактическое значение через плейсхолдер `{MaxCellOutputLength}` [код 0.1.0: `DescriptionPlaceholderResolver`]. То есть описание инструмента в `/mcp` показывает действующий лимит.

**Цена выключения не нулевая.** При `MaxCellOutputLength=0` весь объём едет в Claude Code без сокращения, и роль ограничителя целиком переходит к порогу вывода — который режет иначе и хуже (см. ниже).

**Edge-case конфигурации.** Значения `MaxCellOutputLength` = 1 и 2 опасны: при обрезке вычисляется `ширина − 3`, и на такой ширине выражение уходит в минус. По коду это даёт исключение при форматировании, которое будет перехвачено общим обработчиком и вернётся пользователю как `Error: SQL error while executing query: …` — то есть ошибка форматирования доложится как ошибка SQL [код 0.1.0; вживую не проверено]. Осмысленные значения — `0` либо число заметно больше трёх.

## Обрезка на стороне Claude Code

Пороги не зависят от сервера [док CC]:

- **Предупреждение** при выводе инструмента свыше **10 000 токенов**. Порог фиксирован: «the warning threshold is fixed».
- **Жёсткий лимит по умолчанию — 25 000 токенов**, меняется переменной окружения `MAX_MCP_OUTPUT_TOKENS`:

```bash
export MAX_MCP_OUTPUT_TOKENS=50000
claude
```

- Результат сверх порога **сохраняется на диск**, а в беседу подставляется ссылка на файл.
- Сервер может поднять собственный порог аннотацией `_meta["anthropic/maxResultSizeChars"]` в ответе `tools/list` — «Claude Code raises that tool's threshold to the annotated value, up to a hard ceiling of 500,000 characters» [док CC]. **Выбранный сервер такой аннотации не выставляет**: поиск по исходникам версии 0.1.0 не находит ни `_meta`, ни `anthropic` [код 0.1.0]. Значит на него действует общий порог `MAX_MCP_OUTPUT_TOKENS`.

Ключевое отличие от серверной обрезки: **Claude Code режет ответ целиком и в произвольном месте** — то есть посреди строки таблицы. Со стороны агента это выглядит как полный ответ, если не заметить отсутствия завершающей строки `Total rows: N`, которую сервер печатает всегда.

Отсюда практическое правило: **наличие строки `Total rows:` — признак того, что таблица доехала полностью.** Её отсутствие означает обрыв.

## Границы одного вызова: соединение, `SET`, транзакции

Факт, из которого вытекает несколько следствий сразу: **каждый вызов `execute_query` открывает собственное соединение и закрывает его после чтения результата** [код 0.1.0: `DatabaseService.ExecuteQueryAsync`, чтение через `CommandBehavior.CloseConnection`].

| Следствие | Что это значит |
|---|---|
| Сессия СУБД не переживает вызов | `SET`-операторы, временные таблицы `#tmp`, `USE`, уровень изоляции, установленные в одном вызове, во втором уже не действуют |
| Транзакция должна открыться и закрыться внутри одного вызова | `BEGIN TRAN` в одном вызове и `ROLLBACK` в другом не работают: незакрытая транзакция откатится при закрытии соединения, а второй вызов не найдёт, что откатывать. Приём с обёрткой — в [read-only-layers.md](read-only-layers.md) |
| Запрос — один батч | `GO` не является оператором T-SQL, это разделитель клиентских инструментов; сюда его слать не нужно |

**Про `SET`-операторы отдельно, потому что канал в них вмешивается.** Перед каждым запросом сервер сам выполняет `SET STATISTICS TIME ON` отдельной командой; при параметрах вызова `includeIoStats` и `includeExecutionPlan` к ней добавляются `SET STATISTICS IO ON` и `SET STATISTICS XML ON` [код 0.1.0]. Поэтому:

- Свои `SET`-операторы канал не фильтрует и не отклоняет — они уходят в СУБД как часть вашего батча. Но действуют они только до конца этого вызова.
- **План выполнения запрашивается параметром вызова, а не руками.** `includeExecutionPlan: true` даёт фактический XML-план: сервер включает `SET STATISTICS XML ON` и вылавливает из дополнительного набора результатов значение, начинающееся с `<ShowPlanXML` [код 0.1.0]. Ручной `SET SHOWPLAN_XML ON` в том же батче — другой механизм с другими требованиями к структуре батча со стороны СУБД; его семантика относится к языку и разобрана в `skill-tsql`.
- Статистика по времени приезжает всегда: к результату приписана строка `Execution time: <N>ms (server: <N>ms, CPU: <N>ms)`.

## Бюджет времени

Пять потолков, от ближнего к дальнему:

| Потолок | Умолчание | Чей | Чем меняется |
|---|---|---|---|
| Таймаут SQL-операции | 30 с | сервер, `DefaultCommandTimeoutSeconds` | Параметром вызова `timeoutSeconds`; на лету — `set_command_timeout` (доступен только при включённых сессиях), диапазон 1–3600 с [README] |
| Бюджет вызова инструмента | 120 с | сервер, `TotalToolCallTimeoutSeconds` | Конфигурацией; `null` отключает |
| Автоперевод вызова в фон | 2 минуты | Claude Code | `CLAUDE_CODE_MCP_AUTO_BACKGROUND_MS`; `0` выключает |
| Idle-таймаут stdio | 30 минут | Claude Code | `CLAUDE_CODE_MCP_TOOL_IDLE_TIMEOUT` в миллисекундах; `0` отключает проверку |
| Жёсткий предел вызова | ~28 часов, если не задано | Claude Code | Поле `timeout` у сервера в конфигурации либо `MCP_TOOL_TIMEOUT` |

Тонкости, которые меняют арифметику:

- **Таймаут команды живёт внутри бюджета вызова.** Эффективное значение — минимум из настроенного и остатка бюджета, но не меньше секунды [код 0.1.0]. Поднимать `DefaultCommandTimeoutSeconds` выше `TotalToolCallTimeoutSeconds` бессмысленно.
- **У stdio-серверов нет таймера на отдельный запрос**: «Stdio and WebSocket servers have no per-request timer» [док CC]. Ограничивают только календарный предел и простой.
- **Значения `timeout` меньше 1000 игнорируются**: «Values below 1000 are ignored and fall through to `MCP_TOOL_TIMEOUT`, or to its default of about 28 hours when that variable is unset» [док CC]. Поле задаётся в миллисекундах.
- **Автоперевод в фон не действует на вызовы из субагентов**: «Calls from subagents; Claude Code backgrounds only main-conversation calls» [док CC]. В субагенте длинный вызов блокирует работу до срабатывания одного из потолков.
- **`MCP_TIMEOUT` — про другое.** Это таймаут запуска сервера, а не выполнения инструмента [док CC].

Что делать с запросом, который в бюджет не влезает:

1. Переписать запрос — почти всегда дешевле остального.
2. Поднять `timeoutSeconds` на конкретный вызов, если запрос заведомо тяжёлый и результат нужен целиком.
3. Уйти в фоновую сессию, если включён `EnableStartQuery`: `start_query` → `get_session_status` → `get_session_results`. По README эти инструменты «bypass the `TotalToolCallTimeoutSeconds` limit and run in the background».

## Фоновые сессии: другой набор ограничений

Путь через сессии меняет не только время, но и форму результата. Это не «то же самое, только асинхронно».

| | `execute_query` | `start_query` + `get_session_results` |
|---|---|---|
| Формат | выровненная текстовая таблица | JSON, внутри поле `results` со строкой в формате TSV |
| Обрезка ячеек | применяется | **не применяется вообще** — `MaxCellOutputLength` к сессиям не относится [код 0.1.0] |
| Лимит строк | нет | параметр `maxRows` у `get_session_results` |
| Где живёт результат | формируется и сразу отдаётся | накапливается в памяти процесса сервера до уборки |
| Бюджет вызова | действует | обходится: работа идёт в фоне |

Практические следствия:

- **Фоновая сессия — способ получить значения без обрезки**, даже когда `MaxCellOutputLength` оставлен по умолчанию. Цена — весь объём поедет в порог Claude Code без всякого сокращения.
- **`maxRows` режет текст по переводам строк**, а не по записям: `lines.Take(maxRows + 1)` после разбиения по `\n` [код 0.1.0]. Значение с переводом строки внутри сдвинет счёт.
- **Формат TSV не экранируется.** Значения соединяются табуляцией; таб или перевод строки в данных ломают структуру.
- **Незавершённая сессия отдаёт частичный результат.** Накопленное сохраняется в сессию каждые 1000 строк [код 0.1.0], поэтому до завершения видно количество строк, кратное тысяче.
- **Результат держится в памяти** до уборки — по умолчанию до часа после завершения, при потолке в 10 одновременных сессий.

## Как формулировать запрос, чтобы не упереться

Тактика простая: ограничивать объём на стороне СУБД, а не надеяться на то, что кто-нибудь обрежет по дороге.

1. **Сначала оценить размер**, потом выбирать. `COUNT(*)` до `SELECT` стоит один вызов и снимает вопрос.
2. **Агрегат вместо выгрузки.** Вопросы вида «сколько», «какое распределение», «топ по значению» решаются на стороне СУБД и возвращают десятки строк вместо десятков тысяч.
3. **Ограничение выборки и постраничное чтение** — обязательны для разведки по незнакомой таблице.
4. **Не запрашивать колонки, которые не нужны.** Одна колонка `NVARCHAR(MAX)` способна съесть весь бюджет вывода.
5. **Поднимать `maxCellOutputLength` точечно**, на тот вызов, где нужны полные значения, а не глобально.

Синтаксис ограничения выборки и приёмы пагинации в T-SQL — в `skill-tsql`: здесь числовые пороги канала, там язык запроса.
