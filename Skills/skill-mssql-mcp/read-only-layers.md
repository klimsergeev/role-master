# Как ограничить запись, если это нужно

**Файл опциональный.** Он нужен не всякому подключению: канал работает и там, где учётная запись пишущая. Скилл не постулирует read-only и не считает ограничение записи обязательной частью настройки — что позволено подключению, решает владелец базы.

Читайте этот файл, когда решение «запись должна быть закрыта» уже принято и нужно понять, чем именно её закрывать и что каждый вариант стоит.

---

## Честная рамка: между агентом и СУБД нет фильтра SQL

Первое, что нужно принять до выбора механизма: **ни один из описанных ниже слоёв не читает ваш SQL.**

У выбранного сервера валидации запросов нет вовсе. Единственная проверка перед отправкой в СУБД — что строка запроса не пуста: `if (string.IsNullOrWhiteSpace(query)) return "Error: Query cannot be empty";` [код 0.1.0: `ExecuteQueryTool`]. Поиск по исходникам версии 0.1.0 не находит ни чёрных списков, ни разбора текста запроса, ни проверки «это SELECT или нет» — ничего между строкой запроса и `SqlCommand`.

Из этого следует граница ответственности, которую скилл не размывает:

- **Слой сервера** отвечает на вопрос «какие операции вообще доступны», а не «безопасен ли этот запрос».
- **Что именно позволено сделать через доступную операцию**, определяют права учётной записи в СУБД.

И отдельная граница, важная именно здесь: канал не разбирает семантику T-SQL и не отличает запрос, который читает, от запроса, который только выглядит читающим. Перечень конструкций, попадающих в эту категорию, — в скилле `skill-tsql`; здесь не воспроизводится ни одной позиции, потому что повторять семантику языка в описании канала — верный способ развести две расходящиеся версии одного перечня.

Механизмы ниже либо сужают набор доступных операций, либо ограничивают конкретного клиента, либо закрывают права. Их берут по одному, по два или не берут вовсе.

## Механизм A — права учётной записи

Единственный механизм, который действует независимо от клиента, от конфигурации сервера MCP и от того, кто и чем подключился. Настраивается на стороне СУБД её владельцем.

### Что делает

Базовая пара фиксированных ролей базы данных [док MS]:

| Роль | Что означает | Какие права стоят за ней |
|---|---|---|
| `db_datareader` | «Members of the **db_datareader** fixed database role can read all data from all user tables and views» | `GRANT SELECT ON DATABASE::<database-name>` |
| `db_denydatawriter` | «Members of the **db_denydatawriter** fixed database role can't add, modify, or delete any data in the user tables within a database» | `DENY INSERT ON DATABASE::<database-name>`, `DENY UPDATE …`, `DENY DELETE …` |

`DENY` побеждает `GRANT`, поэтому членство в `db_denydatawriter` перекрывает выданные где-то ещё права на запись. Исключение: `DENY` не действует на владельцев объектов и членов `sysadmin`.

Здесь описано, **что физически запрещено**. Обратная сторона — что именно увидит запрос под такими правами: какие объекты пропадут из системных представлений, где вместо отказа придёт пустой результат — это семантика языка, и она в скилле `skill-tsql`.

Точечная альтернатива ролям — адресный `DENY` на конкретные таблицы или схемы. Она гибче, но требует поддержки: таблица, созданная завтра, под старый `DENY` не попадёт, а `DENY … ON DATABASE::` покрывает и её.

### Чего механизм A не покрывает

Три дыры, каждая из которых оставляет запись возможной при формально «запрещающей записи» роли.

**1. DDL.** `db_denydatawriter` запрещает `INSERT`, `UPDATE`, `DELETE` — и только их. `CREATE TABLE`, `ALTER TABLE`, `DROP TABLE` в этот список не входят: они живут в правах `db_ddladmin` и отдельных `CREATE …`/`ALTER …` [док MS]. Учётная запись, состоящая одновременно в `db_denydatawriter` и `db_ddladmin`, не может изменить строку, но может удалить таблицу целиком.

**2. `TRUNCATE TABLE`.** Формально это не DML: «The minimum permission required is `ALTER` on *table_name*. `TRUNCATE TABLE` permissions default to the table owner, members of the `sysadmin` fixed server role, and the `db_owner` and `db_ddladmin` fixed database roles, and aren't transferable» [док MS]. То есть `DENY DELETE` его не останавливает — останавливает отсутствие `ALTER` на таблице. Проверять надо именно `ALTER`, а не `DELETE`.

**3. `EXECUTE` и цепочка владения — самая недооценённая.** Дословно [док MS]:

> «Stored procedures take advantage of ownership chaining to provide access to data so that users do not need to have explicit permission to access database objects. An ownership chain exists when objects that access each other sequentially are owned by the same user. […] If all objects in the chain of execution have the same owner, then SQL Server only checks the EXECUTE permission for the caller, not the caller's permissions on other objects. Therefore you need to grant only EXECUTE permissions on stored procedures; you can revoke or deny all permissions on the underlying tables.»

Прочитайте последнее предложение ещё раз: механизм, который обычно подают как способ **дать** доступ, ровно так же работает и как способ **обойти запрет**. Если учётной записи выдан `EXECUTE` на процедуру, которая пишет в таблицу, и процедура с таблицей принадлежат одному владельцу, — права вызывающего на таблицу вообще не проверяются. `db_denydatawriter` в этом случае не срабатывает.

Практический вывод для настройки канала: **если запись должна быть закрыта, не включайте `EnableExecuteStoredProcedure` и `EnableStartStoredProcedure`.** Это не паранойя, а прямое следствие документированного поведения СУБД. Сам по себе выключенный флаг прав не меняет — он лишь не даёт агенту готового инструмента для этого пути.

Отдельно: тот же документ прямо советует убирать права и у роли `public`, потому что «All users inherit permissions from public» [док MS]. Учётная запись, которой персонально ничего не выдано, может унаследовать доступ через `public`.

### Server Mode расширяет периметр

Права — свойство конкретной базы. Если в строке подключения база не указана, сервер работает в Server Mode и получает доступ ко всем базам экземпляра ([setup.md](setup.md)). Роли и `DENY`, настроенные в одной базе, о других не говорят ничего: проверять надо каждую.

Практично: когда запись должна быть закрыта, укажите базу в строке подключения. Database Mode сужает периметр до одной базы структурно, а не соглашением.

### Цена механизма A

Подключение перестаёт быть пригодным для задач записи целиком, а не выборочно. Изменить это может только владелец базы — не агент и не настройка канала. Это одновременно и сила механизма (его нельзя снять переменной окружения), и его стоимость (каждое изменение требует согласования).

## Механизм B — не включать `Enable*`-флаги исполнения

### Что делает

Сервер регистрирует инструменты исполнения только при явно выставленном флаге. Пока `EnableExecuteQuery` не `true`, класс `ExecuteQueryTool` не регистрируется, инструмент не попадает в `tools/list`, и вызвать его нельзя [код 0.1.0: `Program.cs`]. То же для `execute_stored_procedure`, `start_query`, `start_stored_procedure`. Все четыре флага по умолчанию `false` — это заявленное изменение поведения версии 0.0.5: «Query and stored procedure execution tools are now **disabled by default** for security» [README].

Достоинство механизма в том, что его состояние **проверяемо снаружи**: счётчик и состав инструментов в `/mcp` показывают фактическую картину, а не то, что написано в конфигурации. Таблица «флаг → инструменты» и ожидаемые счётчики — в [setup.md](setup.md).

### Чего не делает

- **Не смотрит внутрь SQL.** При включённом флаге через `execute_query` проходит любой T-SQL.
- **Не меняет прав.** Выключенный флаг ограничивает агента, а не учётную запись. Та же учётка, подключённая любым другим клиентом, пишет как писала.

### Цена

Механизм грубый: он режет операцию целиком. Вместе с записью через `execute_query` пропадают и произвольные `SELECT` — остаётся только чтение схемы. Для разведочной аналитики это обычно неприемлемо, и тогда механизм B в чистом виде не подходит: выбирают A, а `EnableExecuteQuery` включают.

Второе: флаг снимается одной переменной окружения. Периметром безопасности он не является — это переключатель состава инструментов, не более.

## Механизм C — запретить инструменты в `permissions` Claude Code

### Что делает

Правила `permissions` в `settings.json` управляют тем, какие инструменты Claude Code позволяет вызывать. Имя инструмента MCP имеет форму `mcp__<имя-сервера>__<имя-инструмента>`; имя сервера — то, под которым он зарегистрирован ([setup.md](setup.md)).

Пример: закрыть произвольный SQL, оставив чтение схемы.

```json
{
  "permissions": {
    "deny": [
      "mcp__mssql__execute_query",
      "mcp__mssql__execute_stored_procedure"
    ]
  }
}
```

Файл — `~/.claude/settings.json` (пользовательский уровень) или `.claude/settings.json` в проекте. Это **не** `~/.claude.json`, где живут записи MCP-серверов: разные файлы, разные механизмы.

### Как правила разрешаются

- Порядок: «Rules are evaluated in order: deny, then ask, then allow. The first match in that order determines the outcome, and rule specificity doesn't change the order» [док CC]. Более узкое `allow` не отменяет более широкого `deny`.
- **Голое имя убирает инструмент из контекста:** «A bare tool name like `Bash` removes the tool from Claude's context entirely, so Claude never sees it. […] A scoped rule like `Bash(rm *)` leaves the tool available and blocks matching calls when Claude attempts them» [док CC]. Для MCP-инструмента полное имя `mcp__mssql__execute_query` и есть «голое имя» — инструмент исчезнет из списка, а не будет отклоняться при вызове.
- **Асимметрия глобов.** В `allow`: «Tool-name globs are supported only in the tool position after a literal `mcp__<server>__` prefix, such as `mcp__github__get_*`; the server segment must be glob-free» [док CC]. В `deny` и `ask` глоб может занимать всё имя: «`"*"` matches every tool, and `"mcp__*"` matches every MCP tool across all servers» [док CC]. То есть запретить всё разом можно, разрешить по маске имени сервера — нельзя.

### Ключевое свойство: правила исполняет Claude Code, а не модель

Дословно [док CC]:

> «Permission rules are enforced by Claude Code, not by the model. Instructions in your prompt or `CLAUDE.md` shape what Claude tries to do, but they don't change what Claude Code allows.»

Отсюда прямое следствие: **инструкция в роли, в `CLAUDE.md` или в промпте механизмом не является.** «Не пиши в базу», написанное текстом, — это пожелание модели, а не запрет. Запрет — это правило в `permissions`, `permission mode` или хук `PreToolUse`.

### Цена

Ограничение действует только на Claude Code и только там, где применён этот файл настроек. Тот же сервер, поднятый другим MCP-клиентом или запущенный руками, никаких `permissions` не увидит.

### Чем C отличается от B

Они частично перекрываются, и разница ровно в охвате:

| | Механизм B (флаг сервера) | Механизм C (`permissions`) |
|---|---|---|
| Где применяется | в процессе сервера | в Claude Code |
| На кого действует | на всех клиентов этого сервера | только на Claude Code |
| Гранулярность | операция целиком | отдельный инструмент, вплоть до одного из нескольких серверов |
| Как проверить | состав `tools/list` в `/mcp` | тот же `/mcp`: запрещённого голым именем инструмента там не будет |

Если серверов два и запись надо закрыть только на одном — это работа для C: `deny` на `mcp__mssql-prod__execute_query` при живом `mcp__mssql-dev__execute_query`.

## Приём: транзакционная обёртка

Не механизм ограничения, а способ выполнить изменяющий запрос и не оставить следа: обернуть его в транзакцию и откатить.

```sql
BEGIN TRAN;
UPDATE dbo.Orders SET Status = 'X' WHERE Id = 1;
SELECT @@ROWCOUNT AS Affected;
ROLLBACK;
```

Работает это только **внутри одного вызова инструмента**. Каждый вызов `execute_query` открывает собственное соединение и закрывает его после чтения результата [код 0.1.0: `DatabaseService.ExecuteQueryAsync`, `CommandBehavior.CloseConnection`], поэтому `BEGIN TRAN` в одном вызове и `ROLLBACK` в другом — это две разные сессии СУБД: незакрытая транзакция откатится сама при закрытии соединения, а `ROLLBACK` во втором вызове упадёт, потому что откатывать нечего. Подробнее о границе одного вызова — в [limits.md](limits.md).

Что нужно понимать про этот приём:

- Он **не заменяет прав**: пока транзакция открыта, изменения реально применены и держат блокировки. Запись, которая запрещена правами, здесь просто не выполнится.
- `TRUNCATE TABLE` тоже откатывается внутри транзакции: «A `TRUNCATE TABLE` operation can be rolled back within a transaction» [док MS].
- Как обёртка взаимодействует с уровнями изоляции и что при этом видят другие сессии — вопрос семантики T-SQL, он в `skill-tsql`.

## Чем ограничение записи не является

| Не механизм | Почему |
|---|---|
| `ApplicationIntent=ReadOnly` | Свойство маршрутизации Always On, а не запрет. На первичной реплике с настройками по умолчанию такое подключение успешно пишет. Разбор с таблицей исходов — в [connection-string.md](connection-string.md) |
| Инструкция в роли или `CLAUDE.md` | «Permission rules are enforced by Claude Code, not by the model» [док CC]. Текстом запрет не создаётся |
| Название сервера или базы вроде `*-readonly` | Соглашение об именовании; на права не влияет |
| Умолчание `EnableExecuteQuery=false` | Ограничивает состав инструментов, не права. Снимается одной переменной окружения |
| Отсутствие DML-инструментов у сервера | У выбранного сервера отдельных инструментов записи и нет — писать можно тем же `execute_query`. Отсутствие кнопки «удалить» не означает, что удалить нельзя |

## Как сочетать

Скилл не выбирает за вас. Сводка по цене каждого варианта:

| Механизм | На кого действует | Стоимость внедрения | Что теряется |
|---|---|---|---|
| A — права учётной записи | на всех и всегда | выше всех: нужен владелец базы | подключение перестаёт годиться для записи целиком |
| B — не включать `Enable*` | на всех клиентов сервера | нулевая, одна переменная | вместе с записью уходят произвольные `SELECT` |
| C — `permissions` | только на Claude Code | низкая, одна строка в настройках | ничего, кроме гибкости самого правила |

Типичные сочетания и их смысл:

- **A + включённый `EnableExecuteQuery`** — рабочая раскладка для разведочной аналитики: запись закрыта правами, произвольный `SELECT` доступен. Дыры механизма A закрываются тем, что процедурные флаги остаются выключенными.
- **B в одиночку** — годится, когда от базы нужна только схема.
- **C поверх A** — когда учётная запись пишущая и менять её нельзя, а конкретному агенту писать не нужно. Помните: это ограничение клиента, не базы.
- **Только C** — ограничение, которое снимается редактированием файла настроек тем же пользователем. Как удобство — да; как гарантия — нет.

## Три ошибки, специфичные для этого раздела

Общие запреты канала собраны в [SKILL.md](SKILL.md) и здесь не повторяются. Ниже — то, что ошибочно именно при работе с ограничением записи.

- **Считать `db_denydatawriter` полным запретом изменений.** DDL, `TRUNCATE` и `EXECUTE` через цепочку владения он не покрывает — разбор выше.
- **Проверять периметр в Server Mode по одной базе.** Права действуют в каждой базе экземпляра отдельно; настройка в одной ничего не говорит про остальные.
- **Считать механизм проверенным, потому что он настроен.** «Настроено» и «работает на этих данных» — разные утверждения; второе проверяется на стороне базы её владельцем.

Что из перечисленного действительно проверено на вашей базе — вопрос к её владельцу. Скилл описывает механизмы и их документированные границы; проверка того, как они настроены у вас, выполняется на ваших данных и в этот скилл не входит.
