# Agent Teams — Диагностика

Справочник нестандартных ситуаций Agent Teams: тиммейты не появляются, «пропавший» тиммейт, ошибки API, потеря транскрипта при SendMessage, осиротевшие tmux-сессии, сбои mailbox. Ряд поведений зависит от версии Claude Code — при сомнении сверяйся с официальной докой (code.claude.com/docs/en/agent-teams) как источником истины по версиям.

## Mailbox (механика доставки)

- Inbox каждого агента — JSON-файл: `~/.claude/teams/{team-name}/inboxes/{agent-name}.json`.
- Claude Code **валидирует каждую запись** при чтении mailbox-файла. Записи, не совпадающие с форматом сообщения, репортятся как ошибки и **убираются из файла автоматически**; валидные сообщения при этом доставляются. Отдельная битая запись доставку не останавливает.
- Ручное удаление `~/.claude/teams/{team-name}/inboxes/{agent-name}.json` — **крайний путь**, а не штатная процедура. Прибегать к нему, только если доставка в конкретный mailbox встала намертво и симптом воспроизводится: повторяющаяся ошибка чтения mailbox, при которой сообщения до агента не доходят.

## Тиммейты не появляются

Проверить по порядку:

0. **Команда вообще сформировалась?** Claude иногда спавнит обычных субагентов вместо команды, а они попадают в ту же панель агентов — сами по себе строки в панели формирование команды не доказывают. Если так — попросить ещё раз, явно запросив именно agent team.
1. **«Пропавший» тиммейт — это скрытие строки, а не остановка.** Idle-строка панели скрывается, но тиммейт остаётся запущен и адресуем. Чтобы вернуть строку — отправить тиммейту сообщение по имени (`SendMessage`); строка вернётся на его следующем turn.
2. **Достаточно ли сложна задача.** Claude сам решает, спавнить ли команду, исходя из задачи. Простую задачу он команду не образует.
3. **Split-panes: установлен ли tmux** (если режим запрошен явно):
   ```bash
   which tmux
   ```
4. **iTerm2:** проверить, что установлен CLI `it2` и включён Python API в настройках iTerm2.

## Скрытие и сворачивание idle-строк

Если тиммейт «пропал» из панели — это скрытие строки, **а не остановка**. Пока строка скрыта, тиммейт остаётся запущен и адресуем; строка возвращается на его следующем turn (например, после `SendMessage` по имени).

Механика скрытия: строка idle-тиммейта **остаётся** в панели, пока работает хоть один агент — её можно выбрать, чтобы посмотреть транскрипт или дослать работу. Когда в простое оказываются все, idle-строки прячутся через 30 секунд.

**Сворачивание при >3 idle:** когда одновременно в idle больше трёх тиммейтов, строки сверх первых трёх сворачиваются в одну строку-счётчик, например `2 idle agents` (когда в idle пятеро). Выбрать её и нажать Enter — развернуть; Esc — свернуть обратно. Работающие, упавшие и просматриваемый сейчас тиммейты всегда сохраняют свои строки.

## Слишком много permission-промптов

Пермишен-запросы тиммейтов всплывают у лида, что создаёт трение. **Пре-одобрить типовые операции** в permission settings ДО спавна тиммейтов — тогда прерываний меньше.

## Тиммейт остановился на ошибке

- Тиммейт может остановиться после ошибки вместо восстановления. Открыть его вывод: выбрать тиммейта в agent panel и нажать Enter (in-process) либо кликнуть в его pane (split). Дальше — либо дать доп. инструкции напрямую, либо заспавнить замену.
- Тиммейт, чей turn завершился на **ошибке API**, уведомляет лида, что он упал, и включает текст ошибки — вместо того чтобы выглядеть завершившимся нормально.
- Сообщение от лида или другого тиммейта **будит** in-process тиммейта, ждущего retry упавшего API-запроса, — он повторяет запрос немедленно, не дожидаясь полной задержки retry.

## SendMessage вернул «No transcript found for agent ID»

Штатно продолжение работы опирается на транскрипт агента: описание инструмента `SendMessage` обещает «names keep working after an agent completes (a send resumes it from its transcript)». Транскрипт может оказаться недоступен и внутри живой сессии, без `/resume`: наблюдалось дважды подряд — отправка возвращала «No transcript found for agent ID». Причина не установлена.

- ЕСЛИ отправка вернула эту ошибку -> спавнить агента заново **с полным контекстом**: транскрипта, из которого он мог бы продолжить, больше нет, и ссылки на прошлые turn'ы для нового инстанса пусты.
- НЕ путать с отказом по коллизии имён: там сообщение об ошибке говорит, на какого агента сейчас указывает имя, и лечится перенацеливанием, а не пересозданием.

## Сообщение отрапортовано отправленным, но не дошло

На сборках **до 2.1.224** `SendMessage` мог сообщить «Message sent», хотя запись в inbox тиммейта фактически провалилась — отправитель считал сообщение доставленным, получатель его не видел. С 2.1.224 провалившаяся доставка репортится ошибкой.

- ЕСЛИ тиммейт не реагирует на сообщение, которое отправка признала успешным -> не строить гипотез про idle: отправить повторно и, если тишина сохраняется, открыть транскрипт тиммейта напрямую (agent panel -> Enter).

## Директории команд не удаляются

Дока обещает, что config-директория команды (`~/.claude/teams/{team-name}/`) удаляется при завершении сессии. На практике такие директории могут накапливаться — например, когда сессия была не завершена штатно, а убита.

- Накопившиеся `~/.claude/teams/session-*` — **не признак поломки** команды и не требуют вмешательства.
- Полагаться на автоочистку как на гарантию не стоит: если директории мешают, удалять их вручную безопасно только для сессий, которые заведомо не идут.
- Директорию task list (`~/.claude/tasks/{team-name}/`) это не касается — она сохраняется намеренно, чтобы возобновлённые сессии не теряли задачи, и живёт по `cleanupPeriodDays`.

## Лид завершился раньше времени

Лид может решить, что команда закончила, до фактического завершения всех задач. Если так — сказать ему продолжить. Если лид начал делать работу сам вместо делегирования — сказать «дождись, пока тиммейты завершат свои задачи».

## Осиротевшие tmux-сессии

Если tmux-сессия сохраняется после завершения сессии Claude Code — вероятно, она не была полностью очищена. Посмотреть список и завершить нужную:

```bash
tmux ls
tmux kill-session -t <session-name>
```
