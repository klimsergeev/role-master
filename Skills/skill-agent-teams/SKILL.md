# Agent Teams

## Назначение

Скилл описывает процедуру использования Agent Teams -- экспериментальной фичи Claude Code (актуально для текущих версий) для параллельной работы нескольких агентов-тиммейтов, каждый в своём контекстном окне, с прямой peer-to-peer коммуникацией и общим списком задач.

**Применяется ТОЛЬКО тогда, когда пользователь явно попросил команду или тиммейтов.** Типовые задачи, под которые пользователь такую просьбу формулирует: ревью, дебаг конкурирующих гипотез, новые модули, кросс-слойная координация (фронт + бэк + тесты). Сама по себе форма задачи основанием поднять команду не является -- см. Принцип 1.

> **Фича экспериментальная и выключена по умолчанию.** Дока прямо предупреждает: «Agent teams are experimental and disabled by default… known limitations around session resumption, task coordination, and shutdown behavior». Учитывать нестабильность: не полагаться на восстановление после `/resume`, перепроверять статусы задач, закладывать медленный shutdown (см. «Ограничения» и troubleshooting.md).

Указания нет -- скилл не применяется. Что делать вместо команды, здесь не описывается: предмет скилла -- работа агентских команд и только она.

## Принципы

1. **Команда -- ТОЛЬКО по явному указанию пользователя** -- тиммейты поднимаются, когда пользователь в текущей сессии прямо попросил команду или тиммейтов. Указания нет -- команда НЕ поднимается и НЕ предлагается, скилл не применяется.
2. **Тиммейта ОБЯЗАН остановить тот, кто его поднял** -- работа сдана -> `TaskStop` по каждому тиммейту. Висящих «на всякий случай» тиммейтов не оставлять (см. Шаг 5).
3. **Лид координирует, тиммейты исполняют** -- основная сессия является лидом: спавнит тиммейтов, создаёт и назначает задачи, синтезирует результаты. Тиммейты работают независимо, каждый в своём контексте.
4. **Команда формируется автоматически** -- отдельного шага создания команды нет. Team возникает при спавне первого тиммейта; директории и config генерируются при старте сессии и чистятся при выходе.
5. **Спавн на естественном языке** -- тиммейты запрашиваются в промпте обычным текстом, лид сам вызывает Agent tool. Ручные TeamCreate/TeamDelete не используются.
6. **Idle -- нормальное поведение** -- тиммейт уходит в idle после каждого turn, просыпается при сообщении. Idle не является ошибкой.
7. **Peer-to-peer коммуникация** -- тиммейты общаются напрямую через SendMessage (по одному сообщению на получателя), без посредничества лида. Доставка автоматическая.
8. **Один team на сессию** -- нет вложенных команд, нет параллельных teams, лид фиксирован на всю сессию.

## Актуальность потока (важно)

Скилл описывает **актуальный поток**. Раньше команду создавали вручную через инструменты `TeamCreate`/`TeamDelete` и заранее задавали имя. Оба инструмента **удалены**: команда теперь формируется автоматически при спавне первого тиммейта, а очистка происходит при завершении сессии. Источник истины по версиям и поведению фичи — официальная дока: code.claude.com/docs/en/agent-teams.

Оговорка: в некоторых сборках окружения инструменты `TeamCreate`/`TeamDelete` и параметр `team_name` у Agent tool всё ещё могут присутствовать в списке доступных. Их считать устаревшими и **не использовать** -- `team_name` в Agent tool принимается, но игнорируется; поле `team_name` в payload хуков (`TaskCreated`, `TaskCompleted`, `TeammateIdle`) несёт производное от сессии имя и объявлено deprecated.

## Включение фичи (ОБЯЗАТЕЛЬНО проверить)

Agent Teams выключены по умолчанию. Включаются переменной `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` -- в окружении оболочки или в `.claude/settings.json` (секция `env`):

```json
{
  "env": {
    "CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS": "1"
  }
}
```

При подключении:

1. Проверить наличие переменной (`.claude/settings.json` -> секция `env`, либо окружение).
2. Вывести результат:

   **Agent Teams**
   Переменная CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS: [найдена / НЕ найдена]

- ЕСЛИ переменная не найдена -> предупредить: "Agent Teams недоступны. Добавить `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` в `.claude/settings.json` -> секция `env`?"
- ВСЕГДА помни: переменная читается **при старте сессии**. Добавленная в уже идущую сессию -- не активирует Teams: нужен перезапуск. Без переменной команда при старте не создаётся, директории не пишутся, тиммейты не спавнятся.

## Отличие от субагентов

| Аспект | Субагент (Agent tool) | Teammate (Teams) |
|--------|----------------------|------------------|
| Контекст | Своё окно, результат возвращается вызвавшему | Своё окно, полностью независим |
| Связь | Только с вызвавшим (report back) | Друг с другом напрямую через SendMessage |
| Координация | Всё ведёт вызвавший агент | Общий task list + самоназначение |
| Лучше для | Сфокусированной задачи, где важен только результат | Сложной работы, требующей обсуждения и коллаборации |
| Завершение | Возвращает результат и завершается сам | ОБЯЗАН быть остановлен через `TaskStop`, иначе висит до конца сессии |

Строка «Лучше для» описывает свойства механизмов, а не даёт право выбирать колонку самому: правая колонка включается ТОЛЬКО явным указанием пользователя (Принцип 1).

## Инструменты

> **Набор инструментов тиммейта урезан относительно обычной сессии.** К нему применяется тот же фильтр, что и к фоновому субагенту: все MCP-инструменты сохраняются, встроенных остаётся ограниченный набор, сверху добавляются task- и cron-инструменты. На конкретный состав не полагаться вслепую: если задача требует конкретного инструмента -- проверить его доступность у тиммейта **прежде**, чем поручать работу. Подробности -- [tools-reference.md](tools-reference.md).

### Agent (спавн тиммейта)

Тиммейты спавнятся через **Agent tool**, вызываемый лидом. Отдельного шага создания команды нет -- первый спавн формирует team автоматически.

- **Тиммейта из вызова делает параметр `name`** (установлено прямым сравнением в одной сессии): с `name` агент становится адресуемым тиммейтом и живёт до `TaskStop` или до конца сессии, без `name` при той же включённой переменной запускается обычный субагент, который вернёт результат и завершится. Переменная включает возможность команд, но тиммейтом каждый вызов не делает -- выбор в момент вызова. Поэтому `name` заполняется ТОЛЬКО когда пользователь попросил команду (Принцип 1).
- Тип тиммейта выбирается по нужным ему инструментам (см. Шаг 2).
- Параметры `team_name` и `mode` устарели: принимаются, но игнорируются -- не задавать их как рабочие параметры.
- Имя тиммейту назначает лид при спавне, и оно ОБЯЗАНО совпадать с именем роли тиммейта -- значением `subagent_type` того же вызова. Правило целиком, вместе со случаями «двое одной роли» и «роли нет» -- Шаг 2, блок «Имя тиммейта».
- Параметр `isolation: "worktree"` даёт тиммейту отдельный временный git-worktree -- изолированную копию репозитория. Когда применять -- см. «Правила -> Для лида». Полный перечень параметров -- [tools-reference.md](tools-reference.md).

### SendMessage

Прямая отправка сообщений между агентами по имени.

| Параметр | Обязательность | Описание |
|----------|---------------|----------|
| `to` | обязательный | Имя получателя-тиммейта -- оно же имя его роли (например `"research-analyst"`, при двоих одной роли `"research-analyst-1"`), либо `"main"` -- основной диалог (только для фоновых субагентов). НЕ UUID, кроме документированных исключений (см. «Правила -> Для тиммейтов») |
| `message` | обязательный | Текст (plain text) или структурное сообщение |
| `summary` | обязателен, когда `message` — строка | «5-10 word summary shown as a preview in the UI» |

> Источник по `summary` — **схема самого инструмента `SendMessage`** (описание параметра), а не doc-страница Agent Teams. Формулировка «5-10 слов» и условие «required when message is a string» приведены дословно из схемы. Для структурного `message` (JSON) `summary` не требуется.

- Broadcast (`to: "*"`) **не поддерживается**. Чтобы достучаться до всех -- отправить по одному сообщению на каждого получателя.
- Plain-text вывод агента НЕ виден другим агентам -- для коммуникации обязателен вызов SendMessage.
- Доставка автоматическая: сообщения от тиммейтов приходят лиду как новые turn'ы, inbox вручную проверять не нужно.
- При ретрансляции чужого сообщения **не цитировать оригинал** -- он уже показан пользователю.
- Сам по себе `SendMessage` **не требует включённых Agent Teams**: переменная нужна только для структурных протокольных сообщений (`shutdown_request`, `plan_approval_response`).
- Протокольные JSON-сообщения (`shutdown_response`, `plan_approval_response`) -- legacy: отвечать ими только если получен соответствующий `_request`. НИКОГДА не инициируй `shutdown_request` сам и не считай его средством завершения: тиммейта снимает только `TaskStop` (см. Шаг 5).

### Task-инструменты (общий список)

Общий task list команды: **TaskCreate** (создать), **TaskGet** (прочитать задачу целиком), **TaskList** (посмотреть список), **TaskUpdate** (изменить, назначить через `owner`, сменить статус), **TaskStop** (остановить фоновую задачу или тиммейта). Полные параметры -- [tools-reference.md](tools-reference.md).

- Статусы задач: `pending`, `in_progress`, `completed`, плюс `deleted` -- он **необратимо удаляет** задачу, а не помечает её.
- ВСЕГДА читай актуальное состояние задачи через **TaskGet** перед **TaskUpdate** -- этого прямо требует описание инструмента.
- Зависимости: задача с незакрытыми зависимостями не может быть взята, пока зависимости не `completed`. Разблокировка автоматическая.
- Claim: взятие задачи защищено файловой блокировкой -- гонок при одновременном claim нет.
- Статусы могут отставать: если задача «застряла» -- проверить фактическую готовность работы и обновить статус вручную / попросить лида пнуть тиммейта.
- Шаринг task list между сессиями: задать `CLAUDE_CODE_TASK_LIST_ID` — тогда используется именованная директория в `~/.claude/tasks/`. Пример: `CLAUDE_CODE_TASK_LIST_ID=my-project claude`.

## Рабочий процесс

### Шаг 1: Проверить указание пользователя и включение фичи

1. **Указание.** Убедиться, что пользователь в текущей сессии явно попросил команду или тиммейтов. ЕСЛИ такой просьбы не было -> остановиться здесь: скилл не применяется, команду не поднимать и не предлагать.
2. **Фича.** Убедиться, что `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` активна (см. раздел «Включение фичи»). Если нет -- предупредить и предложить добавить, помнить про перезапуск сессии.

### Шаг 2: Спавн тиммейтов (только по указанию пользователя)

**Путь появления тиммейтов один: явное указание пользователя в текущей сессии.** Пользователь просит команду или тиммейтов -> описать лиду задачу и нужных тиммейтов обычным текстом, лид сам вызовет Agent tool и сформирует команду.

- НИКОГДА не предлагай команду по своей инициативе -- ни спавн, ни спавн «с подтверждением пользователя». Оценка «задача выиграет от параллельной работы» указанием НЕ является: обычные субагенты параллелятся так же.
- ЕСЛИ явного указания в сессии нет -> команду НЕ поднимать и НЕ предлагать, скилл не применяется. В частности, параметр `name` у Agent tool не заполняется: именно он превращает вызов в тиммейта (см. «Инструменты -> Agent»).
- Факт о харнессе: сам Claude Code тиммейтов без одобрения не спавнит -- «Claude won't spawn teammates without your approval». Это страховка платформы, а не разрешение предлагать команду.

**Панель агентов не доказывает, что команда создана.** Claude иногда спавнит обычных субагентов вместо команды, а они попадают в ту же панель -- по одному наличию строк в панели судить нельзя. ЕСЛИ вместо команды заспавнены субагенты -> попросить ещё раз, явно запросив именно agent team.

Выбор типа тиммейта по нужным ему инструментам:
- **Read-only** (Explore, Plan) -- только исследование, поиск, планирование. НЕ давать им имплементацию.
- **Full-capability** (general-purpose) -- полный доступ к Edit, Write, Bash. Для задач с изменениями.
- **Custom** из subagent-определений (project / user / plugin / CLI) -- проверить их ограничения по описанию.

Тиммейт из subagent-определения:
- Наследует из определения `tools` (allowlist) и `model`; тело определения **добавляется** к системному промпту тиммейта (не заменяет его).
- Координационные инструменты (SendMessage, Task-инструменты) доступны тиммейту всегда, даже если `tools` ограничивает остальное.
- Поля `skills` и `mcpServers` из frontmatter субагента к тиммейту **не применяются** -- skills и MCP-серверы грузятся из project/user settings, как в обычной сессии.

**Имя тиммейта (ОБЯЗАТЕЛЬНО):**

- **ВСЕГДА называй тиммейта именем его роли** -- значением `subagent_type` того же вызова Agent tool: `product-manager`, `ux-researcher`, `research-analyst`. Имя и роль совпадают посимвольно.
- **НИКОГДА не выдумывай имя по задаче** (`пишущий-продуктовый`, `security-reviewer`, `frontend-dev`). Задача тиммейта видна в плане запуска и в общем task list -- имя для этого не нужно, а по панели агентов по такому имени не видно, кто из пула ролей на самом деле работает.
- **ЕСЛИ в команде двое и более одной роли -> добавляй к имени числовой индекс** начиная с единицы: `research-analyst-1`, `research-analyst-2`. Роль в единственном экземпляре индекса НЕ получает.
- **ЕСЛИ у тиммейта роли нет** (general-purpose, файла роли не существует) -> имя `general-purpose`; при нескольких таких -- те же числовые индексы: `general-purpose-1`, `general-purpose-2`.
- ВСЕГДА перечисляй эти имена в промпте лиду явно: имена -- адреса `SendMessage` и `task_id` для `TaskStop`, и последующие промпты обращаются к тиммейтам именно по ним.

Контекст тиммейту: наследует CLAUDE.md, MCP-серверы, skills. НЕ наследует историю диалога лида -- задачные детали класть в spawn-промпт.

**Модель и effort тиммейта:**
- Модель тиммейта по умолчанию **НЕ наследуется** от `/model` лида. Дефолт меняется через **Default teammate model** в `/config`; вариант **Default (leader's model)** заставляет тиммейтов следовать текущей модели лида. В spawn-промпте модель можно задать явно (например «Use Opus for each teammate»).
- У этой настройки есть файловый ключ: `teammateDefaultModel` в settings.json -- алиас модели (например `"sonnet"`) либо `null`, чтобы наследовать текущий выбор `/model` лида. **Значение по умолчанию -- `"sonnet"`**: именно поэтому тиммейт, которому модель не задали ни в промпте, ни в определении агента, оказывается на Sonnet, а не на модели лида.
- Effort level тиммейт **наследует** от лида (в том числе в split-pane режиме).
- Модель и fast mode тиммейта **фиксируются при спавне**: `/model` и `/fast` меняют только настройки лида. `/effort` при просмотре тиммейта применяется к его последующим turn'ам (т.к. effort следует за лидом).

**При просмотре in-process тиммейта:** обычный текст и skills идут просматриваемому тиммейту, а built-in команды по-прежнему выполняются в сессии лида. Полный набор клавиш agent panel — см. раздел «Режимы отображения».

### Шаг 3: Создание и назначение задач

1. **TaskCreate** -- создать задачи в общем списке (ориентир: 5-6 задач на тиммейта).
2. **TaskUpdate** с `owner` -- назначить задачу тиммейту. Любой агент может задать/сменить `owner`.
3. Задачи с зависимостями разблокируются автоматически по мере завершения предшественников.

### Шаг 4: Работа команды

Тиммейты работают параллельно:
- Берут назначенные или самоклеймят свободные разблокированные задачи (в порядке ID, меньший первым).
- Общаются через **SendMessage** напрямую (peer-to-peer, по одному сообщению на получателя).
- Отмечают задачи завершёнными через **TaskUpdate**, затем проверяют TaskList на следующую работу.

Лид координирует, при необходимости требует plan approval (для рискованных задач тиммейт работает в read-only plan mode до одобрения его плана лидом), мониторит прогресс и синтезирует результаты.

### Шаг 5: Завершение (ОБЯЗАТЕЛЬНО)

- **ОБЯЗАН остановить каждого тиммейта через `TaskStop`, как только командная работа сдана.** В `task_id` передаётся голое имя тиммейта либо его agent ID формата `name@team`. Остановить нужно всех поимённо -- один вызов на тиммейта.
- **НИКОГДА не рассчитывай на просьбу завершиться естественным языком: она тиммейта не убивает.** Наблюдение проекта: после «заверши работу и выйди» шестеро тиммейтов провисели в idle девять дней. Лид отправляет shutdown-запрос, тиммейт может согласиться, отказаться или просто уйти в idle -- процесс это не снимает. Единственный проверенный способ -- `TaskStop`.
- НИКОГДА не оставляй тиммейтов висеть «на всякий случай» после того, как их работа сдана: цена -- idle-уведомления после каждого сообщения и процессы, живущие до конца сессии.
- Ручная альтернатива в in-process режиме -- клавиша `x` в agent panel на выбранном тиммейте (останавливает по одному). Для команды из нескольких быстрее `TaskStop` по каждому.
- Остановка может быть небыстрой: тиммейт сперва дорабатывает текущий запрос или tool call. Это не повод считать `TaskStop` не сработавшим -- проверять по панели агентов.
- Отдельного шага очистки нет: общие директории команды удаляются автоматически при завершении сессии.

## Что автоматически, а что вручную

| Действие | Как происходит |
|---|---|
| Создание команды | Автоматически при спавне первого тиммейта |
| Имя команды | Производное от сессии: `session-` + первые 8 символов session id |
| `~/.claude/teams/{team-name}/config.json` | Генерируется автоматически при старте, обновляется при join/idle/leave |
| `~/.claude/tasks/{team-name}/` | Общий task list, сохраняется локально, не выгружается, переживает /resume |
| Очистка config-директории | Автоматически при выходе из сессии (task list остаётся по cleanupPeriodDays). На гарантию не полагаться -- см. [troubleshooting.md](troubleshooting.md) |
| Доставка сообщений | Автоматическая, inbox вручную не поллить |
| Разблокировка задач по зависимостям | Автоматическая |
| Остановка тиммейта | **Вручную**: `TaskStop` по имени или `name@team`. Сам тиммейт не завершается -- живёт до конца сессии (Шаг 5) |

`config.json` содержит массив `members` (у члена -- `agentId`, `name`, `agentType`, `joinedAt`, `cwd` и др.) и рантайм-состояние (id сессии лида, tmux pane id). Формат `agentId` -- `name@team`; поле `agentType` отсутствует, если лид не называл тип при спавне. Полная структура -- [tools-reference.md](tools-reference.md). **Не редактировать и не пре-заполнять вручную** -- перезапишется при следующем обновлении состояния. Для дискавери тиммейтов config -- запасной путь после списка соседей; для коммуникации использовать `name`, не `agentId`.

## Режимы отображения

Настройка `teammateMode` в `~/.claude/settings.json` (или флаг `claude --teammate-mode <mode>`):

| Режим | Поведение | Требования |
|---|---|---|
| `in-process` (дефолт) | Все тиммейты в основном терминале, выбор в agent panel (стрелки + Enter) | Любой терминал, без настройки |
| `auto` | Split-panes если уже внутри tmux или iTerm2 + `it2`, иначе in-process | tmux или iTerm2 + it2 |
| `tmux` | Split-panes, автодетект tmux/iTerm2 | tmux или iTerm2 |
| `iterm2` | Нативные split-panes iTerm2 | `it2` CLI + Python API в iTerm2 |

- Split-panes: у каждого тиммейта своя панель. Требуют tmux **или** iTerm2 + `it2`.
- Split-panes **не поддерживаются** в интегрированном терминале VS Code, Windows Terminal, Ghostty.
- Дефолтный режим -- `in-process`, пока `teammateMode` не задан явно.
- Флаг `--teammate-mode` экспериментальный и **не показывается в `claude --help`**. Отсутствие его в справке не значит, что флага нет: он рабочий и переопределяет `teammateMode` на одну сессию.
- У `tmux` известны ограничения на ряде операционных систем, лучше всего он работает на macOS. Рекомендованная точка входа в tmux -- `tmux -CC` в iTerm2.

**Клавиши agent panel (in-process):**

| Клавиша | Действие |
|---|---|
| Стрелки ↑/↓ | Выбрать тиммейта |
| Enter | Открыть транскрипт выбранного тиммейта и писать ему напрямую |
| `x` | Остановить выбранного тиммейта |
| Escape | Прервать текущий turn выбранного тиммейта |
| Ctrl+T | Тоггл чеклиста задач (показывается до пяти за раз) |

- Ctrl+T переключает именно **чеклист задач**, а не окно фоновой работы. Запущенные шеллы и субагенты смотреть командой `/tasks` (алиас `/bashes`).
- Команды `/teams` не существует -- командой управляют естественным языком через лида. Исключение -- остановка тиммейтов: она делается инструментом `TaskStop` или клавишей `x` в панели, словами тиммейт не снимается (Шаг 5). Настройка **Default teammate model** живёт в `/config`.

> Про скрытие/сворачивание idle-строк панели и когда «пропавший» тиммейт на самом деле работает — см. [troubleshooting.md](troubleshooting.md).

## Возможности

- **Plan approval для тиммейтов** -- по запросу тиммейт работает в read-only plan mode; по готовности шлёт лиду запрос на одобрение. Лид одобряет (тиммейт начинает имплементацию) или отклоняет с фидбеком (тиммейт дорабатывает план). Решение лид принимает автономно; критерии можно задать в промпте.
- **Пермишены** -- тиммейты стартуют с настройками лида (включая `--dangerously-skip-permissions`, если у лида он есть). Per-teammate режим на этапе спавна не задаётся -- меняется у отдельного тиммейта уже после спавна. Prompt'ы пермишенов тиммейтов всплывают в сессии лида и подтверждаются там. Дополнительно:
  - Получателю сообщения сообщается, что оно пришло **от другой сессии Claude, а не от пользователя**.
  - Тиммейт **не может** одобрить permission-промпт или дать согласие за пользователя.
  - Тиммейт, которому действие запретили, **не может обойти запрет**, передав действие другому тиммейту.
  - В auto mode заявление об одобрении, пересланное другим агентом, трактуется как **недоверенный ввод**, а не подтверждение пользователя. С 2.1.222 классификатор auto mode дополнительно просматривает каждое межагентское сообщение до доставки и заблокированное сообщение получателю не доходит.
  - **Plan approval -- намеренное исключение:** сессия лида одобряет планы тиммейтов без отдельного промпта пользователю.
- **Хуки** -- три события команды: `TeammateIdle` (перед уходом в idle), `TaskCreated` (создание задачи), `TaskCompleted` (пометка задачи завершённой). Вмешаться можно двумя способами, и они делают **разное**: exit code 2 отменяет само действие и возвращает фидбек, оставляя тиммейта в работе; JSON `{"continue": false, "stopReason": "..."}` **останавливает тиммейта целиком**. Поля payload, ограничения matcher'а и детали -- [tools-reference.md](tools-reference.md).

## Правила

### Для лида (оркестратора)

- НИКОГДА не поднимай команду и не предлагай её без явного указания пользователя в текущей сессии (Принцип 1, Шаг 2).
- ОБЯЗАН остановить каждого тиммейта через `TaskStop`, как только командная работа сдана (Шаг 5). Просьба завершиться естественным языком тиммейта не снимает.
- ВСЕГДА спавни тиммейтов, запрошенных пользователем, через Agent tool по естественно-языковому описанию; не ищи и не вызывай TeamCreate.
- ВСЕГДА называй тиммейта именем его роли -- значением `subagent_type`; двоих одной роли различай числовыми индексами (`research-analyst-1`, `research-analyst-2`), тиммейта без роли зови `general-purpose` (Шаг 2). НИКОГДА не выдумывай имя по задаче.
- ВСЕГДА помни: idle после каждого turn -- норма, не ошибка. Не комментируй idle, пока он реально не блокирует работу.
- ВСЕГДА используй SendMessage, чтобы разбудить idle-тиммейта -- сообщение пробуждает его автоматически.
- ВСЕГДА клади задачные детали в spawn-промпт -- история диалога лида тиммейту не передаётся, а продолжение через SendMessage не гарантировано: транскрипт агента может стать недоступен, и тиммейта придётся поднимать заново (см. [troubleshooting.md](troubleshooting.md)).
- НИКОГДА не проверяй inbox и активность тиммейтов через terminal tools -- доставка автоматическая, коммуникация только через SendMessage.
- ЕСЛИ нужно сообщить нескольким -> отправь по одному SendMessage на каждого (broadcast нет).
- ЕСЛИ тиммейт шлёт DM другому -> лид видит краткое summary в idle notification; реагировать не обязательно.
- ЕСЛИ лид начал делать задачи сам вместо делегирования -> напомнить «дождись, пока тиммейты завершат свои задачи».
- ВСЕГДА разбивай работу так, чтобы у каждого тиммейта был свой набор файлов -- двое, правящих один файл, приводят к перезаписи. Избегай пересечения по файлам при декомпозиции задач.
- ЕСЛИ развести тиммейтов по файлам не выходит (общий модуль, конкурирующие реализации одного куска) -> спавни их с `isolation: "worktree"`. Каждый получает отдельный временный git-worktree -- изолированную копию репозитория, так что правки одного не затирают правки другого; результаты сводятся после. Это прямое средство против того самого риска перезаписи, о котором предупреждает правило выше.
  - Оговорка по версии: на 2.1.220 изоляция worktree покрывает не все типы сессий -- заизолированный агент может выполнить разрушительную git-команду против основного чекаута. Распространение изоляции на файловые правки и Bash во всех типах сессий появилось с 2.1.222.

### Для тиммейтов

- ВСЕГДА проверяй TaskList периодически, особенно после завершения задачи.
- ВСЕГДА бери разблокированные задачи в порядке ID (меньший ID первым).
- ВСЕГДА отмечай задачи завершёнными через TaskUpdate.
- ВСЕГДА общайся plain text, не JSON-статусами; используй TaskUpdate для статусов, а не structured-сообщения.
- ВСЕГДА обращайся к тиммейтам по имени, не по UUID. Имена продолжают работать и после завершения агента -- отправка поднимает его из транскрипта. Голый `agentId` -- документированное исключение ровно для двух случаев: у агента нет имени либо имя перехватил более новый агент (побеждает последний).
- ЕСЛИ нужно узнать список тиммейтов -> сначала смотри **список соседей**: системное напоминание перечисляет `main` и всех именованных агентов сессии, каждое имя -- валидный `to` для SendMessage. Это снимок на момент твоего старта, поэтому агенты, названные позже, в нём не появятся.
- ЕСЛИ в списке соседей нужного агента нет (появился после твоего старта) -> читай `~/.claude/teams/{team-name}/config.json` как запасной путь.

## Формат выдачи

При запуске команды лид выводит план:

```
**Team: {team-name}**
Тиммейты:
- {роль-1} -- {задача}
- {роль-2} -- {задача}

Задачи:
1. {описание задачи} -> {owner}
2. {описание задачи} -> {owner}
```

Имя тиммейта и есть его роль (Шаг 2), поэтому тип отдельной скобкой не дублируется: строка `- research-analyst -- сбор источников по конкурентам` уже говорит и кто работает, и над чем. Двое одной роли идут с индексами -- `research-analyst-1`, `research-analyst-2`.

При завершении лид выводит сводку:

```
**Team {team-name} завершён**
Результаты:
- {роль-1}: {краткий итог}
- {роль-2}: {краткий итог}
```

## Что НЕ делать

- НЕ вызывать TeamCreate/TeamDelete -- они удалены; команда формируется автоматически, очистка тоже.
- НЕ задавать `team_name` в Agent tool как рабочий параметр -- он игнорируется.
- НЕ редактировать и не пре-заполнять `config.json` вручную -- перезапишется рантайм-состоянием.
- НЕ использовать broadcast (`to: "*"`) -- слать по одному сообщению на получателя.
- НЕ создавать вложенные команды -- тиммейты не спавнят sub-teams.
- НЕ запускать несколько teams в одной сессии -- один team на сессию.
- НЕ рассчитывать на `/resume` или `/rewind` для восстановления in-process тиммейтов.
- НЕ использовать terminal tools для проверки статуса/активности тиммейтов; НЕ проверять inbox вручную.
- НЕ поднимать команду и НЕ предлагать её без явного указания пользователя -- «задача выглядит командной» указанием не является.
- НЕ давать тиммейту имя, выдуманное по задаче (`пишущий-продуктовый`, `security-reviewer`, `frontend-dev`), и НЕ сокращать имя роли -- имя тиммейта равно значению `subagent_type`, различаются только числовые индексы у двоих одной роли (Шаг 2).
- НЕ завершать тиммейтов просьбой на естественном языке и НЕ слать `shutdown_request` -- останавливает только `TaskStop`.
- НЕ оставлять тиммейтов висеть после сдачи работы.

## Ограничения

- Один team на сессию, scoped к ней -- нельзя создать дополнительные именованные teams или шарить team между сессиями.
- Нет вложенных команд -- тиммейты не управляют командой, только лид.
- Лид фиксирован на всю сессию -- нельзя повысить тиммейта до лида или передать лидерство.
- `/resume` и `/rewind` не восстанавливают in-process тиммейтов -- после resume лид может слать сообщения несуществующим тиммейтам; тогда попросить спавнить новых.
- In-process тиммейт не может спавнить фоновых субагентов -- его субагенты идут в foreground; запрос background (`run_in_background` или `background: true` в определении) вернёт ошибку.
- Пермишены задаются при спавне (наследуются от лида); per-teammate режим -- только после спавна.
- Split-panes требуют tmux или iTerm2 + it2; не поддерживаются в VS Code integrated terminal, Windows Terminal, Ghostty.
- Статусы задач могут отставать; остановка бывает медленной (тиммейт дорабатывает текущий запрос/tool call).
- Каждый тиммейт -- отдельный инстанс Claude со своим контекстным окном; он остаётся активным до `TaskStop` или до конца сессии. Просьба выйти, отправленная естественным языком, его не снимает (Шаг 5). Историю диалога лида и контекст других тиммейтов он не видит.
- Общие лимиты на число субагентов (конкурентность, глубина вложенности) к тиммейтам **не применяются** -- у команд «свои лимиты», но какие именно, дока не раскрывает. Жёсткого потолка на число тиммейтов нет: дока говорит «There's no hard limit on the number of teammates, but practical constraints apply» и рекомендует ориентир 3-5 по управляемости команды.
- Нет project-level эквивалента config: файл вроде `.claude/teams/teams.json` в проекте **не распознаётся** как конфигурация -- Claude трактует его как обычный файл.

## Примеры

### Пример 1: Параллельный code review (типовой)

**Запрос:** "Подними команду тиммейтов: нужен ревью безопасности, производительности и покрытия тестами для PR #142."

Указание явное («подними команду») -- скилл применим. Без этих слов ровно та же задача команду не поднимает: скилл не применяется, тиммейты не спавнятся и не предлагаются.

**Действия:** Лиду даётся естественно-языковой промпт:

```
Спавни трёх тиммейтов для ревью PR #142, имя каждого = имя его роли:
- Explore-1 -- уязвимости (токены, сессии, валидация ввода)
- Explore-2 -- производительность (N+1, утечки)
- qa-engineer -- покрытие тестами
Пусть каждый отревьюит и доложит находки.
```

Имена взяты по правилу Шага 2: двое read-only исследователей поднимаются типом `Explore` и различаются числовыми индексами, третий берётся из роли `qa-engineer` и идёт без индекса как единственный носитель роли. Имён по задаче (`security-reviewer`, `perf-reviewer`) не появляется -- по панели агентов должно быть видно, кто работает, а над чем -- видно в task list.

Лид сам вызывает Agent tool (без TeamCreate), формирует общий task list, тиммейты работают параллельно, обмениваются находками через SendMessage. Лид синтезирует итоговый отчёт и **сразу после сдачи отчёта останавливает всех троих**: `TaskStop` на `Explore-1`, `Explore-2`, `qa-engineer`.

### Пример 2: Тиммейт ушёл в idle, а его ждут (edge-case)

**Запрос:** "frontend-developer ушёл в idle, а general-purpose ждёт от него формат API."

**Действия:** Лид отправляет SendMessage к `frontend-developer` с запросом предоставить формат API для `general-purpose`. Сообщение автоматически пробуждает `frontend-developer` из idle. Лид НЕ использует terminal tools и НЕ считает idle ошибкой. Broadcast не нужен -- адресное сообщение конкретному тиммейту.

Про имена в этом примере: у фронтендера роль есть, и он назван ею; у бэкендной части подходящей роли в пуле не нашлось, тиммейт поднят типом general-purpose -- по правилу Шага 2 это и есть его имя, `backend-dev` придумывать нельзя. Он единственный без роли, поэтому индекса не получает.

### Пример 3: Дебаг конкурирующих гипотез (адверсариальный)

**Запрос:** "Собери команду тиммейтов и столкни их лбами: приложение выходит после первого сообщения вместо удержания соединения. Найти причину."

**Действия:**

```
Спавни 5 тиммейтов general-purpose с именами general-purpose-1 ...
general-purpose-5, каждый проверяет свою гипотезу выхода. Пусть общаются
между собой и пытаются опровергнуть теории друг друга, как научный спор.
Обнови findings-doc консенсусом, который сложится.
```

Все пятеро одного типа и без роли, поэтому имена -- `general-purpose` с числовыми индексами; называть их по гипотезам (`race-condition-hunter`, `socket-checker`) правило запрещает, гипотеза каждого живёт в его задаче в общем списке.

Тиммейты (general-purpose, потому что нужна проверка кода) исследуют параллельно, шлют друг другу SendMessage (по одному на получателя), спорят peer-to-peer. Выжившая теория с большой вероятностью и есть корневая причина. Лид фиксирует консенсус и останавливает всех пятерых через `TaskStop` -- по одному вызову на имя: `general-purpose-1` ... `general-purpose-5`.
