# Agent Teams

## Назначение

Скилл описывает процедуру использования Agent Teams -- экспериментальной фичи Claude Code для параллельной работы нескольких агентов с peer-to-peer коммуникацией. Применяется когда задача требует одновременной работы нескольких специализированных агентов, которые должны обмениваться информацией напрямую.

## Принципы

1. **Лид координирует, тиммейты исполняют** -- лид создаёт команду, назначает задачи и синтезирует результаты; тиммейты работают параллельно
2. **Idle -- нормальное поведение** -- тиммейты уходят в idle после каждого turn, пробуждаются через SendMessage
3. **Peer-to-peer коммуникация** -- тиммейты общаются напрямую через SendMessage, без посредничества лида
4. **Один team на сессию** -- нет вложенных команд, нет параллельных teams

## Самопроверка при подключении (ОБЯЗАТЕЛЬНО)

При подключении:
1. Проверить наличие переменной `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` в настройках проекта (`.claude/settings.json` -> секция `env`)
2. Вывести результат:

   **Agent Teams подключён**
   Переменная CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS: [найдена / НЕ найдена]

ЕСЛИ переменная не найдена -> предупредить: "Agent Teams недоступен. Добавить `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1` в `.claude/settings.json` -> секция `env`?"

## Отличие от субагентов

| Аспект | Субагент (Agent tool) | Teammate (Teams) |
|--------|----------------------|------------------|
| Связь | Только с вызвавшим | Друг с другом напрямую через SendMessage |
| Жизненный цикл | Выполнил задачу -- завершился | Живёт, уходит в idle, просыпается при сообщении |
| Координация | Результат возвращается вызвавшему | Общий task list + прямые сообщения |
| Task list | Нет | Общий `~/.claude/tasks/{team-name}/` |

## Инструменты

### TeamCreate

Создаёт команду: config в `~/.claude/teams/{team-name}/config.json` + task list в `~/.claude/tasks/{team-name}/`.

| Параметр | Обязательность | Описание |
|----------|---------------|----------|
| `team_name` | обязательный | Имя команды |
| `description` | опциональный | Описание команды |
| `agent_type` | опциональный | Тип агента |

Вызывает только лид (оркестратор).

### SendMessage

Отправка сообщений между тиммейтами.

| Параметр | Обязательность | Описание |
|----------|---------------|----------|
| `to` | обязательный | Имя тиммейта или `"*"` для broadcast |
| `message` | обязательный | Текст или structured сообщение |
| `summary` | обязательный для текстовых | 5-10 слов, краткое описание |

Протокольные сообщения: `shutdown_request`, `shutdown_response`, `plan_approval_response`.

### TeamDelete

Удаляет team и task директории. Без параметров (берёт team из контекста сессии).

## Рабочий процесс

### Шаг 1: Создание команды

Лид вызывает **TeamCreate** с `team_name` и опциональным `description`.

Результат: создаётся config в `~/.claude/teams/{team-name}/config.json` и директория задач `~/.claude/tasks/{team-name}/`.

### Шаг 2: Спавн тиммейтов

Лид вызывает **Agent** с параметрами `team_name` и `name` для каждого тиммейта. Тиммейты присоединяются к команде.

Выбор типа тиммейта:
- **Read-only** (Explore, Plan) -- только исследование, поиск, планирование
- **Full-capability** (general-purpose) -- полный доступ к Edit, Write, Bash
- **Custom** из `.claude/agents/` -- свои ограничения, проверять описание

### Шаг 3: Создание и назначение задач

1. **TaskCreate** -- создание задач в общем списке
2. **TaskUpdate** с `owner` -- назначение задач конкретным тиммейтам

### Шаг 4: Работа команды

Тиммейты работают параллельно:
- Выполняют назначенные задачи
- Общаются через **SendMessage** напрямую (peer-to-peer)
- Отмечают задачи завершёнными через **TaskUpdate**

Лид координирует и синтезирует результаты.

### Шаг 5: Завершение

1. Лид отправляет **SendMessage** с `shutdown_request` каждому тиммейту
2. Тиммейты отвечают `shutdown_response` и завершаются
3. Лид вызывает **TeamDelete** для очистки

## Config файл команды

`~/.claude/teams/{team-name}/config.json` содержит массив `members`:

```json
{
  "members": [
    {
      "name": "frontend-dev",
      "agentId": "abc123",
      "agentType": "frontend-developer"
    }
  ]
}
```

- `name` -- используется для SendMessage и task ownership
- `agentId` -- только для reference, не для коммуникации

## Правила

### Для лида (оркестратора)

- ВСЕГДА помни: тиммейты уходят в idle после каждого turn -- это нормальное поведение, не ошибка
- ВСЕГДА используй SendMessage для пробуждения idle тиммейтов -- сообщение разбудит их автоматически
- НИКОГДА не используй terminal tools для просмотра активности тиммейтов -- только SendMessage
- НИКОГДА не проверяй inbox вручную -- сообщения от тиммейтов доставляются автоматически
- ЕСЛИ тиммейт шлёт DM другому тиммейту -> лид видит summary в idle notification
- ЕСЛИ нужно сообщить всем -> используй broadcast (`to: "*"`), но экономно -- broadcast дорогой по токенам
- ЕСЛИ нужно завершить работу -> сначала отправь `shutdown_request` всем тиммейтам, дождись завершения, затем вызови TeamDelete

### Для тиммейтов

- ВСЕГДА проверяй TaskList периодически, особенно после завершения задачи
- ВСЕГДА бери задачи в порядке ID (меньший ID первым)
- ВСЕГДА отмечай задачи завершёнными через TaskUpdate
- ВСЕГДА общайся plain text, не JSON-статусами
- ВСЕГДА обращайся к тиммейтам по имени, не по UUID
- ЕСЛИ нужно узнать список тиммейтов -> читай `~/.claude/teams/{team-name}/config.json`

## Формат выдачи

При создании команды лид выводит план:

```
**Team: {team-name}**
Тиммейты:
- {name-1} ({тип}) -- {задача}
- {name-2} ({тип}) -- {задача}

Задачи:
1. {описание задачи} -> {owner}
2. {описание задачи} -> {owner}
```

При завершении лид выводит сводку:

```
**Team {team-name} завершён**
Результаты:
- {name-1}: {краткий итог}
- {name-2}: {краткий итог}
```

## Что НЕ делать

- НЕ создавать вложенные команды -- тиммейты не могут создавать sub-teams
- НЕ запускать несколько teams в одной сессии
- НЕ рассчитывать на `/resume` для восстановления тиммейтов
- НЕ использовать terminal tools для проверки статуса тиммейтов
- НЕ проверять inbox вручную -- доставка автоматическая
- НЕ вызывать TeamDelete пока есть активные тиммейты
- НЕ создавать custom агентов через этот скилл (отдельная процедура)
- НЕ путать с оркестрацией обычных субагентов (см. skill-agent-orchestration)

## Ограничения

- Один team на сессию
- Нет вложенных команд -- тиммейты не могут создавать sub-teams
- `/resume` не восстанавливает тиммейтов
- Каждый тиммейт потребляет токены независимо
- TeamDelete нельзя вызвать пока есть активные тиммейты
- Тиммейты не имеют доступа к TeamCreate/TeamDelete

## Примеры

### Пример 1: Параллельный code review (типовой)

**Запрос:** "Нужен ревью безопасности и производительности для модуля авторизации."

**Действия:**

```
Team: "review-auth"
Тиммейты:
- security-reviewer (read-only) -- проверяет уязвимости
- perf-reviewer (read-only) -- проверяет производительность

Задачи:
1. Проверить SQL-инъекции и XSS -> security-reviewer
2. Проверить N+1 запросы и утечки памяти -> perf-reviewer

Тиммейты обмениваются находками через SendMessage.
Лид синтезирует итоговый отчёт.
```

### Пример 2: Тиммейт ушёл в idle (edge-case)

**Запрос:** "Frontend-dev ушёл в idle, а backend-dev ждёт от него формат API."

**Действия:**

Лид отправляет SendMessage к frontend-dev с запросом предоставить формат API для backend-dev. Сообщение автоматически пробуждает frontend-dev из idle. Лид НЕ использует terminal tools и НЕ считает idle ошибкой.

### Пример 3: Full-stack фича с координацией

**Запрос:** "Реализовать фичу авторизации -- фронт и бэк параллельно."

**Действия:**

```
Team: "feature-auth"
Тиммейты:
- frontend-dev (full-capability) -- UI компоненты
- backend-dev (full-capability) -- API endpoints

Задачи:
1. Создать API /auth/login и /auth/logout -> backend-dev
2. Создать форму логина и хук useAuth -> frontend-dev

Frontend-dev спрашивает у backend-dev формат API через SendMessage.
Backend-dev отвечает напрямую (peer-to-peer).
```
