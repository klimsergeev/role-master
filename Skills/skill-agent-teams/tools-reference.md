# Agent Teams — Справочник инструментов и хуков

Точные параметры инструментов, доступных тиммейту, структура `config.json` и настройка командных хуков. Читать, когда нужно понять, можно ли поручить тиммейту конкретную работу, или когда нужны точные поля инструмента. Для запуска и координации команды — SKILL.md.

## Какие инструменты получает тиммейт

**Набор инструментов тиммейта урезан относительно обычной сессии.** К нему применяется тот же фильтр, что и к фоновому субагенту: MCP-инструменты сохраняются все, а из встроенных остаётся ограниченный набор. Дока субагентов формулирует это так: фоновый субагент «keeps every MCP tool but only these built-in tools», дальше идёт перечень; всё остальное удаляется, **даже если перечислено в поле `tools`** определения агента.

Сверх этого набора тиммейт команды сохраняет task-инструменты и cron-инструменты — дословно: «Teammates in agent teams additionally keep the task tools and cron tools: `TaskCreate`, `TaskGet`, `TaskList`, `TaskUpdate`, `CronCreate`, `CronDelete`, and `CronList`».

- ВСЕГДА исходи из того, что набор урезан. Если задача требует конкретного инструмента -- **проверить его доступность у тиммейта прежде, чем поручать работу**, а не предполагать наличие по аналогии с обычной сессией.
- Cron-инструменты (`CronCreate`, `CronDelete`, `CronList`) тиммейту выдаются, но к командной работе отношения не имеют -- в координации не используются.
- `TaskOutput` существует в типах SDK, но **тиммейту не выдаётся** -- искать его бесполезно.
- `TeamCreate` и `TeamDelete` не существуют вообще (удалены; см. SKILL.md, «Актуальность потока»).

## Task-инструменты

Пять инструментов общего списка задач.

| Инструмент | Назначение | Параметры |
|---|---|---|
| `TaskCreate` | Создать задачу | `subject` (обяз.), `description` (обяз.), `activeForm` (форма для спиннера), `metadata` |
| `TaskGet` | Прочитать задачу целиком по ID | `taskId` (обяз.) |
| `TaskList` | Список всех задач | без параметров |
| `TaskUpdate` | Изменить задачу | `taskId` (обяз.), `status`, `subject`, `description`, `activeForm`, `owner`, `metadata`, `addBlocks`, `addBlockedBy` |
| `TaskStop` | Остановить фоновую задачу или тиммейта | `task_id` (`shell_id` устарел) |

**Правила:**

- ВСЕГДА читай актуальное состояние задачи через `TaskGet` перед `TaskUpdate` -- это прямое предписание описания инструмента («Make sure to read a task's latest state using `TaskGet` before updating it»).
- Задача всегда создаётся со статусом `pending` и **без владельца** -- назначение идёт отдельным `TaskUpdate` с `owner`.
- `TaskList` возвращает по каждой задаче `id`, `subject`, `status`, `owner`, `blockedBy`. Полное описание -- только через `TaskGet`.
- `metadata` в `TaskUpdate` **мерджится**, а не заменяется; ключ со значением `null` удаляется.
- Зависимости задаются через `addBlocks` (эта задача блокирует перечисленные) и `addBlockedBy` (перечисленные должны завершиться раньше).
- Чтобы остановить тиммейта через `TaskStop`, передать в `task_id` его agent ID формата `"name@team"` либо голое имя тиммейта.

**Статусы задачи:** `pending` -> `in_progress` -> `completed`, плюс отдельный `deleted` -- он **необратимо удаляет** задачу, а не помечает её. Использовать только для задач, созданных по ошибке или потерявших смысл.

## SendMessage

| Параметр | Обязательность | Значение |
|---|---|---|
| `to` | обязательный | `"researcher"` -- тиммейт по имени; `"main"` -- основной диалог (только для фоновых субагентов) |
| `message` | обязательный | Строка либо структурное протокольное сообщение (`shutdown_request`, `shutdown_response`, `plan_approval_response`) |
| `summary` | когда `message` -- строка | «A 5-10 word summary shown as a preview in the UI», `maxLength: 200` |

- Обращение по **имени** -- дефолт: имена продолжают работать и после завершения агента (отправка поднимает его из транскрипта). Голый `agentId` (формат `a...-...`) из результата спавна использовать только в двух случаях: у агента нет имени, либо имя перехватил более новый агент (latest wins).
- При ретрансляции чужого сообщения **не цитировать оригинал** -- он уже показан пользователю.
- `SendMessage` сам по себе **не требует включённых Agent Teams**: без переменной работает обычный обмен сообщениями, и только структурные протокольные сообщения (`shutdown_request`, `plan_approval_response`) требуют включённой фичи.
- Broadcast (`to: "*"`) не поддерживается -- по одному сообщению на получателя.

## Agent tool: параметры, относящиеся к командам

| Параметр | Значение |
|---|---|
| `name` | Имя тиммейта. Делает его адресуемым через `SendMessage({to: name})` |
| `isolation` | `"worktree"` -- отдельный временный git-worktree, изолированная копия репозитория; `"remote"` -- запуск в облачном окружении (всегда фоновый, доступность гейтится) |
| `team_name` | **Deprecated; ignored.** «The session has a single implicit team» |
| `mode` | **Deprecated; ignored.** Субагент наследует permission mode родительской сессии; frontmatter определения агента может это переопределить |

## config.json команды

Файл `~/.claude/teams/{team-name}/config.json`. Генерируется и обновляется автоматически, **вручную не редактировать и не пре-заполнять**.

- Верхний уровень: `name`, `createdAt`, `leadAgentId`, `leadSessionId`, `members`.
- Член команды: `agentId`, `name`, `agentType`, `joinedAt`, `tmuxPaneId`, `cwd`, `subscriptions`, `backendType`; у заспавненного тиммейта дополнительно `color`, `model`, `prompt`, `planModeRequired`.
- Формат `agentId` -- `name@team` (та же форма принимается `TaskStop`).
- Поле `agentType` несёт тип агента, названный лидом при спавне, и **отсутствует, если лид тип не называл**.

Для дискавери тиммейтов сначала использовать список соседей (см. SKILL.md, «Правила -> Для тиммейтов»); `config.json` -- запасной путь.

## Хуки команды

Три события: `TeammateIdle` (тиммейт собирается уйти в idle), `TaskCreated` (создаётся задача), `TaskCompleted` (задача помечается завершённой).

**Два способа вмешаться, и они делают разное:**

| Механизм | Эффект |
|---|---|
| Exit code 2 | Действие не выполняется, stderr уходит модели как фидбек, тиммейт **продолжает работать**. Для `TeammateIdle` -- не уходит в idle; для `TaskCreated` -- откатывает создание задачи; для `TaskCompleted` -- задача не помечается завершённой |
| JSON `{"continue": false, "stopReason": "..."}` | **Останавливает тиммейта целиком**, как хук `Stop`. `stopReason` показывается пользователю |

**Поля payload** (сверх общих):

| Событие | Поля |
|---|---|
| `TeammateIdle` | `teammate_name`, `team_name` |
| `TaskCreated` | `task_id`, `task_subject`, опционально `task_description`, `teammate_name`, `team_name` |
| `TaskCompleted` | те же, что у `TaskCreated` |

- Все три события **не поддерживают matcher** и срабатывают всегда. Добавленный `matcher` молча игнорируется.
- `team_name` -- «Deprecated. Session-derived team name; will be removed in a future release». Не завязывать на него логику хуков.

## Изменения после 2.1.220

Ниже -- то, чего **нет на сборке 2.1.220**. Не применять, не убедившись, что Claude Code обновлён.

- **С 2.1.224 -- кросс-сессионный `SendMessage`.** Дословно: «Claude Code sessions can now message each other, on any of your machines, with `ListAgents` to discover them (macOS and Linux)». Инструмент `ListAgents` в 2.1.220 отсутствует; на этой сборке обмен сообщениями ограничен агентами своей сессии.
- **С 2.1.224 -- честный отчёт о доставке.** Раньше `SendMessage` мог отрапортовать «Message sent», хотя запись в inbox тиммейта провалилась; теперь провалившаяся доставка репортится ошибкой.
- **С 2.1.224 снят потолок в 200 субагентов на сессию** (лимиты конкурентности и глубины остались). К тиммейтам лимиты субагентов не применялись и не применяются -- см. SKILL.md, «Ограничения».
- **С 2.1.222 длинный `summary` не роняет отправку** -- он обрезается вместо отказа. На 2.1.220 держаться в пределах `maxLength: 200`.
- **С 2.1.222 в auto mode классификатор пермишенов просматривает каждое межагентское сообщение до доставки** -- см. SKILL.md, «Возможности -> Пермишены».
